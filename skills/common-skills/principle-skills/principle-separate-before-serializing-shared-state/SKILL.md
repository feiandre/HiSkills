# 先分离，再串行化共享状态

当并发参与者可能共享可变状态时，首先问它们是否需要同一个可变对象。如果不需要，就消除共享。如果共享确有必要，通过结构强制串行化：锁文件、顺序阶段、独占所有权。指令和约定不是并发控制。

**原因：** 对共享状态的并发写入会制造间歇出现、难以复现且调试成本很高的竞态条件。

**模式：**

1. **识别共享可变状态**（双方都读写的文件、双方都推送到的分支、双方都定义和使用的 API）。

2. **默认做法：消除共享写入目标。** 问自己：这些参与者需要一个规范对象，还是在发布彼此独立的事实？让每个参与者拥有自己的文件、键、分支或状态目录，只在读取/报告边界合并。两个工作者把各自的 `lastX` 字段写入同一个 `state.json`，仍然属于共享修改。`indexer-state.json` + `metrics-state.json` 则不是。

3. **仅当单一共享写入目标确实是不变量时，才通过结构串行化访问**（锁文件、顺序阶段、单写入者 actor，或原子比较并交换）。把“我们需要一把锁”视为需要检查的设计异味，而不是默认答案。
