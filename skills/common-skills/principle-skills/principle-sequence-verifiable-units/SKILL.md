# 将工作排列为可验证单元

把工作安排成一系列小单元，每个都结束于可检查的状态，当前单元通过之前不前进。

**原因：** 在导致故障的单元处捕获故障，定位成本低。批量结束后才发现的故障会被埋住，而且你已在损坏基础上继续构建。把同样单元按审查者可重放的顺序交付，会把“相信我”变成“看它先失败、再通过”。

**执行。** 在全面检查、迁移或任何一系列类似编辑中，开始下一项之前验证每项变更。每个单元都是一个前后括号：已知良好状态、一次变更、运行检查，然后继续。先 rebase 到干净主干，使每个检查针对真实基线进行。由工具执行编辑时，逐单元检查几乎免费。仍然运行它。

**交付。** 按证明工作的顺序堆叠提交和 PR。典型结构是先失败测试，再在上面放修复。其他叙述顺序包括先删减再重塑、先捕获基线再处理、先骨架再功能。每个提交都可独立落地，整个序列读起来像一份论证。

这是 **prove-it-works** 原则技能和 **build-the-lever** 原则技能在顺序方面的补充，前者保证每个检查真实，后者使逐单元检查成本低。
