# 构建省力工具

工作不简单时，构建完成它的工具，而非手工完成。

codemod、生成器或脚本每次以相同方式工作，重跑无需重新付出手工劳动。工具是审查者可以阅读并重跑以检查工作的一份制品。手工变更只能靠重做来重新验证。确定性脚本把“相信我”变成“运行这个”。

默认构建工具。只有任务琐碎、只是几处一眼可见的明显编辑时才跳过。

- 先手工完成第一个单元，了解做法，然后构建工具。通过对该单元重跑工具并与手工版本比较差异来证明它。使工具可安全重跑。
- 编辑用 codemod 或脚本；重复文件用生成器；分析用转储到 sqlite 后的查询；验证用可重跑检查。
- 确定性工具胜过并行分派。如果工具能一遍处理全部单元，就自行运行。不要派代理手工应用脚本能做的事。
- 向子代理分派工作时，把工具写成所有代理都读取的技能：做法、验证契约和禁止触碰边界集中在一个制品。把它放在被委派者写入范围之外，防止它们悄悄修改契约。
- 应用本原则会产出文件。如果引用了它，但差异中没有 codemod、脚本、生成器或委派技能，就没有应用它。
- 如果工作会延续到会话之外，提交工具。

判断标准是是否琐碎，而非是否重复。即使一次性工作，只要工具能使它可检查，也值得构建。按照 [Laziness Protocol](../principle-laziness-protocol/SKILL.md)，构建能完成或证明工作的最小脚本，绝不构建框架。

它不同于 [Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md)，后者把反复出现的指令变成持久护栏。本原则关注眼前工作的吞吐量和可审查性。将验证本身脚本化，参见 [Prove It Works](../principle-prove-it-works/SKILL.md)。
