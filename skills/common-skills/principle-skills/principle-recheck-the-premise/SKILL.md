# 质疑前提

当两个或更多共享同一个前提的修复方案都未能通过同一道关卡时，应当怀疑前提，而不是修复方案。

**原因：** 每一次修复失败，都是反驳其所假定信念的证据。在同一前提下尝试第三次修复，就是在证据已经表明原因不在的地方继续投入精力。

**模式：**

- **把前提写下来。** 前提就是每一个失败的修复方案都假定成立的那一句话。
- **在下一次修复之前检验前提。** 找到一个在前提为假时会产生不同结果的可观察现象，并进行观察。不仅要看失败的严重程度，还要看失败如何分布。按照[构建杠杆](../principle-build-the-lever/SKILL.md)，让检查可以重复运行。
- **跟随证据。** 如果证据与前提矛盾，原因就在别处。寻找这些失败共有、但该前提无法预测的特征。如果证据证实前提，则按照[修复根本原因](../principle-fix-root-causes/SKILL.md)继续追问下一个“为什么”。先前的修复可能处理了后果，而不是原因。
- **消除条件，而不是补偿它**，遵循[懒惰协议](../principle-laziness-protocol/SKILL.md)。如果证据表明某个部分总是处于不利一方，就改变使它处于该位置的因素。一个事后清理的机制会让原因继续存在，而且每次运行都会增加工作。

**停止条件：** 在把前提写下来并检验之前，不要开始下一次修复。

本原则与[从第一性原理重新设计](../principle-redesign-from-first-principles/SKILL.md)不同；后者围绕新需求重建设计。本原则质疑的是当前设计所假定的一个事实。
