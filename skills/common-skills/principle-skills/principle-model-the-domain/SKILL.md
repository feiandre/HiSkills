# 为领域建模

把真实领域编码进数据结构，而不是分散在条件语句中。与领域相匹配的结构能让无效状态无法表示，并消除分支。在编写代码时选择这种结构成本很低。事后恢复这种结构会被视为重构，因而遭到推迟。

优先考虑：

- 用状态机代替散落的布尔值、阶段或生命周期检查。

- 用类型化模型代替松散参数或重复的数据形状假设。

- 用映射、注册表、查找表或可辨识联合类型代替分散在多个文件中的分支。

- 用 reducer 或命令/事件模型代替临时拼凑的状态修改。

- 围绕一组领域知识组织模块，而不是按加载、验证、转换、保存这样的顺序组织。执行顺序不等于所有权。

- 用一个小的模块边界汇集重复行为、所有权或不变量。

- 在访问模式需要时，使用队列、缓存、索引、图、树或规范化集合。

- 任何其他适合的结构。如果没有适合的，先弄清代码绝不能允许什么，以及数据如何被读取，再找到恰好编码这些要求的结构。

不要强行引入抽象。如果当前形态已经清晰、局部化，而且不太可能扩展，就优先使用朴素的代码。对于增加间接层却没有消除分支、重复规则、无效状态或生命周期风险的抽象，要保持怀疑。

跳过这一步的信号是：一个新功能使现有 if/else 链又增加了一个分支，或者出现了第二个必须与第一个保持同步的布尔值。按时间顺序分解也是一种信号。以阶段命名的模块会在不同步骤中重复同样的领域规则。
