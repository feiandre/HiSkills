# 基础性思考

**结构决策**保留未来选择的价值。**代码级决策**保持简单。

**先数据结构。** 写逻辑前先把数据形状做对。及早定义核心类型，追踪每种访问模式，并选择符合主要路径的结构。

在代码层，对结构去重，而非每一行都去重。类型和数据模型应趋于一致。三条类似语句仍优于过早抽象。明确优于巧妙。测试行为和边界情况，而非行数。

**并发推论。** 在参与者之间共享状态前，问：“如果另一个参与者同时修改它，会发生什么？”如果答案不是“什么也不发生”，就隔离。

**先骨架。** 如果某事有益于所有后续阶段，就先做。问：“它的存在是否会使每个后续阶段受益？”CI、lint、测试基础设施和共享类型都是骨架。按保留选择价值的顺序安排：设置先于功能，测试先于修复。提交保持小且目的单一。

每次增量都应落地一个连贯抽象，或深化已有抽象。不要把一项新能力作为特殊协调逻辑分散到多个调用者。

删减先于搭骨架。先移除无用代码，再打基础。
