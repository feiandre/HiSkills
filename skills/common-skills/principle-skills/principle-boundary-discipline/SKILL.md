# 边界纪律

把验证、类型收窄和错误处理放在系统边界。无条件信任内部代码。业务逻辑放在纯函数中。外壳保持轻薄且机械化。

**原因：** 分散验证会产生噪声、冗余，并给人虚假的安全感。让逻辑远离框架连接代码，才能不依赖框架进行测试。

**模式：**

- **边界处**，包括 CLI 参数、配置文件、外部 API、网络协议：验证、返回错误、防御性处理。

- **系统内部：** 有类型数据、错误传播、不重新验证。信任类型。

- **跨越边界时。** 暴露领域概念，而非边界的私有表示。通用机制留在内部，专用策略放在边缘。

**应用：**

验证和错误处理：

- 解析配置时在边界验证，不在业务逻辑中验证

- 在边界把原始数据解析为领域类型

- 不通过公开接口重新导出传输、存储、框架或线格式类型

- 如果边界已经验证，调用链深处不再做冗余 nil 检查

代码组织：

- 业务逻辑放在无框架依赖的纯函数中

- 解析函数：从原始字节到有类型状态的纯转换

- 提示词构建：输入结构化状态，输出字符串

- 评分和评估：从状态到结果的纯转换

**检验：**

- “这份数据此刻正在跨越系统边界吗？”如果不是，验证就冗余。

- “这能成为外壳直接调用的纯函数吗？”如果能，就提取出来。
