# Sentry 错误历史

## 如何搜索

使用 Sentry MCP。

1. **定向。** 如果不知道项目 slug 和组织：

2. **搜索与目标相关的 issue。**

```
   search_issues (自然语言，例如 "中的错误 PaymentService 超时", "未处理异常 uploadFile")
   ```

根据目标处理的异常类名、函数或类名、检查的错误消息字符串以及文件路径构建查询。

3. **按 release 和时间窗口缩小范围。**

```
   search_issue_events (按 release、时间、环境、trace ID、标签过滤)
   get_issue_tag_values (对某个 issue 查看跨版本、用户、环境的分布)
   ```

对疑似 issue，检查 **首次出现** 和 **最后出现**（停止时间是否与目标发布日吻合）、**受影响 release**（哪些版本出现过，哪个版本修复）、以及**频率轨迹**（是否激增后解决）。

4. **拉取完整事件获取上下文。**

```
   get_sentry_resource (传入 Sentry URL 或 type+ID)
   ```

堆栈跟踪是否经过目标代码？标签和面包屑是否匹配目标防护的条件？

5. **检查目标附近发布的 release。**

```
   find_releases (目标提交日期附近)
   ```

将 release 版本与 PR 合并日期交叉核对。

6. **谨慎使用 Seer。**

Seer 的 AI 根因分析是假设生成器。把它视为推断而非权威。真实事件和堆栈跟踪才是主要证据。

## 应返回什么

对每个相关 issue：

- Issue ID 和标题

- 项目和组织

- 首次／最后出现时间戳

- 事件数量（已知时含采样率）

- 受影响的 release

- 一段有代表性的堆栈跟踪片段，显示与目标的关联（逐字摘录，不概括）

- 首次／最后出现与目标发布日期的相关性

- issue 链接

- 任何作者评论或解决说明
