# Linear 工单

## 来源包含什么

- 描述功能、bug 及其动机的 issue

- 附加在 issue 上的项目文档（通常是 PRD 或规格）

- 父/子 issue 关系（更广的倡议 → 具体工单）

- Issue 评论（澄清、范围变化、“为什么这样做”的理由）

- 标签（如 `compliance`、`customer-request`、`perf`），标示动机类型

- 解释范围变化的动态更新

- 附件和关联 GitHub PR

Linear 常保存产品/业务上下文：“因为客户 X 要求”，或“这是为了第三季度合规计划”。

## 如何搜索

使用 Linear MCP。

1. **从关联工单开始。**种子提交或 PR 引用工单 ID（如 `ENG-1234`、`[BUG-567]`）时，先用 `get_issue` 获取完整 issue 和评论。

2. **按关键词列出相关 issue。**用 `list_issues` 搜索功能名、关键符号或业务术语，多试几种说法。

3. **遍历 issue 树。**落在子 issue 上时获取其父项；子项偏战术，父项常说明“为什么”。

4. **读取项目文档。**issue 属于项目时用 `get_project` 检查附件文档，规格和理由常在项目级文档中。

5. **检查标签和里程碑。**标签提示动机类别（客户请求、事件后续、合规），里程碑关联截止日期，也常揭示动机。

## 什么算好证据

- 说明业务问题的 issue 描述：“客户 Acme 因 SOC2 审计而需要 X”

- 记录决策的评论：“我们选择方案 B，因为方案 A 要改动计费服务”

- 标题像倡议的父 issue：“第三季度企业就绪”“减少付款失败”

- 附加的 PRD 或规格

- 如 `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 的标签

## 常见陷阱

- **范围漂移。**PR 引用的工单可能关闭后以不同范围重开；阅读完整历史。

- **机械模板。**有“为什么”栏目却填套话；泛泛的“改善用户体验”通常不是答案。

- **陈旧工单。**旧工单可能反映已改变的计划；核对日期并对照代码发布时间。

- **重复关闭链。**沿 duplicate-of 关系追到规范工单。

- **私有工作区内容。**无法访问 issue 时记录缺口，不要猜测。

## 返回内容

对每个相关工单返回：

- 工单 ID 和标题

- 从描述或评论直接引用的全部问题/动机原文（不要改写；综合器需要准确文本引用）

- 标签、父 issue、项目

- 作者、创建日期、关闭日期

- 可用时附工单链接
