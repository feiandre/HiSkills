# Datadog 遥测

## 此来源包含什么

Datadog 保存运行时记录，即生产环境实际发生了什么，区别于此前的计划或讨论。

- **指标。**团队埋点的计数器、仪表和直方图。指标*存在*本身即证明有人认为该数字值得观察。

- **监控与告警。**团队认为值得叫醒某人的条件。`rate_limit_hit > 10/min` 触发监控，直接证明团队担心该阈值。

- **仪表盘。**团队认为某子系统重要的精选视图。

- **APM 跟踪与 span。**请求级运行数据，用于“为什么慢”/“为什么这里超时”。

- **日志。**高容量事件记录，常包含促成防御性代码的错误条件。

- **事件。**带时间线与事后分析链接的正式事件记录。

- **Notebook。**团队的探索性调查，常含假设与分析。

## 如何搜索

使用 Datadog MCP。先宽泛，再收窄。

1. **识别所属服务。**

2. **先查仪表盘和监控。**

仪表盘或监控覆盖目标时，记录其查询和关注阈值。阈值常能回答“为什么限制在 N”。

3. **围绕目标的指标。**

将指标轨迹与目标的添加/变更日期关联，是有力支持证据：“`payment_timeout` 指标在 2023-11-03 激增，而重试逻辑在 2023-11-06 合并。”

4. **日志。收窄，不要倾倒。**

使用符号、错误字符串或功能名搜索。**强烈优先时间限定查询**（例如改动前后 30 天）。

5. **APM span 与跟踪。**

适用于超时、重试、慢路径和跨服务行为。

6. **事件。**

若目标看起来具有防御性，搜索添加时间附近的事件。时间线含“为 X 添加防御检查”的事件几乎是直接证据。

## 这里什么算好证据

- 查询和阈值与代码执行约束匹配的监控（代码限制为 100，监控在请求超过 100/min 时告警）

- 目标作者创建的仪表盘，其组件对应代码测量或防护的内容

- 显示代码合并前生产激增、之后稳定的指标

- 引用目标代码、相同符号或相同错误字符串的事件记录

- 显示防御代码将防止的具体错误模式、时间戳在改动前窗口内的日志

## 常见陷阱

- **相关不等于因果。**PR 前激增、之后稳定仅提示可能，因为同一窗口可能有其他改动。检查邻近 PR。

- **过度拟合找到的图表。**图表反映制作者视角。名为“重试成功率”的图表证明团队在意重试成功，并不证明某行代码因此存在。

- **遥测消失。**指标可能被重命名、删除或保留期很短。找不到相关窗口数据是缺口，不是空结果。

- **大规模噪声。**按服务、标签和时间窗口积极收窄日志搜索。使用 `analyze_datadog_logs` 聚合，而不是转储原始日志。

- **有埋点不等于由它导致。**指标表明有人足够重视某物而测量它，并非代码*因为*它而添加。与提交/PR 日期交叉引用。

## 应返回什么

对每个相关条目：

- 类型（dashboard / monitor / metric / log pattern / trace / incident / notebook）

- 标题或名称

- 链接或标识符（仪表盘 ID、监控 ID、指标名称、事件 ID）

- 所有者/作者及创建/修改日期

- 与问题相关的具体条件、查询或引用（尽可能逐字）

- 相关性：它对目标代码提示了什么，以及联系强度
