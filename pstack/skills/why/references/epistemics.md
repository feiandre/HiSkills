# 认识论

当证据是历史的、零碎的、有时矛盾的，如何判断置信度，并向用户表达而不压成虚假确定性。代码显示做什么，不显示*为何存在*。原因存在于提交、PR、工单、文档和对话中，它们不完整、有偏差且有时缺失。假装不是这样，会产出自信却误导用户的猜测。

## 置信层级

输出中每个断言都属于一个层级；层级决定章节和措辞。

### 1. 直接证据

明确文本引用直接回答问题：作者实际*写下*的原因，而非“代码做 X，所以作者想要 X”。例如 PR 描述“修复用户有超过1000项时无法分页的问题”，工单“客户 Acme 在安全审查中提出，因此要加此功能”，代码注释“// 限制到100，因为上游 API 拒绝更大值”，设计文档“我选 A 不选 B，因为需要跨重启持久化”，或作者聊天“旧方案测试不稳定，所以换这个”。

措辞：自信、现在时、有引用。“它存在是因为 X。”

### 2. 支持推断

多条间接证据汇聚到一个结论；没有单一来源明说，但组合起来很可能。例如 PR 标题“改善性能”、工单标签“perf”，相关提交都触碰同一热点；或者改动新增测试都处理超大输入；或同一周作者其他 PR 都提同一事故。

措辞：自信但明确是推导，并引用每项证据。“证据强烈指向 X：[具体项]。”

### 3. 解释性推断

对上下文的合理解读，但无明确支持。这是*你的解释*，不是记录事实。例如 PR 没写原因，但错误发生在生产（依据事件频道时间），修复当天仓促合并，因此可能是热修；或函数名显示重试，次数3符合团队其他约定。

措辞：带限定语并明确推导链。“给定 A 和 B，C 很可能，因为 D。”

### 4. 推测

证据薄弱但可能的假设，其他解释同样成立。值得提出，因为用户可能知道答案，但必须标为猜测。例如“可能是已修复浏览器 bug 的绕过方案，但未找到当时证据”，或“阈值可能是为 SLA 设置，但没有 SLA 文档引用它”。

措辞：“一种可能是 X，但无直接证据。”通常与其他可能放在竞争假设中。

### 5. 未知

你查过但找不到。这是有效且重要的结果，要记录。

措辞：“搜索了 X、Y、Z，未找到原因证据。”具体说明*搜索了什么*。比“找不到”更有用：“用关键词 A、B 搜工单跟踪器，扫描2023年以来触碰此文件的6个PR，并 grep 仓库中阈值字符串；均未找到理由。”

## 措辞指南

**置信词**意味着直接或支持证据，旁边必须有引用。绝不要用于推断：“because”“the reason is”“was designed to”（声称作者意图）、“fixes/addresses/solves”（声称实现目标）、“the team decided”（声称团队决定）。

**限定语**表示解释而非事实，在可合理推断中多用：“appears to”“seems to”“likely”“suggests”“is consistent with”“one reading is”“plausibly”“may have been”“the evidence points toward”。

**避免：**

- “obviously”（如果明显，用户不会问）

- “clearly”（几乎总在引出并不清楚的事）

- “of course”（同理）

- “just”（如“只是为了性能”——轻视并掩盖不确定）

- “I think/I believe”（你在综合证据，不是给个人意见；用“证据表明”）

## 避免合理化

今天看起来“合理”的代码可能因已失效或当时错误的理由写成。不要给混乱历史补上干净理由，不要假定作者做对再倒推，不要把复制粘贴当一致模式，也不要把无证据当成无问题（“没人提安全，说明无关”）。

## 谄媚陷阱

用户常嵌入假设：“为什么这样做，我猜是为了性能？”不要直接确认。猜测是调查提示，不是待验证结论；把它当候选并独立检查。证实则带引用说明，否则说明证据实际支持什么。

## 证据矛盾

在输出中带引用呈现双方，不要选更好听的故事。例如工单说“客户X合规需要”，PR说“清理技术债”。两者可能都真（工单是动机，PR是作者框架），也可能一项错误；让用户判断。

## 证据缺失

诚实的“不知道”很有价值。用户可知道答案不在明显处，需要问原作者/产品负责人/团队负责人，或决定不值得继续。未标记缺口而以自信猜测填补，会主动伤害用户，因为他们会据此行动。具体列出每个缺口：问题、搜索来源、每处搜索内容和结果（没有或只有间接材料）。

## 最终交付前

综合器交付前检查“发现”和“可合理推断”中每个断言：有引用，或移到推测/假设；措辞匹配层级；不把代码当作自身意图证据（若有，删除或重分类）；有“仍未知道”章节。若没有缺口反而可疑：证据异常完整，或某事被掩盖。
