# 措辞提示词

提示词说明意图和完成检查。手册提供步骤，所以几句朴素的话胜过一份规格。

## 应包含

- 目标。说明哪里不对或用户想要什么。

- 完成检查。它可以通过或失败。“做得更好”和时长不是检查。

- 要展示的证据。要求真实命令输出、流程视频、存储值或前后数字。

- 用户已经知道的内容。症状、复现步骤、日志或链接能节省智能体搜索。

- 真实约束。“先复现”“暂不要修改代码”“行为零变化”“继续前让我审阅”都会改变智能体的行为。

## 应省略

- 做法。说明要实现什么，给智能体寻找更好方法的空间。

- 技能或步骤列表。手写顺序会删掉或重排手册保留的步骤。只有要覆盖某项选择时才点名技能。

- 用户对原因的推测，直到智能体复述问题后再决定是否提供。说出的猜测会缩小搜索范围。

## 先加载上下文

- 报告混乱时，先让智能体用自己的话、用朴素语言复述底层问题，再做其他事。误读会在代码出现前暴露。

- 在新聊天中用 `/recall` 调取此前关于该主题的工作。旧聊天包含新智能体没有的上下文。

- 修改陌生代码前，用 `/how` 了解机制，用 `/why` 了解原因。没有可追踪模型的智能体会在第一个看似合理的位置修症状。

- 用 `/teach` 为选择提供论据，例如“说服我它会修复根因而不是症状”。论据比摘要更容易检查。

## 计划前先设计

- 绝不采用第一个设计。要求为几个选项制作原型；UI 提供截图或视频，再根据证据选择。

- 让原型回答开放问题。不要对抗式审阅抽象计划，因为审阅者会发明从未发生的风险。

- 对共享包或 API，先要求 README 或教程，再反推代码。文档会成为智能体自查的目标。

- 设计确定后才要求计划。计划的每一步都以检查结束。

## 简短跟进

- 聊天已保存任务后，“做吧”“继续”“一直做到完成”就是完整提示。

- 主题变化时以“新任务”开头，否则模式会把消息当作下一步。

## 离开前

- 说“我要睡了”或“我要离开”，让智能体停止提问。

- 把完成条件写成每次迭代都能运行的检查，并把该谓词交给 `/loop`。

- 要求从指定基点创建新工作树。

- 预先回答智能体会因此停下询问的事项，例如“提交前不要问我”。

- 要求记录决策日志供之后审计。

- 给出退出方式：“如果数小时后确实卡住，就停下并写清原因”。

## 用一行转向

- 重述目标：“我说目标是复现，还没让你修复。”

- 点名原则：“应用 prove it works，给我真实输出，不要构建日志。”

- 原则名称有效，因为智能体已经读过规则。它的回复应说明规则改变了哪项决策。
