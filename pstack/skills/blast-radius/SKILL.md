# 影响范围

交付前找出变更会在其他位置破坏什么。用于“blast radius of X”“what could this break”，或审查你尚不信任的小 diff。

它是 `how` 和 `why` 的配套技能。`how` 告诉你代码做什么。`why` 告诉你为何采用这种结构。Blast radius 告诉你会破坏其他什么地方。

任务不是罗列调用者。代理一秒就能 grep 出来。任务是寻找 grep 看不到的故障。

## 不要相信自己的报告

听起来合理的影响范围报告毫无价值。无论真假，它读起来都可能令人信服。所以不要只交还报告。找出整套判断依赖的一两个事实，通过运行代码证明它们。

### 你有多确定

对变更安全性依赖的每个事实，在成本低廉的范围内尽量推进到下列更靠后的级别，并说明停在哪里。

1. 你这么说。单独看毫无价值。

2. 你指出代码行。真实 `file:line`，或库自身源码。

3. 你展示坏情况不可能发生。逐步走过失败路径，证明到达不了。

4. 你运行了它。脚本或测试调用真实代码，若判断错误就明确失败。

5. 你在运行中的应用里复现了它。

第 4 步通常只需一个小脚本，导入应用交付时使用的同一库，调用你担心的那个确切函数。

## 步骤

1. 阅读变更。包括 diff、添加修改删除的符号，以及它现在与过去有何不同，包括 diff 没明说的部分。使用 `why` 的步骤 2 拉取 PR 和提交。

2. 找到使它安全的关键事实。多数看似危险的变更，因单个事实而安全，例如“此调用只移除已经失效的缓存条目，不做其他事”。找到这个事实。若成立，多数风险情形会一起排除。把时间花在这里，而非冗长的可能性清单。

3. 查看 grep 到不了的地方。阅读所调用库的源码，检查锁定版本及任何本地补丁。弄清执行时机：微任务、卸载和清理、Solid 与 React 的差异。追踪符号搜索遗漏的内容：API 返回的 JSON、数据库列、传输格式、另一种语言读取同样字节、功能开关、下游三跳的代码。

4. 诚实描述每个风险。给出真实发生可能性和发生时的真实代价。保留已确认的风险。已检查并排除的风险另列。规则与 `why` 相同。引用真实 `file:line`，搜索无结果也算答案，绝不编造调用者或 API。

5. 证明关键事实。编写运行真实代码的脚本或测试，运行它，并粘贴实际结果。

6. 对大型或广泛变更，以 `arena` 方式运行。向不止一个模型问相同问题，再合并答案。不同模型会发现不同的真实 bug。

## 交还什么

- **它做什么。** 改了什么，包括不明显的部分。

- **使其安全的关键事实。** 陈述它，说明推进到哪个级别，并展示证明。如果无法证明，写明 unproven。

- **风险。** 每项指出如何出错、`file:line`、可能性和严重程度，以及如何检查。粘贴重要风险的证明。

- **已排除。** 检查了什么，为何没有问题。

- **合并之前。** 能捕获真实 bug 的最低成本测试或复现，包括你写的脚本。

使用 `unslop` 处理文字，引用真实代码，并在公开发布前去除任何私人内容。

**回复：** 上述报告，关键安全事实要么已证明，要么明确标记未证明。
