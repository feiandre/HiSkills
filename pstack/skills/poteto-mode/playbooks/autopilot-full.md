### 全自动驾驶

**你负责裁决，绝不负责 PR。每位负责人把每个 PR 从构建带到合并；在你那支从未编写代码的群体证明即将合并的代码之前，什么都不合并。**

一条裁决覆盖一个补丁，绿色 CI 覆盖一个 head。第 4 步完整运行一次群体，之后只有重大变更才再次完整运行。`playbooks/shipping.md` 中的 patch-id 规则可以沿用车道结果，每个新 head 仍需自己的绿色 CI。

1. **操作者的关卡优先。** 授权只覆盖队列中的事项，因此操作者声明属于其本人、以及队列之外的 PR 都停在可合并状态。要求说明计划不代表放行。

2. **每个 PR 生成一位负责人，并把工作留在替代者能找回的位置。** 为整个计划只解析一次代码托管平台。GitHub CLI（`gh`）是默认值。若 `command -v origin` 成功且 Origin 能解析仓库，则所有 PR 操作使用 `origin pr`；否则留在 `gh` 并记录回退。绝不要求 Graphite（`gt`）。每位负责人是 Cursor 云代理，负责构建、按 `playbooks/opening-a-pr.md` 打开 PR、在真实产物上证明变更、按 `playbooks/babysit.md` 照看到全绿，并在第 4、5 步放行后合并。

尽早打开 PR，让 CI 和机器人并行工作。代码只有在去除空泛内容（来自 `cursor-team-kit` 插件的 `deslop` 技能，`/deslop`）并完成 `/no-comments` 检查后才就绪，因此完整群体针对完成代码运行。随后变基到当前主干，并在自证前报告代码就绪的 head，使验证运行于补丁最终落地的基线。报告之后每个 head；自证、CI 和照看都完成后报告可合并。修复轮次保持在该基线，除非主干冲突、破坏 CI，或在相同文件上落地已知并发变更，因为每次变基都会重启 CI。代码就绪推送前，以及需要验证者的后续推送前，在已提交 head 上运行涉及路径的仓库检查。

假定 VM 会死。启动后尽快推送，并按 **show-me-your-work** 技能在根代理存储（路径见系统提示词）创建决策轨迹；然后每完成一个单元就推送，再开始下一个。生成子代理的人在其存储中记录其 id、状态，以及同类过往运行得到的 stuck-after 时长，使父代理死亡后根代理仍可探测。只对自身分支强制推送，`--force-with-lease` 锁定为你上一次推送或接管的 SHA；任何不是你执行的推送都停下并报告根代理。

3. **各负责人从主干并行运行，绝不堆叠**，让每个 PR 独立落地。

4. **只做一次群体验证。** 完整群体在代码就绪 head 运行一次。只有新行为、重设计或大量新差异才再次完整运行。变基、合并冲突解决或小修复在新 head 只需单个验证者；只改措辞的变更不需要。按 **swarm** 技能在代码就绪 SHA 扇出独立验证者。它们重跑关卡，通过控制技能（如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或指定驱动在真实表面证明承重行为，并审计差异。没有实时车道，或在你审计可合并报告的凭据前，裁决不能算干净，因为任何车道都不信任未核查的主张。

只有能展示的问题才阻塞 PR：head 上的失败运行，或 PR 使某行文档变错。PR 基线已存在的问题（主干或堆栈下方的 PR）不阻塞，除非 PR 复制它或新触达它。只阻塞用户会遇到的缺陷、失败关卡或错误的已交付文档，其他都放后续事项。

5. **负责人只合并你已验证且在其落地主干上测过的内容。** 仅绿色 CI 从不授权合并。群体车道启动后，合并准备变基到当前主干、报告新 head 并等待绿色 CI。

合并前获取主干，判断其变更是否影响补丁，因为每次主干移动都变基永无止境。将要落地的代码从未测试时（冲突、双方都改的文件，或改变 PR 检查项），应变基并等待 CI。双方修改的 lockfile，若冻结安装在合并结果上通过，且 PR 修改的包在那里解析结果与 head 相同，则无需变基，因为该安装测试的是即将落地的 lockfile；安装失败意味着变基必须修复。主干改变补丁的调用方或其依赖（调用的代码、依赖版本）时，在合并结果上运行补丁检查，通过即合并；否则直接合并。若主干会在合并准备后迫使第三次变基，停下并报告根代理，由根代理排列冲突工作。

6. **运行根层。** 任何放松关卡的内容（提高预算或白名单条目）都需要验证者证明，再由你重新副签，因为负责人本身希望变绿。在批准权限覆盖下，该副签就是批准，负责人记录它并指向你的副签供车道检查。禁用或软失败的检查必须出现，因为它不再保护任何情况。绝不给或绕过代码托管平台强制执行的批准，副签无法覆盖。

操作者放行后，启用 `/loop 1h` 审计直到没有委派工作，因为长时运行会漂移，代理会静默卡住。每个周期从主干重读本操作手册并修正漂移（未报告 head、未记录代理），由负责人记录，因为漂移是记录缺口，不是停顿。它探测每个代理直到叶子车道，按副作用判断，因为状态文本与总结可能隐藏卡住子代理。代理报错、无法开始轮次，或超过 stuck-after 时长仍无新动作即卡住；第一次周期既未推送也未写轨迹行的负责人亦然。等待你或操作者不是卡住，要回答它。立即替换卡住代理，不等其停止落地。周期若为操作者改变什么，按 **ketchup** 技能收尾告知；无变化则保持安静。

7. **操作者叫停时立即停止。** 暂停以零写入命令传达到每位负责人。各自报告当前状态并保留简报，直到操作者释放。

**回复：** 按 **ketchup** 技能向操作者汇报，覆盖每个 PR 的状态与裁决、已合并内容、副签与原因、未决操作者关卡、暂存后续事项，并链接各 PR 与轨迹。
