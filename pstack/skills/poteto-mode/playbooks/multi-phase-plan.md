### 多阶段或多 PR 计划

**你负责计划，而非代码。计划是一份由负责人逐框执行、由操作者根据证据审计的检查清单。** 计划就是交付物。不要实施。

1. 变更只有一两个文件且方法显而易见时，跳过计划。说明这一点后停止。

2. 写计划前通过原型解决开放问题。每个问题都运行 `playbooks/prototype.md`。为附录 A 保留分支、SHA 和截图。只有任何运行都无法解决的产品或偏好决策才询问操作者。提供选项（**never-block-on-the-human** 原则技能）。

3. 使用 `subagent_type: "poteto-agent"` 的子智能体开展探索，并按“子智能体”章节明确指定模型（**guard-the-context-window** 原则技能）。按该章节为每个子智能体选择适合工作的推理级别及快速或标准速度。各自返回文件指针、约定、测试命令和入口点。不要内联大段转储内容。

4. 将下方骨架复制到计划文件，填写每个占位符。除非操作者指定路径，否则写入智能体存储中的 `docs/`。按照所示顺序保留所有标题及子块。每个 PR 一节。一个 PR 是一个拥有独立证据的变更（**sequence-verifiable-units** 原则技能）。在**如何阅读本文**中写明执行手册。运行允许合并时选择 `playbooks/autopilot-full.md`。由操作者落地 PR 时选择 `playbooks/autopilot-stack.md`。持续运行的项目使用 `playbooks/orchestrate.md`。

5. 完整遵循 `/technical-writing` 写作，再运行 `/unslop`。正文只采用一种 Diátaxis 模式，即操作指南。解释和参考资料放入附录。各标题说明任务或发现。不要使用长破折号。不要在句中使用冒号。

6. 运行 `node pstack/skills/poteto-mode/scripts/check-plan.mjs <plan.md>`，修复其输出的每一行问题（**encode-lessons-in-structure** 原则技能）。

7. 交回。发布计划路径和脚本输出，然后停止。只有操作者明确同意后，才按计划指明的执行手册开始执行。

**验证。** 只有测试不足以完成验证。只有单元、实际运行和性能复选框全部勾选，PR 才算通过验证（**prove-it-works** 原则技能）。这句话就是验证规则。每个验证块以它开头。实际运行块为必需项。按 **swarm** 技能，在 PR 头版本运行十条通道，使用 `swarm workers` 模型（默认 `grok-4.7-xhigh-fast`），通过控制技能操作真实界面。每条通道对应一个框，包含具体场景、保存的截图和通过判据。一条通道为**对照主干的回归通道。** 它在主干和头版本运行相同的关键承载场景。如果主干没有该功能，该通道记录这一事实，改为把关差异新增行为及用户等待的最终状态，而不是编造主干结果。性能关卡是双边的。主干和头版本都必须产生指定指标。如果主干缺少该功能，还需隔离差异新增的工作，为该工作及用户等待的端到端状态设定绝对预算。不要声称不同场景之间的比率。性能块写明指标、交错探测、首先测量的主干基线及包含失败阈值数值的规则。改变交互的 PR 需要审阅关卡。合并前由操作者在聊天中查看截图和视频。没有改变交互的 PR 写 `**Review gate.** None. <PR id> is not review-gated.`（中文即“**审阅关卡。** 无。<PR id> 无需审阅关卡。”），其下不设复选框。

**控制技能。** 按操作界面选择。浏览器、Electron 和网页 UI 使用 `cursor-team-kit` 的 `control-ui`。CLI 和 TUI 使用 `cursor-team-kit` 的 `control-cli`。原生移动端使用仓库现有的模拟器驱动技能。涉及两个界面的 PR 在两者上都设通道。没有控制技能的界面要列为附录 C 的风险，其实际运行块仍须说明每条通道如何驱动该界面。
