### Bug 修复

**你负责此任务。计划、审查、验证。** 将调查和修复委派给子智能体，你保持主导。按“子智能体”章节，为每个子智能体选择适合工作的推理级别和快速或标准速度。

保持科学态度。每一行发布代码都能追溯到运行时证据。“可能有帮助”的冗余保护是假设，不是修复，不应发布。证据推翻假设时，回退它促成的改动。只发布证据证明必要的最小变更，不多做。

1. 自己通过控制技能在匹配界面上复现（见“不可妥协事项”），即使调试或插桩协议要求让用户复现。只有控制面确实无法到达目标并有具体理由时才询问用户，而且要先尽可能驱动到极限。不能直接复现时，构造触发器、收紧条件或加插桩，直到触发。

2. 二分搜索原因。形成候选假设，逐一排除直到一项幸存。用对受影响子系统的 `how` 和回归历史的 **why** 技能为它们提供线索。每轮选择能最大削减剩余问题空间的切分，取得运行时证据并排除。程序状态不清楚时，加插桩或日志并在代码运行时读取。不要猜。用 Cursor 的 `/loop` 命令驱动漫长或顽固的追查。步骤 3 的 architect／interrogate 展开前，先用运行时证据确认幸存*机制*。

3. 计划修复。跨越函数边界时先用 `architect`。用配置的 bug 修复模型（默认 `grok-4.7-xhigh-fast`）将实现委派给子智能体，并给出具体范围。

4. 在同一界面验证。原始复现现在通过。“无法确定”或错误界面不算通过，要标记。单元测试显示分支行为，不证明 bug 消失。

5. 安排提交，使失败复现先于修复进入 git 历史。bug 有廉价本地测试路径时，按 **tdd** 技能的失败测试先行节奏执行。测试昂贵、集成重或不清晰时跳过。
   这是 **sequence-verifiable-units** 原则技能的标准形式：先失败测试，再叠加修复。

6. 运行**创建 PR**。

**回复：** 哪里坏了、根因、修复、如何验证。逐字粘贴先失败后通过复现的输出。
