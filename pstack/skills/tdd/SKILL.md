# 用 TDD 修复 bug

在修复测试路径清晰、成本低的 bug 时，先让错误行为能够被执行，再修改生产代码。目标是一个聚焦的回归测试，在修复前失败，修复后通过。

测试不切实际时，不要强求。如果可用测试需要大范围的测试支架搭建、脆弱的 mock、缓慢的端到端基础设施、仅生产环境才有的状态、模糊的复现步骤，或大量无关 fixture 改动，就跳过添加新测试，改用最接近且有用的验证。

## 工作流

1. **理解 bug。** 确定预期行为、当前行为、受影响路径以及最小可观察复现。

2. **选择范围最窄的可执行检查。** 优先使用该代码路径现有的最接近的单元、组件、集成或回归测试。如果没有明显且切实可行的测试路径，不要仅仅为了满足工作流而从零创建。

3. **先写失败测试。** 添加本可以捕获该 bug 的最小聚焦测试。测试应编码预期行为，而不是照搬当前实现。

4. **修复之前运行新测试。** 确认它因为预期原因失败。如果它通过，或因无关原因失败，先修正测试或复现方式，再编辑实现。

5. **修复 bug。** 在保留相邻契约的前提下，作出满足预期行为的最小生产代码变更。

6. **重新运行回归测试。** 确认测试现在通过。

## 无法实际编写失败测试时

改用最接近的可执行回归检查：针对性脚本、手动复现命令、浏览器自动化、快照比较、日志断言，或聚焦的集成检查。

宁可不新增测试，也不要坏测试。坏测试主要测试 mock、编码当前实现细节、依赖时序或无关全局状态、为小修复需要昂贵基础设施，或者证明修复后就会立即被删除。

## 约束

- 不要只为了匹配错误实现而修改测试。

- 除非预期行为确实改变且原因明确，否则不要弱化现有断言。

- 让回归测试聚焦于该 bug。避免大范围 fixture 改动或无关覆盖扩张。

- 如果 bug 间歇出现，尽可能让测试具有确定性，并记录所要固定下来的信号。

- 如果 bug 暴露了更广泛的一类失败，先落实聚焦的回归路径，再考虑增加同类覆盖。

## 最终回复

报告证据，而不只是结果：

- 给出修复前失败的测试或可执行检查的名称，以及它产生的失败。

- 给出修复后通过的测试运行，以及执行过的相邻验证。

- 如果无法展示修复前失败的证据，说明原因，并描述代替使用的最接近的回归检查。
