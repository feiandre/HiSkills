# 自动化我的工作方式

通过引导流程，把用户的工作约定转化为代理会遵循的技能。输出是一个为其定制的 `-mode` 技能，例如 `jay-mode`、`priya-mode`。

本技能编排其他三部分：内联挖掘检查（见步骤 1）、Cursor 内置 `create-skill`（编写）以及 **unslop** 技能（文字规范）。它安排执行顺序，不取代这些部分。

## 流程

### 0. 检查已有技能

递归查找与用户标识相匹配的 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md`。模式技能可位于个人分类目录（`.cursor/skills/<handle>/`），不限于顶层。若存在，用 `AskQuestion` 确认意图，除非用户已经说“更新我的技能”或类似意思：

- 更新已有技能（重复运行的默认选项）

- 从头开始（少见，执行前询问原因）

更新模式会改变后续流程：

- 步骤 1 只挖掘技能上次编辑以来的历史（`git log -1 --format=%cI <path>`）。

- 步骤 2 询问有什么变化或缺失，而非从零询问要记录什么。

- 步骤 4 原地编辑已有文件。保留用户未反驳的章节。用新证据修订相关章节。只有出现真正的新规则时才添加章节。

### 1. 挖掘其历史

并行分派前，先定位当前工作区的对话记录。系统提示词会给出工作区的 `agent-transcripts/` 目录。仅使用该路径。不要对 `~/.cursor/projects/*/` 做 glob 搜索。那会跨越工作区边界，读取无关项目的私人聊天。

在此范围内调查近期代理对话，寻找重复模式。让多个子代理并行处理不同历史切片，例如最近 2–4 周，分为 3 片，使每片都有足够材料。按照 **poteto-mode** 技能的 Subagents 部分，为每个子代理选择推理级别及 fast 或 standard 速度。每个历史切片挖掘子代理从父代理提供的工作区限定路径读取对话，寻找下列信号，并返回带证据指针的简短结构化模式清单。默认值得寻找的信号：

- 回复偏好（长度、语气、格式、“说简单些”的纠正）

- 委派习惯（子代理、模型、专门工作流、并行）

- 验证立场（什么算“完成”、单元测试与现场复现、审查者）

- 代码和文字规范（风格、引用原则、lint 和格式工具）

- 流程约定（worktree、提交、PR、审查和合并工具）

- 元偏好（任务中修复技能、提议新技能）

提升某个信号为规则前，在切片之间交叉核对。至少在两个切片中出现的模式置信度高。只出现一次的信号较弱，通常丢弃。

### 2. 直接询问用户

挖掘会漏掉尚未出现过的意图。使用 `AskQuestion` 工具（结构化多选），而不是让用户从头打字。

形式：一到两个问题，每题 4–6 个选项，类别题使用 `allow_multiple: true`。先宽泛地问“哪些方面最重要？”，再针对所选领域以具体选项跟进。结构化轮次之后，用一个自由回答的聊天问题捕获选项遗漏的内容。

不要一次丢出 20 个问题。

### 3. 聚类发现

将合并后的信号分组为章节。常见章节如下，仅使用适用的：

- **回复风格**：长度、语气、格式。

- **自主程度**：不询问就做多少、MCP 工具使用。

- **先理解**：界定或调查变更时选哪些技能。

- **子代理**：默认设置、并行、模型与任务匹配、专门工作流。

- **文字与代码规范**：原则、lint 工具、风格指南。

- **审查与验证**：复现立场、验证技能、实时测试工具。

- **流程**：git worktree、提交、PR、审查和合并工具。

- **技能**：编写技能的习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了结构。阅读它以把握粒度。不要复制内容。用户规则与 poteto-mode 的规则不同。

### 4. 起草技能

使用 Cursor 内置 `create-skill` 技能编写。放置要求：

- 路径：保留已有模式技能的分类。新模式若仓库已有该标识的个人分类，使用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认使用项目中的 `.cursor/skills/<handle>-mode/SKILL.md`；用户偏好个人技能时使用 `~/.cursor/skills/<handle>-mode/`。

- 标识：用户的名字或所选标识符。

- Frontmatter 的 `description`：以其名字 + `/<handle>-mode` + “按其风格工作”触发，不用“写代码”或“审查 PR”等通用关键词。

- Frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持为单个 YAML 标量。标点或换行需要时，加引号，或使用 `description: >-` 并缩进续行。

- Frontmatter 默认设置 `disable-model-invocation: true`。只有用户明确希望模式每轮适用时才取消此设置。

### 5. 迭代文字

对每一行应用 **unslop** 技能和 `create-skill` 的写作指南。

向用户展示草稿并接受反馈。预计会有多轮迭代。果断删减。模式技能不是手册。

### 6. 使其落地

在从 main 分出的 worktree 中工作。提交并创建 PR。不要直接推送到 main。

## 护栏

- **不要过度拟合一次对话。** 某次表达、另一次被否定的偏好是噪声。形成规则前要求多个实例。

- **不要耍巧。** 重述其他技能内容、发明隐喻或为代理读者写“诗意”文字，都只有成本而无收益。保持可操作。

- **引用，不内联。** 用户依赖的其他技能应以路径引用出现，而非粘贴摘录。其在别处维护的原则文档也一样。

- **章节保持最少。** 只有用户在该方面有具体、非默认的规则时才添加章节。“清晰沟通”不是一个章节。“短段落。比较选项时用表格。只有各项确实平行时才用项目符号。”才是。

- **称谓约定保持通用。** 命令式要求中用“用户”或“人类”，不用作者名字。

- **不要强求对称。** 如果用户没有值得记录的流程规则，完全跳过流程章节。

## 评估

`-mode` 技能是主观输出。类似 `create-skill` 的测试与迭代基准循环在这里没有用。与用户检查感觉：读起来像他们吗？漏了什么吗？然后交付。

只有实际使用中发现触发准确率有问题时，才运行描述优化循环。

## 何时不使用

- 用户想要任务专属技能，而非工作约定：单独使用 `create-skill`，无需挖掘。

- 用户想记录一个狭窄工作流，例如“我如何写提交消息”。那是普通技能，不是模式技能。
