# 竞技场

在启动任何工作之前，打开待办清单，每个阶段一项（界定任务、扇出、交叉评判、选择、嫁接、验证）。

## 阶段 A：界定任务

每个候选者都收到相同提示词，因此提示词就是契约。

1. 说明每个候选者要产出的产物。

2. 推导评分标准：3–6 条具体、可评分的条件，描述在*当前*任务上成功是什么样子。这是阶段 D 中选择者的工具。候选者只看到任务。

3. 选择执行者。使用 `~/.cursor/rules/pstack-models.mdc` 中的 `arena runners` 行。如果规则或该行不存在，默认分别使用一个 `claude-opus-5-5-xhigh` 和一个 `grok-4.7-xhigh-fast`。该行中的 `auto` 或 `inherit-parent` 条目表示父模型，因此省略其 `model`。如果 Task 工具拒绝某个已配置条目，让该席位使用其家族的默认模型，并说明。家族按前缀划分：`claude-*` 为一类；`grok-*` 与 `cursor-grok-*`、`composer-*` 为另一类。被拒绝的 `composer-*` 条目改用 `grok-4.7-xhigh-fast`。如果该家族没有默认值，或 Task 工具也拒绝该默认值，从错误消息中选择同一家族最接近的有效 slug；如果没有，就取消该席位并说明。如果取消后执行者少于两个，添加执行者直至有两个；若该行只有一个条目，则保留一个。每个新增执行者使用剩余执行者的模型；若没有剩余执行者，则省略 `model`，使其使用父模型，并说明。当竞技场覆盖多个设计方向时，生成更多执行者。当工作主要受生成能力限制而非判断敏感性影响时，可将同一模型运行 N 次。根据 **poteto-mode** 技能的 Subagents 章节，为每个子代理选择适合任务的推理级别，以及快速或标准速度。

4. 根据 **separate-before-serializing-shared-state** 原则技能，为每个候选者提供自己的输出位置（可行时使用 git worktree，否则使用 `/tmp/arena-<slug>/candidate-<n>/`）。

## 阶段 B：扇出

在同一条消息中生成全部 N 个子代理，设置 `run_in_background: true`，分别提供任务、共享基础资料的路径、自己的输出路径，以及产出产物和简短理由的指令；理由需列出考虑过的替代方案及被否决的方案。

如果某个候选者没有产出，使用 N-1 个继续推进，并注明退出情况。

## 阶段 C：交叉评判

阶段 B 的所有候选者完成后，从 `~/.cursor/rules/pstack-models.mdc` 的 `arena cross-judge pool` 行选择一个模型。如果规则或该行不存在，从 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast` 中选择。生成一个只读评判子代理。评判者绝不能来自父模型的家族，家族定义见阶段 A 步骤 3。按模型池顺序，仅尝试其他家族的条目。`auto` 或 `inherit-parent` 条目就是父模型，因此绝不能担任评判。使用默认模型池时，Claude 父模型选择 `grok-4.7-xhigh-fast`；其他任何家族的父模型首先选择 `claude-opus-5-5-xhigh`。如果 Task 工具拒绝某个条目，从错误消息中使用同一模型在最接近级别或速度下的有效 slug；若没有，移至下一条目。如果其他家族的所有条目都无法运行，以相同方式尝试默认模型池中来自其他家族的条目。如果仍都无法运行，跳过评判者，在阶段 D 独自选择基础方案，并说明。如果不知道父模型是什么，按模型池顺序尝试其中实际的 slug，并说明没有执行家族检查。评判者按路径标签查看评分标准和候选方案，为每条标准评分，并推荐基础方案及理由。它与阶段 D 中你的阅读并行执行。候选者还在写入时，不要生成评判者。

## 阶段 D：选择基础方案

选择之前，从头到尾阅读每个候选方案。逐条标准评分，不要凭整体感觉；如果阶段 C 运行了交叉评判者，与其结果比较。对基础方案意见一致可确认选择。意见不一致意味着你们其中一方存在偏见，或评分标准有歧义。作决定前阅读双方理由。

选择未来维护者最容易扩展且不会破坏不变量的基础方案。感觉两个方案不分上下时，根据懒惰协议，优先选择边界更清晰或 API 更小的方案。

## 阶段 E：嫁接

再次逐一查看落选候选方案，寻找值得移植到基础方案的部分，通常每个方案一两项，而不是大部分内容。根据 **redesign-from-first-principles** 原则技能，手工融入每项嫁接，让结果在同一个心智模型下保持一致。不要机械粘贴。

如果各候选方案收敛到同一形态，这是强烈的一致意见。说明这一点，并交付共识形态。不需要嫁接。如果各方案差异极大，说明阶段 A 的定义不足。重新界定并重新运行，而不是把分歧取平均。

## 阶段 F：验证

按照 **prove-it-works** 原则技能，像验证其他输出一样验证综合产物。如果验证发现了竞技场遗漏的问题，要么阶段 A 有误（重新界定并重跑），要么某个候选方案已经捕获但你遗漏了嫁接（返回阶段 E）。不要掩盖问题。

## 输出

一个综合产物，旁边附上简短的综合说明，指出基础方案及选择理由、交叉评判者的裁决或阶段 C 跳过了评判者、每项嫁接及其来源候选方案、被否决的内容及理由、任何收敛或退出情况，以及验证结果。
