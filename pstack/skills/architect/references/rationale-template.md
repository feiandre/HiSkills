# 设计理由模板

与类型草图一起交付的正文。一页。标题采用句首大写风格，不要套话。把斜体说明替换为实际内容。

## 问题

*一段。我们想做什么，现有系统或约束的哪些特点使设计形态不明显。如果[阶段 A](../SKILL.md#phase-a-ground-the-problem) 揭示了设计必须遵守的约束（要互操作的现有类型、不能破坏的调用方、跨越边界的不变量），在这里点明，使读者看到你看到的相同约束。*

## 用法（调用方视角）

*在类型草图之前先写本节。展示使用者阅读的 README 或快速入门，以及他们自己代码中两三个真实调用点。导入什么、调用什么、返回什么。[形态](#shape) 中的类型草图由此推导。两者必须一致。有分歧时让草图适应用法，不要反过来。调用方体验就是规格，类型为它服务。*

## 形态

*推荐的架构。先写数据结构，再写数据如何流经各签名。点明关键承重决策。说明哪些不变量编码进类型、验证位于哪里，以及系统刻意不做什么。明确评判接口深度：公共表面隐藏什么复杂度、调用方仍面对什么，以及接口为何不比所需更大。引用各决策背后的原则（例如 `per boundary-discipline`），不要重述原则。*

## 综合决定

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成为基础及原因，从其余每个候选采用了什么，拒绝了什么及原因。*

## 接受的取舍

*选定形态的每项取舍各占一个条目。形式：“我们接受 X，以换取 Y。”点明未来读者可能误认为疏漏的任何内容，包括看似过早优化或过早简化的事。*

## 考虑过的替代方案

*必填。至少指出一种具体替代形态，用一行解释落选原因。依据接口深度评判各方案，不只看实现是否简单。说明向调用方暴露什么复杂度、隐藏什么复杂度。设计空间确有竞争者时列两三个；约束已决定答案时一个也可以，结论写成“这是唯一可行形态，因为……”。不要列同一形态的不同口味。本节涵盖选定形态考虑并拒绝的设计方案，不是其他参赛候选。*

## 未决问题与风险

*绘制草图时注意到的、需要人类发表意见的事项，以及开始实现前值得指出的风险。写成问题而非断言，使人类回答成为解决方案，而不只是评论。*

## 下一实现步骤

*针对草图首先构建什么。一句话。综合完成后（或选择检查点时，阶段 D 签字后）你会立即开始写什么。*
