# Architect 运行器提示词

编排器在阶段 B 将此文件传给每个并行候选运行器，并填入周围的变量输入：任务、阶段 A 基础材料、隔离工作目录和输出路径。可用时工作目录是 Git 工作树，否则是草图目录下每个运行器的子目录。重要的是候选之间彼此独立。

你正在 architect 的并行探索中产出一个候选设计。先完整阅读 **architect** 技能，你身处其工作流中。输出候选设计包：类型草图、函数签名、模块映射，以及按 [`rationale-template.md`](rationale-template.md) 组织的文字理由。

遵循以下纪律。编排器在这些维度比较候选并选择基础设计。

- 调用方用法优先。先写 README 风格用法和两三个真实调用点，再写类型，并从它们推导类型草图。用法就是规格，二者必须一致，因此草图服从用法。

- 数据结构优先。核心类型正确后代码会变得自然。通过拟议结构追踪每种主要访问模式。如果答案是“以后再加入 map／index／cache”，结构就是错的。

- 接口深度。比较公开表面之后隐藏的能力与该表面大小。优先使用简单接口，把复杂性拉入被调用方，即使实现变得不那么简单。不要把传输或线缆类型放入公开 API，在接口后解析成领域类型。

- 共享状态：若两方都可能写入，问“会发生什么？”若答案不是“没事发生”，默认采用每个行为者独立状态，并在读取边界合并，遵循 **separate-before-serializing-shared-state** 原则技能。

- 让边界可见。函数体用 `not implemented` 错误，棘手逻辑用 `// TODO` 伪代码，文档注释说明意图和不变量。读者仅阅读类型和签名就应能追踪数据从输入到输出。

- 用类型编码不变量：难以误用的类型 > 运行时检查 > 文字注释，遵循 **encode-lessons-in-structure** 原则技能。

- 在边界验证，在内部信任类型，遵循 **boundary-discipline** 原则技能。业务逻辑使用纯函数，外壳保持薄。

- 每个不变量只有一个事实来源。推导而非同步。

- 适用时使状态转换幂等，遵循 **make-operations-idempotent** 原则技能。询问操作运行两次或中途崩溃时会怎样。

- 短调用链。追踪流程需要超过三个文件时，压平层级，遵循 **laziness-protocol** 和 **minimize-reader-load** 原则技能。

你是不同模型上的并行运行器之一。产出你的模型所能作出的最佳设计。不要为其他候选留退路。候选差异是选择基础和嫁接内容的信号。趋同于看似安全的中间方案会破坏探索。
