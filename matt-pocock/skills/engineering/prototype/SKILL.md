# 原型

原型是**用来回答问题的用后即弃代码**。问题决定形态。

## 选择分支

根据用户提示、周围代码，或（若用户在附近）提问，判断正在回答哪个问题：

- **“这套逻辑／状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。构建单个可分享 HTML 文件（自由操作按钮加分页引导演练），让状态机经过纸面上难以推理、非开发者也能驱动的案例。

- **“它应该长什么样？”** → [UI.md](UI.md)。在单个路由生成几个差异很大的 UI 变体，通过 URL 搜索参数和浮动底栏切换。

两个分支产生非常不同的产物，选错会浪费整个原型。如果问题确实含糊且联系不到用户，默认选择更匹配周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明该假设。

## 两个分支都适用的规则

1. **从第一天就明确是一次性产物。** 将原型代码放在实际使用位置附近（它所原型化的模块或页面旁），让上下文清楚，但命名要让普通读者看出它是原型而非生产代码。一次性 UI 路由遵守项目现有路由约定，不要发明新的顶层结构。

2. **运行要极其容易。** UI 原型通过项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击打开的一个 HTML 文件。无论哪种，启动都无需思考。

3. **默认不持久化。** 状态保存在内存。持久化是原型正在*检查*的事项，不应成为依赖。若问题明确涉及数据库，使用临时数据库或文件名清楚写着“PROTOTYPE, wipe me”的本地文件。

4. **跳过打磨。** 不写测试，不作超出原型*可运行*所需的错误处理，不做抽象。重点是快速学习。

5. **展示状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染所有相关状态，让用户看到变化。

6. **完成后保存。** 将任何已验证决策融入真实代码，然后把原型本身作为**一手来源**保存：提交到 `main` 之外的临时分支，并在实现 issue 留下指向该分支的上下文指针。也应在 issue 或提交中记录答案（结论和它解决的问题）。主分支只保留已验证决策。
