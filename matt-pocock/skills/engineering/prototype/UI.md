# UI 原型

在单一路由生成**几个根本不同的 UI 变体**，通过底部浮动栏切换。用户在浏览器中翻转，选择一种（或从各方案取部分），再丢弃其余。

如果问题关于逻辑／状态而不是外观，应走另一分支。使用 [LOGIC.md](LOGIC.md)。

## 何时适合这种形态

- “这个页面应该长什么样？”

- “提交前我想看看这个仪表盘的几个选项。”

- “为设置页面尝试不同布局。”

- 用户原本要在脑中比较三个模糊稿并耗掉一天的任何时候。

## 两种子形态：强烈优先 A

当 UI 原型**贴着应用其余部分**——真实页头、侧栏、数据和密度——时更容易判断。独立的一次性路由像真空：每个变体单独看都不错。有合理现有页面承载变体时默认用 A；只有确实没有附近归宿时才用 B。

### 子形态 A：调整现有页面（首选）

路由已存在。变体**在同一路由**渲染，由 `?variant=` URL 搜索参数控制。现有数据获取、参数和认证全部保留，只替换渲染。这是默认选择，除非有具体理由不用。

若新事物尚无页面，却*自然会位于某页面内*（仪表盘新分区、设置页新卡片、现有流程新步骤），仍属于 A。把变体挂载到宿主页面中。

### 子形态 B：新页面（最后选项）

只在被原型化的内容确实没有现有页面可嵌入时使用（例如全新顶层表面，或无法合理嵌入任何地方的流程）。

遵循项目现有路由约定创建**一次性路由**。不要发明新顶层结构。命名应明显是原型（例如路径或文件名含 `prototype`）。同样使用 `?variant=`。

确定 B 前先检查：真的没有现有页面可嵌入吗？空路由会隐藏有内容页面本会暴露的设计问题。

两种子形态的底部浮动栏相同。

## 流程

### 1. 陈述问题并选择 N

默认 **3 个变体**。超过 5 个往往从根本不同退化为噪声，因此上限为 5。

在原型位置或文件顶部注释中用一行写出计划：

> “设置页面的三个变体，通过 `?variant=` 切换，使用现有 `/settings` 路由。”

无论用户是否来反驳，都这样做。

### 2. 生成根本不同的变体

起草每个变体。各自必须满足：

- 页面目的及其可访问的数据。

- 项目组件库／样式系统（TailwindCSS、shadcn、MUI、普通 CSS 等）。

- 清楚的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构不同**：布局、信息层级、主要可供性不同，而不只是颜色不同。三个略调过的卡片网格不是 UI 原型，只是墙纸。两个草稿太相似时，重做一个并明确要求“不要使用卡片网格”。

### 3. 连接它们

在路由上创建一个切换组件：

```tsx
// 伪代码，适配项目框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：数据获取全部留在切换器上方，只替换每个变体的渲染子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同切换器。

### 4. 构建浮动切换器

屏幕底部中央的小型固定栏，包含三部分：

- **左箭头**：切到上一变体（循环）。

- **变体标签**：显示当前键，以及变体导出名称（如有），例如 `B (Sidebar layout)`。

- **右箭头**：切到下一变体（循环）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架路由，如 Next 的 `router.replace`、React Router 的 `navigate`），使变体可分享且刷新稳定。

- 键盘：`←`、`→` 也能切换。`<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时不要拦截方向键。

- 视觉上与页面区分（如高对比药丸、轻阴影），明显不属于正在评估的设计。

- 生产构建隐藏：依据 `process.env.NODE_ENV !== 'production'` 或等价检查，防止误合并原型时把栏带给用户。

把切换器放进共享组件，供两个子形态复用。放在项目共享 UI 的位置。

### 5. 交付

提供 URL（及 `?variant=` 键）。用户方便时翻看。有意思的反馈通常是 **“我要 B 的页头加 C 的侧栏”**，那正是实际设计。

### 6. 记录答案并清理

变体胜出后记录答案（哪个、为什么），再按 [SKILL](SKILL.md) 描述留存原型。将赢家折入真实代码，其余放到一次性分支，不留在 main：

- **子形态 A**：把赢家折入现有页面；从 main 移除落选变体和切换器。

- **子形态 B**：将赢家提升为真实路由；从 main 移除一次性路由和切换器。

全部变体是主要来源，因此进入一次性分支而非垃圾桶；留在 main 的变体组件与切换器会迅速腐坏并误导下一位读者。

## 反模式

- **只有颜色或文案不同的变体。** 那是微调，不是原型。真正的变体在结构上不同。

- **变体之间共享过多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 会破坏意义。每个变体应能丢弃布局。

- **把变体接入真实写操作。** 只读原型即可。需要写入时指向桩：问题是“它应长什么样”，不是“后端能用吗”。

- **把原型直接提升到生产。** 变体代码在原型约束下编写（无测试、最少错误处理）。折入时正确重写。
