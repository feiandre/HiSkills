# 逻辑原型

一个自包含 HTML 文件（**可分享演示**），任何人都能点击按钮驱动状态模型。适用于问题涉及**业务逻辑、状态转换或数据形状**：纸上看似合理，真实案例一跑才发现不对。

单文件无需安装，可交给非开发者（设计师、PM、领域专家）亲自体验，因此使用他们的语言而非代码语言。

## 适用形态

- “不确定这个状态机能否处理先 X 后 Y 的边界情况。”

- “这个数据模型真能表示……的情况吗？”

- “写 API 前想先感受它应长什么样。”

- 任何需要**按按钮观察状态变化**的问题。

若问题是“应该长什么样”，走错分支，使用 [UI.md](UI.md)。

## 流程

### 1. 写明问题

写代码前写清原型针对的状态模型和问题，放在演示顶部可见介绍中。逻辑原型回答错问题就是浪费，必须显式写出以便事后检查，无论用户现在观察还是稍后离开键盘查看。

### 2. 将逻辑隔离为可移植模块

把实际逻辑放进单个 `<script>` 块，写成小而纯、以后可直接移入真实代码库的模块。页面是丢弃式，模块不是。

形状取决于问题：

- **纯 reducer**：`(state, action) => state`，适合离散事件和单一状态值。

- **状态机**：显式状态和转换，适合“当前哪些动作合法”也是问题的一部分。

- **小型纯函数集**：作用于普通数据类型，适合没有隐式当前状态、只有转换。

- **类或模块**：具有清晰方法面，适合逻辑确实拥有持续的内部控制状态。

选择最适合问题的形状，而非最容易接页面的形状。保持纯粹：无 DOM、`document` 或深入内部的按钮处理器；页面单向调用模块。这样验证后的 reducer/状态机/函数集以后可独立移入真实模块。

### 3. 构建可分享 HTML

单文件纯 HTML/CSS/JS：无框架、打包器、服务器，全部内联，双击可开，经邮件传递仍可用。

面向非开发者。每个标签使用**领域语言**，按钮和状态像业务而非 reducer，用通俗话解释变化。

自上而下清晰布局：

1. **标题和一行说明**演示可探索的问题（第1步问题）。

2. **当前状态**：以可读面板显示完整相关状态（带标签字段，不倾倒原始 JSON），每次点击后重渲染；合适时指出刚变化什么。

3. **自由操作按钮**：每个动作一个，始终可用，可按任意顺序试验；每次派发动作并重渲染。

4. **引导演示**：每标签一个**场景**，简述设定与要观察之处，下方按顺序列出**按钮**。每步是真按钮，点击执行动作并前进。开始演示重置到已知初始状态，确保每次一致。

选择难以纸上推理的尴尬场景：正常路径、棘手边界、本应非法的尝试。

美观但克制：清晰字体、宽松间距、一个强调色；无动画噱头，避免与状态和按钮竞争。

### 4. 交付

发送或打开文件。接收者按自己时间体验；关键反馈是“等等，这不该发生”或“我以为 X 会不同”，这些是*想法*中的 bug，正是原型目的。需要新动作或场景就加，原型会演进。

### 5. 记录答案和原型

原型回答后记录答案，再按 [SKILL](SKILL.md) 保存原型。逻辑部分：验证过的 reducer/状态机/函数集移入真实模块；HTML 外壳随原型进入丢弃式分支作为主要来源，单文件可随时重跑。

## 反模式

- **不要加测试。**需要测试的已不是原型。

- **不要接真实数据库。**用内存状态，除非问题专问持久化。

- **不要泛化。**不写“以后支持 X 怎么办”；原型只答一个问题。

- **不要混淆逻辑与页面。**纯模块引用 DOM、`document` 或按钮处理器后便无法移出；页面应是纯模块的薄壳。

- **不要用框架、打包器或服务器。**接收者双击一个文件；React 应用或开发服务器违背“可分享”。

- **不要把 HTML 外壳发布到生产。**页面为手动点击优化，只有其后的逻辑模块值得保留。
