# 范围外知识库

仓库中的 `.out-of-scope/` 目录保存被拒绝功能请求的持久记录。它有两个用途：

1. **机构记忆**：记录功能为何被拒绝，使 issue 关闭后理由不会丢失

2. **去重**：新 issue 与先前拒绝项匹配时，技能可呈现先前决定，而不是重新争论

## 目录结构

每个**概念**一个文件，而不是每个 issue 一个文件。请求同一内容的多个 issue 归入一个文件。

## 文件格式

文件应采用轻松易读的风格，更像简短设计文档而非数据库条目。使用段落、代码样例和示例，使首次接触的人能清楚理解理由。

```markdown
# 深色模式

本项目不支持深色模式或面向用户的主题定制。

## 为何不在范围内

渲染管线假定 `ThemeConfig` 中定义的单一调色板。支持多主题将需要：

- 包裹整个组件树的主题上下文提供器
- 逐组件主题感知样式解析
- 用户主题偏好的持久化层

这是重大架构改动，不符合项目对内容创作的关注。主题是嵌入或
再分发输出的下游消费者的问题。

```ts
// 当前 ThemeConfig 接口并非为运行时切换设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## 先前请求

- #42：“Add dark mode support”（添加深色模式支持）

- #87：“Night theme for accessibility”（无障碍夜间主题）

- #134：“Dark theme option”（深色主题选项）

```

### 命名文件

对概念使用简短、描述性的短横线命名：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应足够易识别，使浏览目录的人无需打开文件就知道拒绝内容。

### 编写理由

理由应实质具体：不要写“我们不想要”，而要写为什么。好的理由引用：

- 项目范围或理念（“本项目聚焦 X；主题是下游关注点”）
- 技术约束（“支持它需要 Y，与我们的 Z 架构冲突”）
- 战略决定（“我们选择 A 而不是 B，因为……”）

理由应持久。避免引用临时情况（“我们现在太忙”）；那不是真正拒绝，只是延后。

## 何时检查 `.out-of-scope/`

分诊期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中所有文件。评估新 issue 时：

- 检查请求是否匹配现有范围外概念
- 按概念相似性匹配，而非关键词：“night theme”匹配 `dark-mode.md`
- 若匹配，向维护者展示：“这类似 `.out-of-scope/dark-mode.md`。我们此前因[理由]拒绝。你现在仍这样认为吗？”

维护者可以：

- **确认**：把新 issue 加入现有文件的“Prior requests”列表，然后关闭
- **重新考虑**：删除或更新范围外文件，issue 进入正常分诊
- **不同意**：两个 issue 有关但不同，进入正常分诊

## 何时写入 `.out-of-scope/`

只在**增强**（不是缺陷）以 `wontfix` *被拒绝*时写入。这也适用于增强 PR：被拒绝 PR 也记录在此，避免同一请求作为全新代码回归。

因**已经实现**而以 `wontfix` 关闭时，**不要**写入。那是已构建功能，不是拒绝项；记录它会让去重检查出现误判。关闭评论应指向功能所在位置。

流程：

1. 维护者决定功能请求超出范围
2. 检查匹配的 `.out-of-scope/` 文件是否已存在
3. 是：把新 issue 追加到“Prior requests”列表
4. 否：创建新文件，写概念名、决定、理由及首个先前请求
5. 在 issue 评论中解释决定并提及 `.out-of-scope/` 文件
6. 用 `wontfix` 标签关闭 issue

## 更新或移除范围外文件

若维护者改变对先前拒绝概念的看法：

- 删除 `.out-of-scope/` 文件
- 技能无需重新打开旧 issue；它们是历史记录
- 触发重新考虑的新 issue 进入正常分诊
