# 分诊

让项目问题追踪器中的问题经过一个由分诊角色构成的小型状态机。

如果本仓库将外部拉取请求视为请求入口（见问题追踪器配置），分诊也包含它们：**PR 是附带代码的问题**，使用相同角色、状态和状态机，下文用“对于 PR”标出少量差异。根据追踪器配置，把单独的 `#42` 解析为问题或 PR。

分诊期间发布到问题追踪器的每一条评论或问题，都**必须**以此声明开头：

```
> *此内容由 AI 在分诊期间生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写经得起时间考验的代理简报。

- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的运作方式。

## 角色

两个**分类**角色：

- `bug`：有东西坏了。

- `enhancement`：新功能或改进。

五个**状态**角色：

- `needs-triage`：维护者需要评估。

- `needs-info`：等待报告者补充信息。

- `ready-for-agent`：说明充分，可以交给无人值守的代理。

- `ready-for-human`：需要人类实现。

- `wontfix`：不会处理。

对于 PR，相同状态应结合所附代码理解：`ready-for-agent` 表示已附简报，代理应对差异采取下一步；`ready-for-human` 表示已可由人类合并。

每个已分诊的问题都应恰好有一个分类角色和一个状态角色。如果状态角色冲突，先指出问题并询问维护者，再做其他事。

这些是规范角色名。追踪器中的实际标签字符串可能不同。你应该已得到映射；如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态转换：无标签问题通常先进入 `needs-triage`，然后转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者可随时覆盖；发现看似异常的转换时先指出并询问，再继续。

## 调用

维护者调用 `/triage`，并用自然语言说明希望做什么。理解请求并行动。例如：

- “给我看看有哪些需要我关注。”

- “我们看一下 #42。”（问题或 PR）

- “把 #42 移到 ready-for-agent。”

- “有哪些已准备好让代理接手？”

## 展示需要关注的内容

查询问题追踪器，按最旧优先展示三组：

1. **无标签**：从未分诊。

2. **`needs-triage`**：正在评估。

3. **自上次分诊笔记后报告者有新活动的 `needs-info`**：需要重新评估。

当 PR 属于范围内时，把外部 PR 包含在这些分组中，并在每行标注 `[PR]` 或 `[issue]`。发现阶段只展示*外部* PR（追踪器配置定义哪些作者属于外部），因此协作者正在推进的 PR 不属于分诊工作。这个过滤仅用于发现；明确点名的 PR，无论作者是谁，都要分诊。

展示每组数量，并为每项给出一行摘要。让维护者选择。

## 分诊指定问题或 PR

1. **收集上下文。** 阅读完整问题或 PR（正文、评论、标签、作者、日期；PR 还要阅读差异）。解析以往分诊笔记，避免重问已解决的问题。使用项目领域术语表探索代码库，遵守相关区域的 ADR。对代码库进行两项检查：(a) **重复性**：按领域概念搜索请求行为是否已有实现（不只按请求措辞），并报告搜索过哪里。如果找到，就是已经实现的 `wontfix`（第 5 步）。(b) **以往拒绝记录**：阅读 `.out-of-scope/*.md`，指出任何与当前请求相似的记录。

2. **给出建议。** 告诉维护者建议的分类和状态及理由，同时简述与请求相关的代码库情况（包括是否已经实现）。等待指示。

3. **验证主张。** 在追问之前检查主张是否成立。对于错误，按报告者步骤复现。对于 PR，确认差异是否做到其宣称的内容：检出代码，运行相关测试或命令。报告实际情况：已确认（附代码路径）、失败，或细节不足（这是强烈的 `needs-info` 信号）。验证得到确认，会让代理简报更扎实。

4. **追问（如有必要）。** 如果请求需要细化，调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"，每轮一组问题把它打磨清楚；决策确定时，立即澄清领域术语并更新 `GLOSSARY.md` / ADR。

5. **应用结果：**

   - `ready-for-agent`：发布代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。

   - `ready-for-human`：结构与代理简报相同，但注明为什么不能委派（判断性选择、外部访问、设计决策、手动测试）。

   - `needs-info`：发布分诊笔记（见下方模板）。

   - 对于 `wontfix`，关闭问题，评论内容取决于*原因*：

     - **已经实现**：变更已存在于代码库。指出位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，不是已构建的请求）。

     - **被拒绝（错误）**：礼貌解释，然后关闭。

     - **被拒绝（增强）**：写入 `.out-of-scope/`，在评论中链接引用，再关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。

   - `needs-triage`：应用角色。如果已有部分进展，可选地发表评论。

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，信任他们并直接应用角色。确认将要做什么（角色变更、评论、关闭），然后行动。跳过追问。如果未经过追问会话就移到 `ready-for-agent`，询问他们是否想编写代理简报。

## 待补充信息模板

```markdown
## 分诊笔记

**目前已确认的内容：**

- 第 1 点
- 第 2 点

**仍需你（@reporter）提供的内容：**

- 第 1 个问题
- 第 2 个问题
```

把追问期间所有已解决内容记录在“目前已确认的内容”下，避免工作丢失。问题必须具体、可行动，而不是“请提供更多信息”。

## 恢复以往会话

如果问题或 PR 上已有分诊笔记，阅读它们，检查报告者是否回答了任何未决问题，在继续之前展示更新后的情况。不要重问已经解决的问题。
