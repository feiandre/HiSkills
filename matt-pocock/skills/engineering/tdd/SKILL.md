# 测试驱动开发

TDD 是红 → 绿循环。本技能作为参考，让该循环产出值得保留的测试：什么是好测试、测试放在哪里、反模式，以及循环规则。每节都适用于每一轮循环：循环之前和期间查阅，而非结束后才查阅。

探索代码库时，阅读 `GLOSSARY.md`（若存在），使测试名称和接口词汇符合项目的领域语言，并尊重所修改领域中的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而非实现细节。代码可以彻底改变，测试不应随之改变。好测试读起来像规格说明：“用户可使用有效购物车结账”准确告诉你存在什么能力；它不关心内部结构，因此能经受重构。

示例参见 [tests.md](tests.md)，mock 指南参见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝**是进行测试的公共边界：无需深入内部即可观察行为的接口。测试位于接缝处，绝不针对内部内容。

**只在预先商定的接缝处测试。** 编写任何测试之前，先写下要测试的接缝，并与用户确认。不在未经确认的接缝处编写测试。你无法测试一切，因此预先商定接缝，才能使测试投入落在关键路径和复杂逻辑，而非每个边缘情况上。

询问：“公共接口是什么，我们应测试哪些接缝？”为每个建议的接缝附上一行说明，讲清它能捕获什么、遗漏什么。

如果接口本身的形状还不确定（模块应多深、接缝应放哪里、接口应暴露什么），调用 Skill 工具并传入 "codebase-design"，获取词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共享来源，是供查阅的参考，而非要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或经由旁路验证（查询数据库，而不使用接口）。识别信号：重构时行为未变，测试却失败。

- **同义反复**：断言按与代码相同的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、以相同方式手工推导的快照、断言常量等于自身），因此按构造必然通过，永远无法与代码得出不同结论。预期值必须来自独立事实来源：已知正确的字面值、演算过的示例、规格说明。

- **水平切片**：先编写全部测试，再编写全部实现。成批测试验证的是**想象中的**行为：测试的是事物的**形状**，而非面向用户的行为；测试对真实变化变得不敏感，而且在理解实现前就锁定了测试结构。改用**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是一发**曳光弹**，响应上一轮所教会你的东西。

## 循环规则

- **先红后绿。** 先写失败测试，再只写足以通过它的代码。不要预判未来测试，也不要添加推测性功能。

- **一次一个切片。** 每轮一个接缝、一个测试、一个最小实现。

- **重构不属于循环的一部分。** 它属于审查阶段（参见 `code-review` 技能），不属于红 → 绿的实现循环。
