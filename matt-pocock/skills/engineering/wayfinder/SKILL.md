一个模糊的想法出现了：它大到单次代理会话装不下，而且笼罩在迷雾中，从这里通往**目的地**的路线还不可见。寻路的重点是找到这条路线，而不是直接冲向目的地。本技能先在仓库的问题跟踪器上绘制一张**共享地图**，再逐一处理其中的**决策工单**（解决结果是一项决策的问题，而不是要执行的构建工作切片），直到路线清晰。

每项工作的目的地各不相同，为它命名是绘图的第一步：它决定每张工单的形状。目的地可能是一份供交接和迭代的规格说明、开始规划前必须敲定的决定，或直接完成的一项变更，例如数据结构迁移。地图与领域无关：工程工作、课程内容，以及其他符合这种结构的工作，都适用。

## 规划，而非执行

Wayfinder 默认用于**规划**：每张工单解决一个决策；当路线清晰、实际动手之前已无事项需要决定时，地图就完成了。想要直接开始工作的冲动，通常意味着已经走到了地图的边缘，该交接了。某项工作可以在其 **Notes** 中覆盖这一默认值，把执行也纳入地图；但若没有这样的说明，应产出决策，而不是交付物。

## 按名称引用

每张地图和工单都是一个 issue，因此都有一个**名称**，即其标题。在所有供人阅读的内容中（过程叙述、地图的 Decisions-so-far），都按这个名称引用它，绝不只用裸露的 id、编号或 slug。满屏 `#42, #43, #44` 难以阅读；名称则一眼可懂。id 和 URL 并不会消失：链接包在名称中，但它们应放在名称之内，不能代替名称。

## 地图

地图是本仓库问题跟踪器上的一个 issue，标记为 `wayfinder:map`，是权威工件。地图中的工单是它的子 issue。

地图是一份**索引**，而非存储库。它列出已作出的决策，并指向保存详细内容的工单；一项决策只存在于一个位置，也就是它自己的工单中，因此地图只概括并链接，不重复陈述。

**地图、子工单、阻塞关系和前沿查询具体存放在哪里，取决于所用的跟踪器。** 应当已经向你提供了问题跟踪器。若没有，告诉用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档中的“Wayfinding operations”部分，了解本仓库如何表达这些概念。如果没有提供跟踪器，则默认使用 local-markdown 跟踪器。

### 地图正文

以低分辨率呈现整张地图，每次会话加载一次。**不**列出未关闭工单：它们是尚未关闭的子 issue，通过查询查找。

```markdown
## 目的地

<地图终点的目标状态：本次工作要找到的规范、决策或变更。一到两行；每次会话在选择工单前都先据此定位。>

## 备注

<领域；每次会话应参考的技能；本次工作的长期偏好>

## 迄今作出的决策

- [<已关闭工单标题>](链接)：<答案要点的一句话概述>

## 尚未明确

## 范围之外

```

### 工单

每张工单都是地图的一个**子 issue**；跟踪器的 issue id 是它的身份标识。正文就是要回答的问题，规模应适合一个 100K token 的代理会话：

```markdown
## 问题

<本工单要解决的决策或调查事项>
```

每张工单带有一个 `wayfinder:<type>` 标签，类型为 `research`、`prototype`、`grilling`、`task` 之一（参见[工单类型](#ticket-types)）。地图及其工单只带 `wayfinder:` 标签，绝不带 `ready-for-agent` 这样的分诊标签：它们是决策，而非实现工作。

会话在开始任何工作**之前**，必须**先**把工单分配给推动这张地图的开发者，以此**认领**工单，让并发会话跳过它。受让人本身就是认领标志：未关闭且未分配的工单，就是尚未认领的工单。

阻塞关系使用跟踪器的**原生**依赖关系：这一点至关重要，因为它能在跟踪器自己的 UI 中把前沿**可视化**呈现，让人无需打开地图就能看见哪些工单可以领取。只有缺少原生阻塞功能的跟踪器，才退回使用正文约定。阻塞某张工单的所有工单都关闭时，该工单就**解除阻塞**；**前沿**是所有未关闭、未阻塞、未认领的子工单，即已知范围的边缘。

答案不属于正文；它在解决工单时记录（参见[沿地图推进](#work-through-the-map)）。解决工单时创建的资产应从 issue 链接过去，不要粘贴进去。

## 工单类型

每张工单要么是 **HITL**（human in the loop，人类参与，与能表达自身意见的人一起处理），要么是 **AFK**，由代理独立推动。HITL 工单只有经过这种实时交流才能解决；代理绝不能代替人类那一方发言（如果负责 grilling 的代理自己回答自己的问题，就违反了这一点）。

- **Research，研究**（AFK）：阅读文档、第三方 API 或知识库之类的本地资源，找出决策所依赖的事实。由调用 Skill 工具并传入 "research" 的子代理解决。需要当前工作目录之外的知识时使用。

- **Prototype，原型**（HITL）：通过调用 Skill 工具并传入 "prototype"，制作一个成本低、粗略而具体、可供反馈的工件（提纲、粗稿、桩实现或 UI/逻辑代码），提高讨论的具体程度。将原型作为资产链接。关键问题是“应该长什么样”或“应该怎样运行”时使用。

- **Grilling，追问**（HITL）：对话。这是默认情况。始终调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"。

- **Task，任务**（HITL 或 AFK）：作出一项**决策**之前必须完成的手动工作：没有需要决定、制作原型或研究的内容，但在它完成之前讨论无法推进。例如注册一个服务以便评判它的 API、开通访问权限、搬移数据以便观察其结构。这是唯一一种重在**执行**而非决策的类型；它之所以进入地图，是因为能解除一项决策的阻塞，而不是因为能交付目的地。代理能独立推动时就自行执行（AFK）；否则给人一份精确的检查清单（HITL）。工作完成即解决；答案记录已完成的事项及后续工单依赖的事实，如凭据位置、新 URL、行数。

## 战争迷雾

地图**刻意**保持不完整：不要绘制尚未看清的东西。现有工单之外是**战争迷雾**：你隐约知道将来会出现某些决策和调查，却尚不能确定它们，因为它们依赖仍未回答的问题。解决一张工单，就会清除它前方的迷雾，把现在可以明确描述的事项逐一转成新工单，直到通往目的地的路线清晰，且不再剩下工单。

地图的 **Not yet specified** 部分记录这种模糊的视野：怀疑将要面对的问题，以及稍后需要重新查看的领域。这是**通往**目的地、尚未发现的前沿：这里的一切都在范围之内，只是尚不足以明确到可以建立工单。视野允许多粗略或多完整，就写到什么程度；它也为阅读本次工作走向的协作者充当路标。

**是迷雾，还是工单？** 判断标准是现在能否精确陈述问题，**不是**现在能否回答它。

- **应建立工单的情况**：问题已经明确，即使它被阻塞、尚无法着手。

- **应归入尚未明确的情况**：还不能把问题表达得那么精确。不要预先把迷雾切成工单大小的块：迷雾比工单更粗；当前沿到达时，一片迷雾可能转成多张工单，也可能一张都没有。

**Not yet specified** 不包含已决定的事项（Decisions so far）、已经有活跃工单的事项，以及范围之外的事项（下一节）。

## 范围之外

迷雾只会聚集在**通往**目的地的方向。目的地确定范围，因此超出目的地的工作属于**范围之外**：它不是迷雾，也不属于 **Not yet specified**。它在地图中有自己的 **Out of scope** 部分：记录你有意识地从**本次**工作中排除的事项。它出现在这里，是因为范围，而不是因为不够明确。

范围外的工作永远不会转成工单（前沿在目的地停止），因此只有重画目的地时它才会重新出现，而且应作为新的一次工作，而非恢复原来的工作。

把某事排除在范围之外，是一次范围界定行为，并非路线中的一步。如果已有工单被发现位于目的地之外（绘图时误纳入范围，或解决其他问题后才暴露出来），就**关闭它**（已关闭工单显然不在前沿上），并在 **Out of scope** 部分留一行：概括其内容、说明为何超出范围，并链接已关闭工单。不要将其放入 **Decisions so far**，因为后者记录实际走过的路线；范围边界不属于路线中的一步。

## 调用

两种模式。无论哪一种，**每次会话绝不解决超过一张工单**，研究工单除外。

### 绘制地图

用户带着一个模糊想法调用。

1. **命名目的地。** 调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"，明确这张地图要通往什么：规格说明、决策或变更。目的地决定范围，所以先确定它。

2. **绘制前沿。** 再进行追问，这次采用**广度优先**：展开整个空间，而非深入某一条线索，找出未决事项及现在可采取的第一步。**如果没有发现任何迷雾**（通往目的地的路线已清晰，整个过程小到一次会话足以容纳），就不需要地图。停止，并询问用户希望如何继续。

3. **创建地图**（标签 `wayfinder:map`）：填写 Destination 和 Notes，Decisions-so-far 留空，把迷雾勾勒到 **Not yet specified**。

4. **为现在能够明确描述的事项创建工单**，作为地图的子 issue，然后在**第二轮**连接阻塞边（issue 必须先拥有 id，才能相互引用）。也在这一轮用真实 id 写交叉引用：`#<n>` 这样的占位符会自动链接到不相关的 issue。连接后，工单被分为前沿和被阻塞的部分；尚不能明确描述的内容仍留在迷雾，也就是 **Not yet specified** 部分。

5. **启动研究子代理。** 对刚创建的每张 `research` 工单，启动一个拥有全新上下文窗口的子代理，由它调用 Skill 工具并传入 "research"，并行解决问题；在一次性的 `research/<name>` 分支上记录发现，并从工单提供上下文指针。推送分支，但不要开 PR：它永远不会被合并。

6. 停止：绘图本身就是一次会话的工作；它不手动解决任何工单。

### 沿地图推进

用户带着地图（URL 或编号）调用。指定工单是**可选的**：没有指定时，由你选择下一项决策，而不是用户。

1. 加载**地图**：低分辨率视图，而非每张工单的正文。

2. 选择工单。如果用户点名了一张，就用那张。否则按顺序取第一张前沿工单。**认领它**：任何工作开始前，先分配给自己。

3. 按 `wayfinder:<type>` 标签指定的类型解决它（参见[工单类型](#ticket-types)）。读取标签，而不只看正文：正文从不声明类型。**按需深入**：需要时获取相关或已关闭工单的完整正文；为 `## Notes` 块列出的所有技能调用 Skill 工具。如果拿不准，就调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"。

4. 记录解决结果：把答案发布为**解决结果评论**，**关闭** issue，并向地图的 Decisions-so-far **追加上下文指针**。

5. 添加新浮现的工单（先创建，再连接）；把答案使之可以明确描述的迷雾转为工单，并从 **Not yet specified** 清除每片已转化的迷雾，使它只以新工单的形式存在。如果答案表明某张工单（当前这张或其他工单）超出目的地，就**将它排除在范围之外**，而不是当作路线中的一步来解决。如果该决策使地图其他部分失效，更新或删除那些工单。

用户可能并行处理已解除阻塞的工单，因此应预期其他会话也会并发编辑跟踪器。
