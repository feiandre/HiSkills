从 `HEAD` 与用户提供的固定点之间的差异进行双轴审查：

- **标准**：代码是否符合本仓库文档化的编码标准？

- **规范**：代码是否忠实实现原始 issue/规范？

两个轴都作为**并行子代理**运行，避免互相污染上下文，然后由本技能汇总发现。每个子代理都从全新上下文窗口开始。

应当已向你提供 issue 跟踪器。若未提供，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比较点

用户所说的任何固定点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。若用户未指定，询问。

记录一次差异命令：`git diff <fixed-point>...HEAD`（三点，与合并基线比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续前确认固定点可解析（`git rev-parse <fixed-point>`）且差异非空。坏引用或空差异应在此处失败，而不是在两个并行子代理内部失败。

### 2. 识别规范来源

按此顺序查找原始规范：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过跟踪器文档中的工作流获取。

2. 用户作为参数传入的路径。

3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规范文件。

4. 若都找不到，询问用户规范在哪里。若用户说没有，**规范**子代理将跳过并报告“无可用规范”。

### 3. 识别标准来源

搜索仓库中每个记录代码应如何编写的文件。存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 时必须列入。

在仓库文档之上，标准轴始终带有下方 **坏味道基线**：一组固定的 Fowler 代码坏味道（_Refactoring_，第 3 章），即使仓库没有文档也适用。两条规则约束：

- **仓库优先。**有文档的仓库标准始终优先；若它认可某基线会标记的内容，则抑制该坏味道。

- **始终是判断。**每种坏味道都是有标签的启发式（“可能的 Feature Envy”），绝非硬违规。与这里任何标准一样，跳过工具已强制执行的内容。

每种坏味道读作*它是什么* → *如何修复*；与差异匹配：

- **神秘名称**：函数、变量或类型名称不能揭示其作用或保存内容。→ 重命名；若找不到诚实名称，设计含混。

- **重复代码**：相同逻辑形状在改动中出现在多个 hunk 或文件。→ 提取共享形状，从两处调用。

- **依恋情结**：方法访问另一对象数据多于自身数据。→ 将方法移到它依恋的数据上。

- **数据泥团**：同一组少数字段或参数总一起出现（想成为类型）。→ 组合成一个类型并传递。

- **基本类型偏执**：用原始值或字符串代表应拥有独立类型的领域概念。→ 给概念一个小类型。

- **重复 switch**：同一类型上的 `switch`/`if` 级联在改动中反复出现。→ 用多态或双方共享的一张映射替换。

- **霰弹式修改**：一个逻辑改动迫使差异中多个文件分散编辑。→ 把一起变化的内容集中到一个模块。

- **发散式变化**：一个文件或模块因多个无关原因被编辑。→ 拆分，使每个模块只因一个原因变化。

- **夸夸其谈通用性**：为规范没有的需求添加抽象、参数或钩子。→ 删除；内联回去，直到真实需求出现。

- **过长的消息链**：调用者不应依赖的长 `a.b().c().d()` 导航。→ 在第一个对象上用单一方法隐藏遍历。

- **中间人**：主要只转发调用的类或函数。→ 删除它，直接调用真实目标。

- **被拒绝的遗赠**：子类或实现者忽略/覆盖继承的大部分内容。→ 放弃继承，使用组合。

### 4. 并行生成两个子代理

在前台同时发起两个子代理调用，并汇总其报告。

**标准子代理提示词**应包含：

- 完整差异命令与提交列表。

- 步骤 3 找到的标准来源文件清单，**加上步骤 3 的坏味道基线全文**（子代理没有其他访问方式）。

- 任务简报：“按相关文件/hunk 报告：(a) 差异违反文档标准的每一处：引用标准（文件 + 规则）；(b) 发现的每个基线坏味道：命名并引用 hunk。区分硬违规与判断：文档标准违反可为硬违规，但基线坏味道始终是判断，文档化的仓库标准优先于基线。跳过工具强制的内容。少于 400 词。”

**规范子代理提示词**应包含：

- 差异命令与提交列表。

- 规范的路径或获取内容。

- 任务简报：“报告：(a) 规范要求但缺失或部分实现的要求；(b) 差异中未被要求的行为（范围蔓延）；(c) 看似已实现但实现错误的要求。每个发现引用规范原句。少于 400 词。”

若规范缺失，跳过规范子代理，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 与 `## Spec` 标题下展示两份报告，可逐字或稍作清理。**不要**合并或重新排序发现，因为两个轴有意分开（见_为何两个轴_）。

最后用一行摘要：每轴发现总数，以及*每轴内部*最严重问题（若有）。不要跨轴选唯一赢家：那正是分离要防止的重排。

## 为何两个轴

一项改动可通过一个轴而失败另一个轴：

- 遵循所有标准但实现错误目标 → **标准通过，规范失败。**

- 完全实现 issue 要求但破坏项目约定 → **规范通过，标准失败。**

分开报告可防止一个轴掩盖另一个。
