# 询问 Matt

你记不住所有技能，所以来询问。

在说明某项技能的作用或建议跳过某一步骤前，请阅读该技能的 SKILL.md：这里的摘要仅用于定位。

**流程**是穿越技能的一条路径。多数路径沿一条**主流程**运行，并有两条**入口**汇入。其余内容是独立技能，或运行在底层的词汇层。

## 主流程：想法 → 交付

多数工作所走的路线。你有一个想法，希望把它构建出来。

1. **`/grill-with-docs`** 通过访谈厘清想法。只要你在**工作目录**中工作，就从这里开始：它是有状态的，会把所学保留在 `GLOSSARY.md` 和 ADR 中。（没有工作目录？改用 `/grill-me`，见“独立技能”。两者运行相同的 `/grilling` 原语；`grill-with-docs` 会留下文字记录，因此只要有仓库可留存，它就是更好的选择。）

2. **分支：是否能在对话中解决每个问题？**如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看到的 UI），就绕道原型，并由 **`/handoff`** 双向衔接（原型位于自己的目录中，这正是 `/handoff` 的用途；参见阶段边界）：

   - 用 **`/handoff`** 输出，然后针对该文件打开全新会话，

   - 用 **`/prototype`** 以一次性代码回答该问题，

   - 用 **`/handoff`** 把所学带回，并在原始想法线程中引用它。

3. **分支：这是跨多个会话的构建吗？**

   - **是** → 用 **`/to-spec`**（将线程转化为规范），再用 **`/to-tickets`** 分成 tracer-bullet 工单，每个工单声明其**阻塞边**。然后以两种方式之一处理工单：

     - 每张工单运行 **`/implement`**，且在每张之间执行 **`/clear`** 清理上下文。本地跟踪器中，每张工单是 `.scratch/<feature>/issues/` 下一个文件，手工按阻塞优先顺序处理；真实跟踪器中，边会成为原生阻塞链接，因此任何阻塞项已完成的工单都可领取。每张工单自包含，所以上一张的上下文可丢弃。

     - 用 **`/implement-spec` 一次运行整个规范。它把工单读成**任务图**，跨就绪的**前沿**并行运行实现者子代理，并将全部内容落到一个**集成分支**。若你更愿意编排构建，而非自行驱动每张工单，就使用它。

   - **否** → 就地在同一上下文窗口运行 **`/implement`**。

   无论哪种方式，代码都通过驱动 **`/tdd`**（一次一个红绿切片）构建，最后以 **`/code-review`** 收尾；后者对差异进行双轴审查（标准 + 规范）。`/implement` 对每张工单运行两者；`/implement-spec` 的每位实现者各自驱动 `/tdd`，并在集成分支上运行一次 `/code-review`。只想在没有完整规范时以测试优先构建具体行为，就单独使用 **`/tdd`**；想以固定点为基准审查分支或 PR，就单独使用 **`/code-review`**。

   工作以拉取请求提交时，**`/pr`** 组织正文：展示变更的最小可视化、证明其有效的修改前后证据，以及单向门或双向门判断。它由模型调用，因此代理在编写 PR 时会自动使用它。

4. **`/retro`** 闭环。构建后，尤其是走偏的构建后，它会回顾会话并提出对代理**环境**的改动，而非代码：导航指针、自动检查、`/code-review` 执行的编码标准、指导文件、工具。机械性错误变成确定性检查；判断性问题变成编码标准。下一次构建便从更好的环境开始。

### 上下文卫生

让步骤 1–3 保持在**一个不间断的上下文窗口中**（`/to-tickets` 前不要压缩或清空），使访谈、规范和工单都建立在同一思考之上。之后每个 `/implement` 都从工单开始全新运行。在它回顾的那个会话中、清空之前运行 `/retro`；清空后，则让它查看该会话日志。

限制因素是 **[智能区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口（最先进模型约 150k token）。若会话在 `/to-tickets` 前接近该限制，不要继续在退化状态下硬撑；在最近的阶段边界执行 `/compact` 后继续（参见阶段边界）。

## 入口

会产生工作、随后汇入主流程的起始情境。

- **缺陷和请求堆积** → **`/triage`**。它让 issue 经过分诊角色并产出可供代理执行的 issue，之后由 **`/implement`** 接手。

  分诊只处理**你没有创建**的 issue：缺陷报告、传入的功能请求、任何原始到达的内容。`/to-tickets` 产出的工单已可由代理执行，因此**不要分诊它们**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于困难问题：一眼无法解决的缺陷、间歇性短暂故障、在两个已知良好状态之间潜入的回归。它在获得**紧密反馈循环**（一个已经能针对*此*缺陷变红的命令）前拒绝凭空推测，然后用回归测试修复。修复完成后，在同一会话运行 **`/retro`**，询问本可如何预防；若真正发现是没有良好接缝可锁定问题，则应由 **`/improve-codebase-architecture`** 处理。

- **庞大而模糊的工作：全新项目或大型功能构建，超出单会话范围** → **`/wayfinder`**，这里认知负担最重的流程。当前往目的地的道路尚不可见时，它在 issue 跟踪器上绘制 **decision ticket** 的**共享地图**，逐个解决，产出**决策而非交付物**，直到迷雾退去、道路清晰。**`/grill-with-docs`** 用于细化你能在一个会话中把握的想法；wayfinder 用于无法把握的想法，它更慢、更密集，应只为这种情形保留，绝不用于范围明确的功能。

  地图清晰后，**它进行交接，而非构建**：在 **`/to-spec`** 处汇入主流程，将地图中链接的决策汇聚为可构建计划，再照常执行 `/to-tickets` 和 `/implement`。将地图直接循环进 `/implement` 会跳过这一汇聚，丢弃链接细节；只有工作事实证明确实很小，才直接进入 `/implement`。

## 代码库健康

这不是功能工作，而是日常维护。

- 只要有空余时间，就运行 **`/improve-codebase-architecture`**，保持代码库适合代理运作。它呈现**加深机会**；选定一个会*产生想法*，可带到主流程的 `/grill-with-docs`。它是寻找候选的调查；**`/codebase-design`**（见下文）是设计所选候选的工作台。

## 底层词汇

两个由模型调用的参考在*其他技能之下*运行，各自是其词汇的单一事实来源。当问题在于**词语**而非流程时，直接使用它们；或让上述技能将其引入。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑模糊术语、消解一词多义（“account”同时承担三种职责）、将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动的主动纪律，用于让 `GLOSSARY.md` 成为干净的术语表。

- **`/codebase-design`** 是用于设计模块*形状*的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：在干净接缝后将大量行为置于小接口之后。`/tdd` 和 `/improve-codebase-architecture` 都会使用它。

## 阶段边界

**阶段**是会话中的一块工作：访谈、实现、QA。两个阶段的**边界**处有五个选项，在其中选择是整张地图上最模糊的决策：

- **继续**：保持原位。无成本，也无损失。

- **`/clear`**：清空窗口，适用于此处的一切对未来都无关紧要时。

- **`/handoff`** 写一个可移植的 Markdown 文件。范围很窄：仅用于**新宿主**、**新目录**、**同事**，或在**阶段中途**分叉侧任务。它提供的是可移植性。

- **子代理**：将范围严格限定的任务送到自己的窗口，并取回报告。

- **`/compact`** 压缩当前上下文，并用它为全新会话提供种子。这是**默认选项**，位于决策树底部，而非首选项。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树：五个问题、每个分支背后的推理，以及为何一手来源成本使它应首先排除**继续**。**在**边界处作决定；阶段中途则继续，或将剩余工作拆给子代理。

## 独立技能

完全脱离主流程。

- **`/grill-me`**：与 `/grill-with-docs` 同样不懈的访谈，但**无状态**：不在本地保存任何内容，也不建立 `GLOSSARY.md`。在**不在工作目录中**工作时使用（打磨计划、设计、一篇文章，或任何没有下方仓库的内容）。若你在工作目录中，改用 `/grill-with-docs`：它运行相同访谈并留下文字记录，因此严格来说更好。

- **`/grilling`** 是访谈原语本身：轮次、前沿、事实由代理负责，决策由你负责。`/grill-me` 与 `/grill-with-docs` 是两个具名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有想要不带包装的访谈时，才直接使用它。

- **`/prototype`** 是一个小型一次性程序，用于回答一个设计问题：这个状态模型感觉对吗，或这个 UI 应该是什么样子。一次性是对代码编写方式的约束，并非销毁承诺：答案会并入真实代码，而原型会保留为**一手来源**，放在从 main 分出的 `prototype/<name>` 分支上，并由实现 issue 指向。它是主流程步骤 2 的绕道；只要设计问题难以纸面解决，也可随时使用。

- **`/research`**：将阅读苦工委派给**后台代理**：它对照**一手来源**调查问题，然后在仓库中留下带引用的 Markdown 文件。它阅读时你可继续工作。所产生的文件可在 `/grill-with-docs` 中带*入*主流程，因为研究为思考提供输入，而非替代思考。

- **`/to-questionnaire`** 用于阻塞你的信息既不在你脑中、也不在代码库中，而在**别人那里**时；它会写一份问卷供对方填写。这与 `/grill-me` 相反：它不访谈你关于主题的内容，而访谈你关于**发送**的内容（发给谁、你需要什么回信），并把问题对准信息缺口。返回内容可作为 `/grill-with-docs` 或 `/to-spec` 的素材。

- **`/wizard`** 用于只有**人类**能完成的步骤：配置基础设施、设置凭据或 CI secret、点击陌生第三方仪表盘、执行一次性迁移或切换。它生成交互式 bash 脚本，依次打开每个 URL、捕获每个值，并写入 `.env` 和 GitHub secret，使该过程不再每次都需要向代理重新解释。它由模型调用，代理遇到只有你能越过的障碍时会自动使用。若代理能自行完成，它就应该自行做；此技能用于人类确实参与流程的情形。

- **`/wait-what`** 是消息未被理解时的纠正方法。可在对话中途、任何其他技能内部使用，代理会用你缺少的上下文、平实英语及 `GLOSSARY.md` 词汇重新解释刚说的话。它在事后生效；`/grill-with-docs` 是事前治疗，因为尽早商定共同语言能阻止术语堆砌发生。

- **`/teach`**：跨多个会话学习概念，以当前目录作为有状态工作区。

- **`/writing-for-agents`** 是编写代理所消费文档的参考：技能、AGENTS.md、被指向的文档。
