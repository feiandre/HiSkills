# ADR 格式

ADR 位于 `docs/adr/`，使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

延迟创建 `docs/adr/` 目录：仅在需要第一份 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{1—3 句话：背景是什么、作出了什么决定、为什么。}
```

仅此而已。ADR 可以只有一段。价值在于记录*作出了*决策以及*为什么*，而非填满各章节。

## 可选章节

只有确实增加价值时才包含这些内容。大多数 ADR 不需要。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：重新审视决策时有用

- **考虑过的选项**：仅当被否决的替代方案值得记住时

- **后果**：仅当需要指出不明显的下游影响时

## 编号

扫描 `docs/adr/` 中现有最高编号，然后加一。

## 何时提出编写 ADR

以下三项必须同时成立：

1. **难以逆转**：以后改变主意的成本不可忽略

2. **缺乏背景会令人意外**：未来读者看着代码会问“他们究竟为什么这样做？”

3. **真实取舍的结果**：确有可选方案，而且出于具体理由选择了其中一个

决策容易逆转就跳过：直接逆转即可。不令人意外，就没人会问原因。没有真实替代方案，就没有比“做了显而易见的事”更多的内容值得记录。

### 符合条件的内容

- **架构形态。** “我们采用单体仓库。”“写模型采用事件溯源，读模型投影到 Postgres。”

- **上下文间的集成模式。** “订购和计费用领域事件通信，而非同步 HTTP。”

- **带来锁定效应的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库，只包括替换起来需要一个季度的那些。

- **边界和范围决定。** “客户数据由客户上下文拥有，其他上下文只通过 ID 引用。”明确拒绝的事项与接受的事项同样有价值。

- **刻意偏离显然路径。** “因为 X，我们使用手写 SQL 而不是 ORM。”任何合理读者会以为应反着做的事。这些记录防止下一位工程师“修复”刻意作出的选择。

- **代码中不可见的约束。** “由于合规要求不能使用 AWS。”“由于合作方 API 合同，响应时间必须低于 200ms。”

- **否决理由不明显的替代方案。** 如果考虑了 GraphQL，却因微妙原因选了 REST，应记录；否则六个月后又会有人提议 GraphQL。
