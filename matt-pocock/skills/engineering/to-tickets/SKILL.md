# 转换为工单

将计划、规格或对话拆分为一组**工单**：曳光弹式纵向切片，每张都声明哪些工单**阻塞**它。

你应该已经得到问题追踪器和分诊标签词汇。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

使用对话上下文已有的内容。如果用户通过参数传入引用（规格路径、问题编号或 URL），获取它并阅读完整正文与评论。

### 2. 探索代码库（可选）

如果尚未探索代码库，就去探索，了解代码当前状态。工单标题和描述应使用项目领域术语表的词汇，并尊重所涉区域的 ADR。

寻找可以先行重构代码、使实现更容易的机会。“先让变更容易，再做这个容易的变更。”

### 3. 起草纵向切片

把工作拆为**曳光弹式**工单。

- 每个切片穿过所有层（schema、API、UI、测试），形成狭窄但**完整**的路径：是纵向切片，**不是**某一层的横向切片。

- 完成的切片可以独立演示或验证。

- 每个切片的大小应能放进一个全新的上下文窗口。

- 任何先行重构都应最先完成。

为每张工单给出**阻塞依赖边**：它开始前必须先完成的其他工单。没有阻塞项的工单可以立即开始。

**大范围重构是纵向切片的例外。****大范围重构**是某个机械变更（重命名列、改变共享符号的类型），其**影响范围**扩散到整个代码库，使单次编辑同时破坏成千上万处调用，任何纵向切片都无法独立以绿色状态落地。不要强行把它塞进曳光弹切片；应按**扩展—收缩**排序。先扩展：在旧形式旁增加新形式，不破坏现有内容。再按影响范围分批迁移调用处（按包、按目录），每批各为一张受扩展工单阻塞的工单；由于旧形式仍存在，各批之间 CI 保持绿色。最后收缩：没有调用方后，在一张受所有迁移批次阻塞的工单中删除旧形式。如果连各批都不能单独保持绿色，则保留顺序，但让它们共享一条集成分支，并共同阻塞最后的“集成并验证”工单；只承诺在那里实现绿色状态。

### 4. 向用户确认

以编号列表呈现建议的拆分。每张工单展示：

- **标题**：简短描述性名称。

- **阻塞项**：哪些其他工单（若有）必须先完成。

- **交付内容**：这张工单将使什么端到端行为正常工作。

询问用户：

- 粒度是否合适？（过粗 / 过细）

- 阻塞依赖边是否正确：每张工单是否只依赖真正限制它启动的工单？

- 是否有工单应该合并或继续拆分？

持续迭代，直到用户批准拆分。

### 5. 将工单发布到已配置的追踪器

发布获批工单。**如何发布**取决于 `/setup-matt-pocock-skills` 配置的追踪器；两种情况下工单相同，只有阻塞依赖边的表示形式不同：

- **本地文件** → 每张工单一个文件，写到 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，按依赖顺序（阻塞项优先）从 `01` 编号。每个文件的 “Blocked by” 列出其依赖的编号 / 标题。使用下面的单工单文件模板：一张工单一个文件，绝不要合并为单一文件。

- **真正的问题追踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞项优先）为每张工单发布一个问题，使其阻塞依赖边可引用真实标识符。平台有原生阻塞关系时使用它；否则把每张工单的 “Blocked by” 设为相应阻塞问题。如果来源是已有问题，把每张工单建为其子问题（使用追踪器文档的操作）。除非另有指示，应用 `ready-for-agent` 分诊标签；这些工单从构造上就能让代理直接领取。

处理**前沿任务集合**：即所有阻塞项均已完成的工单。对于纯线性链，这意味着从上到下。

不要关闭或修改任何父问题。

## 阻塞项
