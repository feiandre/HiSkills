用户要求进行一次**回顾**。你将针对编码代理的**环境**提出改进建议，以改善后续运行。

## 步骤

1. 调用 Skill 工具，传入 `writing-for-agents`，获取写作风格指南。

2. 阅读用户指定会话的第一手资料。这可能意味着搜索本机的会话日志。若用户没有指定会话，默认为当前会话。

3. 在以下类别中寻找可改进的候选事项。

- **导航**：代理找到正确文件有多容易？文件之间有没有隐藏依赖？**导航指针**能否让它更容易？**使用时机**：会话花了很长时间寻找某项信息。

- **自动检查**：是否有自动检查能发现代理犯的错误？Lint、类型检查、测试、文件系统 lint？先阅读仓库自己的检查命令（`package.json`/构建工具的 `lint`/`check` 脚本、CI 工作流），这样发现的应是某项已有检查未接入或悄然失效，而不是重新发明一遍。仓库没有**护栏**（既没有 pre-commit hook，也没有运行 lint/typecheck/test 命令的 CI 作业）本身就是一项发现：没有 lint 的仓库是一项长期错失的机会，而非中性的默认状态。**使用时机**：代理犯了自动检查本可捕获的错误，或仓库完全没有护栏。

- **编码规范**：是否应让**审查代理**强制一条新规则？是否应删除或澄清某条现有规则？先对违规分类：**机械性**违规（固定语法模式、禁用 API、导入形式、文件位置规则）就必须用确定性检查处理，仅此而已：仓库自身 linter 的自定义规则、新 pre-commit hook，或新 CI 作业，具体选仓库语言和已有护栏使成本最低的方式。默认构建检查，而不是撰写规则。把 `CODING_STANDARDS.md` 留给真正的**判断性问题**（跨文件一致性、“符合周围风格”，以及任何护栏都无法替代的事项）。**使用时机**：审查代理没有发现某个错误。

- **全局 AGENTS.md**：是否有引导指令更应该移入编码规范（或自动检查）？**使用时机**：仓库或用户全局范围的 AGENTS.md 特别大。

- **工具经济性**：代理是否进行了可精简的昂贵工具调用？是否有特别浪费 token 的自定义工具（CLI、MCP）？**使用时机**：代理执行了昂贵的工具调用。

- **无效指令**：寻找引导文件中不会改变代理行为的指令。**使用时机**：引导文件庞大、难以驾驭。

- **信息访问**：寻找增加代理信息访问能力的机会。例如分流保存开发服务器日志、对第三方服务的只读访问。**使用时机**：代理无法获得某项关键信息。

4. 按严重程度排序，向用户展示这些候选事项。

## 参考

### 实现与审查

记住，所有工作都经历两个阶段：实现和审查。实现代理承受最大的**上下文压力**，负责探索、编写代码和调试失败。

审查代理的上下文压力最小：它收到 diff，因此无需探索。它通常也不需要写代码或调试。

这意味着，应由审查代理负责施行编码规范，而不是实现代理。

### 文件

你可以访问仓库中的多种文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推入任何在本仓库工作的代理的上下文窗口。应极其节制地使用，通常只放指向其他文件的**导航指针**。

- `CODING_STANDARDS.md`：审查期间读取，而非实现期间读取。如果规范文件超过 1,000 行，添加指向文档文件夹的**导航指针**。

- 文档：把文档用作由其他文件指向的参考文件。编写新文档前先查找已有文档。

- 技能：技能可用于承载文档（其 description 会进入代理上下文窗口），或提供用户调用的命令。遵循 `writing-for-agents` 技能中的建议。
