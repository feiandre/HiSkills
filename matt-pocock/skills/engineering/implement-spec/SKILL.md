已经向你提供一份规格说明。它应有关联工单，描述如何实现该规格说明。

应当已经向你提供问题跟踪器。若没有，告诉用户运行 `/setup-matt-pocock-skills`。

目标是在一个**集成分支**上实现整份规格说明，并按照问题跟踪器关闭工作的方式解决每张工单。

工单不是步骤列表，而是具有相互阻塞关系的**任务图**。这意味着始终存在一组可以领取的工单**前沿**。

每个子代理都从全新上下文窗口开始。

与子代理之间的双向通信应尽量少。主要通过**上下文指针**通信：指向规格说明、工单、研究笔记和此前提交。不要重复已经可以通过指针取得的信息。

尽可能在后台运行**实现子代理**，以获得最大并发度。

## 步骤

1. 阅读规格说明和工单，理解任务图。

2. （可选）使用**探索子代理**进行工单需要的任何探索——相关代码库文件或外部文档。确保探索子代理能够保存文件：它应将 Markdown 笔记存入仓库外、所有后续子代理均可访问的目录。这样**实现子代理**可以专注实现，而非探索。

3. 创建集成分支。如果问题跟踪器通过 PR 关闭工作，或用户要求 PR，就在步骤 5 首次合并后打开草稿 PR（相对 main 没有领先提交的分支无法打开 PR），标明它将关闭规格说明及工单。

4. 为每张工单使用一个全新的**实现子代理**，各自在独立分支的独立 worktree 中工作。每个实现子代理都要：

   - 开始前确认其 worktree 基于集成分支；若不是，则重置到集成分支；

   - 调用 Skill 工具并传入 `tdd`，实现该工单；

   - 报告完成之前，把集成分支的最新提交合并到自己的分支。

5. **实现子代理**完成后，使用一个**合并子代理**，把其工作合并进集成分支。

6. 如果这改变了可用工单的**前沿**，启动更多**实现子代理**处理新工单，以获得最大并发度。

7. 所有工单完成后，在集成分支上调用 Skill 工具并传入 `code-review`。使用单个全新的**实现子代理**修复代码审查提出的全部问题。

8. 如果有草稿 PR，将它标记为可供审查。否则，按问题跟踪器关闭工作的方式逐一解决工单，并报告集成分支。

9. 清理所有**实现子代理**的 worktree。
