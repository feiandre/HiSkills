# 诊断缺陷

处理困难缺陷的一套纪律。只有在明确说明理由时才跳过阶段。

探索代码库时，阅读 `GLOSSARY.md`（如存在），建立相关模块的清晰心智模型，并检查正在触碰区域的 ADR。

## 脱敏

本技能要求你展示命令、输出和捕获产物。**先对所有机密脱敏**：在原处写 `<REDACTED>`。围绕环境变量构建循环，让凭据留在环境中，而非出现在展示内容里。捕获产物可能包含认证头：只引用带有信号的行。

若脱敏后的输出不足以诊断缺陷，请说明并询问用户。

## 阶段 1：构建反馈循环

**这本身就是技能核心。** 其余都是机械操作。如果有一个针对缺陷的**紧密**通过／失败信号（会在这个缺陷上变红），你就能找到原因；二分、假设检验和插桩都只是消费该信号。没有信号，盯多少代码都救不了你。

在这里投入不成比例的努力。**积极尝试，发挥创造力，不放弃。**

### 构建方式，大致按以下顺序

1. 在能够触及缺陷的任意接缝处编写**失败测试**：单元、集成、端到端。

2. 针对运行中的开发服务器编写 **Curl / HTTP 脚本**。

3. 使用夹具输入执行 **CLI 调用**，将 stdout 与已知良好快照做差异比较。

4. 编写驱动 UI 并对 DOM／控制台／网络断言的**无头浏览器脚本**（Playwright / Puppeteer）。

5. **重放捕获的跟踪。** 把真实网络请求、载荷或事件日志保存到磁盘，并隔离重放相应代码路径。

6. **一次性测试框架。** 启动系统最小子集（一个服务、模拟依赖），通过单次函数调用执行缺陷代码路径。

7. **属性／模糊循环。** 若缺陷是“有时输出错误”，运行 1000 个随机输入并寻找故障模式。

8. **二分测试框架。** 若缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”，以便用 `git bisect run` 执行。

9. **差分循环。** 用同一输入分别执行旧版本与新版本（或两种配置），并比较输出。

10. **人在回路 bash 脚本。** 最后手段。若必须由人点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，使循环仍有结构。捕获的输出反馈给你。

构建正确的反馈循环后，缺陷就已修复 90%。

### 收紧循环

把循环当作产品。有了*一个*循环后，应**收紧**它：

- 能更快吗？（缓存准备、跳过无关初始化、缩小测试范围。）

- 信号能更精确吗？（断言具体症状，而不是“没有崩溃”。）

- 能更确定吗？（固定时间、设定随机种子、隔离文件系统、冻结网络。）

30 秒且偶发失败的循环比没有循环好不了多少；2 秒且确定的循环足够紧密，是调试的超能力。

### 非确定性缺陷

目标不是干净的复现，而是**更高的复现率**。循环触发 100 次、并行化、增加压力、缩小时序窗口、注入等待。50% 率的缺陷可以调试，1% 不行，因此持续提高概率直到可调试。

### 确实无法构建循环时

停下来并明确说明。列出尝试过的方法。向用户请求：(a) 能复现该问题的环境访问权限；(b) 脱敏捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像）；或 (c) 添加临时生产插桩的许可。没有循环，**不要**继续提出假设。

### 完成标准：能变红的紧密循环

阶段 1 在循环**紧密**且**能够变红**时完成：你能说出**一条命令**（脚本路径、测试调用或 curl），并且**已经至少运行一次**（展示调用及脱敏输出），同时满足：

- [ ] **能够变红**：执行实际缺陷代码路径，并断言**用户的确切症状**，因此能在此缺陷上变红、修复后变绿。不是“运行时没有报错”；它必须能*捕获这个特定缺陷*。

- [ ] **确定性**：每次运行结论相同（偶发缺陷：按上文固定高复现率）。

- [ ] **快速**：以秒计，而非分钟。

- [ ] **智能体可运行**：可无人值守运行；只有通过 `scripts/hitl-loop.template.sh` 才允许人在回路中。

如果发现自己在命令出现前阅读代码构建理论，**停下：直接跳到假设正是本技能要防止的失败方式。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现并最小化

运行循环，观察缺陷出现时它变红。

确认：

- [ ] 循环产生用户描述的故障模式，而不是碰巧在附近的另一种失败。错误的缺陷意味着错误的修复。

- [ ] 失败在多次运行中可复现（非确定性缺陷则需以足够高的复现率支持调试）。

- [ ] 已捕获确切症状（错误消息、错误输出、缓慢耗时），让后续阶段能验证修复是否真正解决。

### 最小化

一旦变红，就把复现缩减为**仍然变红的最小场景**。对输入、调用方、配置、数据和步骤**逐个删减**，每删一项后重跑循环，只保留对失败有承载作用的部分。

为什么值得做：最小复现会缩小第 3 阶段的假设空间（剩余活动部分更少），并在第 5 阶段成为干净的回归测试。

当**每个剩余元素都有承载作用**时完成：删除任何一项都会使循环变绿。

复现**并且**最小化完成前不要继续。

## 阶段 3：提出假设

在测试任何假设前，生成 **3–5 个有排序的假设**。只生成一个会让思考锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说明它给出的预测。

> 格式：“如果 <X> 是原因，则 <changing Y> 会使缺陷消失／<changing Z> 会使缺陷加重。”

说不出预测时，这个假设只是感觉：丢弃或使其更明确。

**测试前向用户展示排序列表。** 他们常有立即重新排序的领域知识（“我们刚部署了与 #3 相关的改动”），或知道已被排除的假设。这是低成本、高收益的检查点。不要因此阻塞；用户不在线时按自己的排序继续。

## 阶段 4：插桩

每个探针都必须对应第 3 阶段的具体预测。**一次只改变一个变量。**

工具偏好：

1. 环境支持时使用**调试器／REPL 检查**。一个断点胜过十条日志。

2. 在能够区分假设的边界处添加**定向日志**。

3. 绝不要“记录所有内容再 grep”。

**为每条调试日志加独特前缀**，例如 `[DEBUG-a4f2]`。最后清理只需一次 grep。无标签日志会留下；有标签日志会消失。

**性能分支。** 对于性能回归，日志通常不是正确工具。应建立基线测量（计时框架、`performance.now()`、性能分析器、查询计划），再二分。先测量，后修复。

## 阶段 5：修复并编写回归测试

**在修复前**编写回归测试，但前提是存在**正确接缝**。

正确接缝是测试能在调用位置按实际方式执行**真实缺陷模式**的地方。若唯一可用接缝太浅（缺陷需要多个调用方却只测试单个调用方，单元测试无法复现触发缺陷的调用链），在那里写回归测试只会带来虚假信心。

**若不存在正确接缝，这本身就是发现。** 记录它。代码库架构正在妨碍锁定缺陷。为下一阶段标出这一点。

若存在正确接缝：

1. 把最小复现变成该接缝上的失败测试。

2. 观察它失败。若通过修改代码或夹具强制变红，先与原始干净副本做 `diff`，证明修改确实生效后再信任结果。

3. 应用修复。

4. 观察测试通过。

5. 对原始（未最小化）场景重新运行第 1 阶段反馈循环。

## 阶段 6：清理

宣告完成前必须满足：

- [ ] 原始复现不再出现（重跑第 1 阶段循环）

- [ ] 回归测试通过（或已记录缺少接缝）

- [ ] 所有 `[DEBUG-...]` 插桩均已移除（对该前缀执行 `grep`）

- [ ] 一次性原型已删除（或移到明确标记的调试位置）

- [ ] 提交／PR 消息写明最终正确的假设，让下一位调试者有所收获
