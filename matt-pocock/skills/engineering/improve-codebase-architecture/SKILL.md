# 改进代码库架构

揭示架构摩擦，并提出**加深模块的机会**：通过重构把浅模块变成深模块。目标是可测试性，以及便于 AI 导航理解。

本命令以项目领域模型为*依据*，并建立在共享设计词汇上：

- 调用 Skill 工具，传入 "codebase-design"，获取架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试、“接口就是测试面”、“一个适配器 = 假设接缝，两个 = 真实接缝”）。每项建议都精确使用这些术语，不要漂移到 “component”、“service”、“API” 或 “boundary”。

- `GLOSSARY.md` 中的领域语言为良好的接缝命名；`docs/adr/` 中的 ADR 记录本命令不应重新争论的决策。

## 流程

### 1. 探索

**扫描前先定范围：YAGNI。** 加深模块的回报在于让未来修改更容易，因此要更重视代码库中最近变化的部分。先决定*看哪里*，再去看：

- 如果用户指定方向（模块、子系统、痛点），就采用它，并跳过下面的推断。

- 否则，向前回顾足够长的一段提交历史（`git log --oneline`），找出代码库热点，即反复出现的文件和区域，优先关注那些路径。如果变更分散，没有明显热点，就扩大范围。

首先阅读项目领域术语表（`GLOSSARY.md`）以及所涉区域的所有 ADR。

然后启动一个具有全新上下文窗口的子代理遍历代码库。不要遵循僵硬的启发式规则；自然探索，记录你感到阻力的位置：

- 理解一个概念时，哪里需要在许多小模块之间来回跳转？

- 哪里存在**浅模块**，其接口几乎与实现同样复杂？

- 哪里只是为了可测试性而抽出纯函数，但真正的错误藏在其调用方式中（缺少 **locality**）？

- 哪里紧密耦合的模块会跨越接缝泄漏内部细节？

- 代码库哪些部分尚未测试，或难以通过现有接口测试？

对任何疑似浅模块应用**删除测试**：删除它会集中复杂性，还是只会搬移复杂性？“会集中”才是你要找的信号。

### 2. 用 HTML 报告呈现候选项

把自包含的 HTML 文件写到操作系统临时目录，避免内容落入仓库。通过 `$TMPDIR` 解析临时目录，不存在则回退到 `/tmp`（Windows 为 `%TEMP%`）；写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行产生新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告知绝对路径。

报告通过 CDN 使用 **Tailwind** 完成布局与样式；当图、流程或时序能可靠传达结构时，通过 CDN 使用 **Mermaid** 画图。混合使用 Mermaid 与手工 CSS / SVG 可视化：关系呈图状时（调用图、依赖、时序）使用 Mermaid；需要更具编辑设计感的表达时（体量图、剖面图、折叠动画），使用手工 div / SVG。每个候选项都应有**前后可视化对比**。注重视觉表达。

为每个候选项渲染一张卡片，包括：

- **文件**：涉及哪些文件 / 模块。

- **问题**：当前架构为什么造成摩擦。

- **方案**：用通俗英语描述会有什么变化。

- **收益**：从 locality 和 leverage 的角度解释，并说明测试如何改善。

- **之前 / 之后图示**：并排、定制绘制，说明原来的浅薄程度和加深后的形态。

- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三者之一，渲染为徽章，分别表示强烈推荐、值得探索、推测性建议。

报告最后设置**首选建议**章节，说明优先处理哪一项及理由。

**领域内容使用 GLOSSARY.md 词汇，架构内容使用 `/codebase-design` 词汇。** 如果 `GLOSSARY.md` 定义了 “Order”，就说“Order 接收模块”，而不是 “FooBarHandler”，也不是“Order 服务”。

**ADR 冲突**：如果候选项与已有 ADR 矛盾，只有摩擦确实严重到值得重审 ADR 时才展示它。在卡片中明确标注（例如警告提示：“与 ADR-0007 矛盾，但值得重新讨论，因为……”）。不要罗列 ADR 禁止的每一种理论重构。

完整 HTML 脚手架、图示模式和样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提出接口。写好文件后询问用户：“你想探索其中哪一项？”

### 3. 追问循环

用户选中候选项后，调用 Skill 工具，传入 "grilling"，与用户遍历决策树：约束、依赖、加深后的模块形态、接缝后承载什么，以及哪些测试会保留下来。

决策逐渐明确时，随即执行相应更新；调用 Skill 工具，传入 "domain-modeling"，在推进过程中保持领域模型最新：

- **加深后的模块以 `GLOSSARY.md` 中没有的概念命名？** 将术语加入 `GLOSSARY.md`。文件不存在时按需创建。

- **对话中澄清了模糊术语？** 当场更新 `GLOSSARY.md`。

- **用户因关键理由拒绝候选项？** 提议创建 ADR，措辞为：“要我把它记录为 ADR，以免未来架构审查再次建议它吗？” 只有未来探索者确实需要这个理由才能避免重提相同方案时才提议；跳过临时理由（“现在不值得做”）和不言自明的理由。

- **想为加深后的模块探索不同接口？** 调用 Skill 工具，传入 "codebase-design"，使用其中“设计两次”的并行子代理模式。
