# 代码库设计

设计**深模块**：在小接口背后承载大量行为，放在清晰接缝处，并可通过该接口测试。在设计或重构代码的任何地方使用这些语言和原则。目标是给调用者杠杆效应，给维护者局部性，给所有人可测试性。

## 术语表

严格使用这些术语：不要替换成“component”“service”“API”或“boundary”。语言一致正是重点。

**Module（模块）**：任何具有接口和实现的东西。刻意不限定规模：函数、类、包或跨层切片。*避免*：unit、component、service。

**Interface（接口）**：调用者正确使用模块必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。*避免*：API、signature（范围过窄，仅指类型层面的表面）。

**Implementation（实现）**：模块内部内容，即代码主体。与 **Adapter** 不同：一个东西可以是实现很大的小适配器（Postgres 仓库），也可以是实现很小的大适配器（内存假实现）。话题是接缝时使用“adapter”，否则用“implementation”。

**Depth（深度）**：接口处的杠杆效应。调用者（或测试）每学习一个单位的接口，能执行多少行为。大量行为位于小接口后时，模块是**深的**；接口几乎与实现同样复杂时，是**浅的**。

**Seam（接缝）** *（Michael Feathers）*：无需编辑该处代码就能改变行为的位置；模块接口所在的*位置*。接缝放在哪里是独立设计决定，不同于其背后放什么。*避免*：boundary（与 DDD 的 bounded context 含义重叠）。

**Adapter（适配器）**：在接缝处满足接口的具体事物。描述的是*角色*（填哪个槽位），而非内部实质。

**Leverage（杠杆效应）**：调用者从深度获得的收益。每学习一个单位接口，获得更多能力。一个实现可在 N 个调用点和 M 个测试中回报。

**Locality（局部性）**：维护者从深度获得的收益。变更、缺陷、知识和验证集中在一处，不扩散到调用者。修复一次，处处修复。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│      小接口         │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│    深厚实现         │  ← 复杂逻辑隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│          大接口                 │  ← 方法多、参数复杂
├─────────────────────────────────┤
│      单薄实现                   │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时问：

- 能减少方法数量吗？

- 能简化参数吗？

- 能把更多复杂性隐藏在内部吗？

## 原则

- **深度是接口属性，不是实现属性。** 深模块内部可由小型、可 mock、可替换部分组合；它们只是不属于接口。模块可在实现内部拥有**内部接缝**（仅供自身测试使用），并在接口处拥有**外部接缝**。

- **删除测试。** 想象删除模块。复杂性消失，说明它只是透传；复杂性重新出现在 N 个调用者中，说明它此前在发挥价值。

- **接口就是测试表面。** 调用者和测试跨越同一接缝。若你想越过接口去测试更深，模块形状可能错了。

- **一个适配器意味着假设性接缝，两个适配器意味着真实接缝。** 除非确实有事物跨它变化，否则不要引入接缝。

## 为可测试性设计

良好接口让测试自然发生：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // 易于测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 易于测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- **Module** 恰好有一个 **Interface**（向调用者和测试呈现的表面）。

- **Depth** 是 **Module** 的属性，以其 **Interface** 为参照衡量。

- **Seam** 是 **Module** 的 **Interface** 所在位置。

- **Adapter** 位于 **Seam**，并满足 **Interface**。

- **Depth** 为调用者产生 **Leverage**，为维护者产生 **Locality**。

## 不采用的理解框架

- **深度为实现行数与接口行数之比**（Ousterhout）：会奖励给实现注水。这里采用深度即杠杆效应。

- **“Interface”指 TypeScript `interface` 关键字或类的 public 方法**：太狭窄；此处接口包含调用者必须知道的所有事实。

- **“Boundary”**：与 DDD 的 bounded context 重叠。使用 **seam** 或 **interface**。
