# 来自用户反馈的技能改进

**日期：** 2025-11-28
**状态：** 草稿
**来源：** 两个在真实开发场景中使用 superpowers 的 Claude 实例

## 执行摘要

两个 Claude 实例提供了真实开发会话中的详细反馈。反馈揭示当前技能中的**系统性缺口**：即使遵循技能，仍让本可避免的缺陷发布。

**关键洞见：** 这些是问题报告，不只是解决方案提案。问题真实存在；方案需要仔细评估。

**关键主题：**

1. **验证缺口**——验证操作成功，却没验证达到预期结果

2. **流程卫生**——后台进程跨子代理累积并互相干扰

3. **上下文优化**——子代理收到过多无关信息

4. **缺少自省**——交接前没有批评自身工作的提示

5. **mock 安全**——mock 可能偏离接口却未被发现

6. **技能激活**——技能存在却未被读取／使用

## 已识别问题

### 问题 1：配置变更验证缺口

**发生了什么：**

- 子代理测试“OpenAI 集成”

- 设置 `OPENAI_API_KEY` 环境变量

- 得到 200 状态响应

- 报告“OpenAI 集成正常”

- **但是**响应含 `"model": "claude-sonnet-4-20250514"`，实际仍使用 Anthropic

**根因：**
`verification-before-completion` 检查操作成功，却没检查结果是否反映目标配置变更。

**影响：** 高——对集成测试产生虚假信心，缺陷进入生产。

**示例失败模式：**

- 切换 LLM 提供商 → 验证 200，却不检查模型名

- 启用功能开关 → 验证无错误，却不检查功能已激活

- 更换环境 → 验证部署成功，却不检查环境变量

### 问题 2：后台进程累积

**发生了什么：**

- 会话中分派多个子代理

- 每个启动后台服务器进程

- 进程累积（4 个以上服务器在运行）

- 陈旧进程仍占用端口

- 后续 E2E 测试连到配置错误的陈旧服务器

- 测试结果混乱／错误

**根因：**
子代理无状态，不知道先前子代理的进程；没有清理协议。

**影响：** 中高——测试连接错误服务器，出现假通过／假失败，调试混乱。

### 问题 3：子代理提示词上下文膨胀

**发生了什么：**

- 标准做法：让子代理读完整计划文件

- 实验：只给任务、模式、文件和验证命令

- 结果：更快、更聚焦，一次完成更常见

**根因：**
子代理把词元和注意力浪费在无关计划章节。

**影响：** 中——执行更慢，失败尝试更多。

**有效做法：**

```
你正在向 packnplay 的测试套件添加一个 E2E 测试。

**你的任务：** 将 `TestE2E_FeaturePrivilegedMode` 添加到 `pkg/runner/e2e_test.go`

**测试内容：** 本地 devcontainer 功能在元数据中请求 `"privileged": true` 时，容器应以 `--privileged` 标志运行。

**严格遵循 TestE2E_FeatureOptionValidation 的模式**（位于文件末尾）

**写完后运行：** `go test -v ./pkg/runner -run TestE2E_FeaturePrivilegedMode -timeout 5m`
```

### 问题 4：交接前缺少自省

**发生了什么：**

- 增加自省提示：“用新鲜眼光看工作——哪里还能更好？”

- 任务 5 的实现者发现失败测试源于实现缺陷，不是测试缺陷

- 追踪到第 99 行：`strings.Join(metadata.Entrypoint, " ")` 生成无效 Docker 语法

- 没有自省，只会报告“测试失败”而没有根因

**根因：**
实现者不会自然地在报告完成前退一步批评自己的工作。

**影响：** 中——本可由实现者发现的缺陷交给审查者。

### 问题 5：mock 与接口漂移

**发生了什么：**

```typescript
interface PlatformAdapter {
  close(): Promise<void>;
}
await adapter.cleanup();
vi.mock('web-adapter', () => ({
  WebAdapter: vi.fn().mockImplementation(() => ({
    cleanup: vi.fn().mockResolvedValue(undefined),
  })),
}));
```

- 测试通过

- 运行时崩溃：“adapter.cleanup is not a function”

**根因：**
mock 根据有缺陷代码的调用生成，而非接口定义。TypeScript 无法捕获方法名错误的内联 mock。

**影响：** 高——测试产生虚假信心，运行时崩溃。

**为何 testing-anti-patterns 没阻止：**
技能覆盖测试 mock 行为和不理解就 mock，但没覆盖“从接口而非实现推导 mock”的具体模式。

### 问题 6：代码审查者文件访问

**发生了什么：**

- 分派代码审查子代理

- 找不到测试文件：“文件似乎不存在于仓库”

- 文件实际存在

- 审查者不知道要先显式读取

**根因：**
审查者提示词没有明确文件读取指令。

**影响：** 低至中——审查失败或不完整。

### 问题 7：修复工作流延迟

**发生了什么：**

- 实现者在自省中发现缺陷

- 实现者知道修复方法

- 当前流程：报告 → 我分派修复者 → 修复者修复 → 我验证

- 额外往返增加延迟却没有价值

**根因：**
实现者已经诊断，仍严格分离实现者和修复者角色。

**影响：** 低——延迟，但无正确性问题。

### 问题 8：技能未被读取

**发生了什么：**

- `testing-anti-patterns` 技能存在

- 人类和子代理写测试前都没读

- 本可避免部分问题（并非全部——见问题 5）

**根因：**
没有强制子代理读取相关技能，提示词也不含技能读取。

**影响：** 中——未使用则技能投入浪费。

## 建议改进

### 1. verification-before-completion：增加配置变更验证

**增加新章节：**

```markdown
## 验证配置变更

测试配置、提供商、功能开关或环境的变更时：

**不要只验证操作成功。要验证输出反映了预期变更。**

### 常见失败模式

操作会因*某个*有效配置而成功，但并不是你想测试的配置。

### 示例

| 变更 | 不充分的验证 | 必需验证 |
|--------|-------------|----------|
| 切换 LLM 提供商 | 状态 200 | 响应包含预期模型名 |
| 启用功能开关 | 无错误 | 功能行为确实激活 |
| 更换环境 | 部署成功 | 日志／变量引用新环境 |
| 设置凭据 | 认证成功 | 已认证用户／上下文正确 |

### 关卡函数
```

声称配置变更生效前：

1. 识别：此变更后应有什么不同？

2. 定位：差异在哪里可见？

- 响应字段（模型名、用户 ID）

- 日志行（环境、提供商）

- 行为（功能激活／未激活）

3. 运行：显示可观察差异的命令

4. 验证：输出包含预期差异

5. 然后才：声称配置变更生效

红旗：

- “请求成功”却不检查内容

- 只检查状态码不检查响应体

- 只验证无错误，不做正面确认

```

**为什么有效：**
强制验证意图，而不只验证操作成功。

### 2. subagent-driven-development：为 E2E 测试增加流程卫生

**增加新章节：**

```markdown
## E2E 测试的流程卫生

分派启动服务（服务器、数据库、消息队列）的子代理时：

### 问题

子代理无状态，不知道先前子代理启动的进程。后台进程会持续并干扰后续测试。

### 解决方案

**分派 E2E 测试子代理前，在提示词中加入清理：**
```

启动任何服务之前：

1. 终止已有进程：pkill -f "<service-pattern>" 2>/dev/null || true

2. 等待清理：sleep 1

3. 验证端口空闲：lsof -i :<port> && echo "ERROR: Port still in use" || echo "Port free"

测试完成后：

1. 终止你启动的进程

2. 验证清理：pgrep -f "<service-pattern>" || echo "Cleanup successful"

```

### 示例
```

**为什么重要：**
陈旧进程以错误配置响应；端口冲突导致静默失败；进程累积拖慢系统；测试结果混乱，因为可能连错服务器。
```

**取舍分析：**

- 给提示词增加样板

- 但防止非常困惑的调试

测试完成后：

- 对 E2E 测试子代理值得

- mock 把缺陷编码进测试

```

### 为什么重要

- 陈旧进程以错误配置处理请求
- 端口冲突造成静默失败
- 进程累积拖慢系统
- 测试连到错误服务器，结果混乱
```

**取舍分析：**

- TypeScript 无法捕获错误方法名的内联 mock

- 测试通过，因为代码和 mock 同时错误

- 使用真实对象时运行时崩溃

### 6. testing-anti-patterns：增加 mock 接口漂移反模式

- 后台进程累积（问题 2）

```markdown
## 反模式 6：从实现推导 mock

**违规示例：**
```typescript
await adapter.cleanup();

const mock = {
  cleanup: vi.fn().mockResolvedValue(undefined)
};

interface PlatformAdapter {
  close(): Promise<void>;
}
```

- 上下文膨胀（问题 3）

- 自省（问题 4）

- mock 接口漂移（问题 5）

- 文件访问（问题 6）

- 修复延迟（问题 7）

- 技能未读取（问题 8）

```typescript

const mock = {
  initialize: vi.fn().mockResolvedValue(undefined),
  close: vi.fn().mockResolvedValue(undefined),
};
```

### 门控函数

```
编写任何 mock 之前：

  1. 停止——此时不要查看被测代码
  2. 查找：依赖的接口／类型定义
  3. 阅读：接口文件
  4. 列出：接口中定义的方法
  5. mock：只 mock 这些方法，并严格使用这些名称
  6. 不要：查看你的代码调用了什么

  如果测试因代码调用了 mock 中不存在的内容而失败：
    ✅ 正确——测试发现了代码缺陷
    修复代码，让它调用正确的接口方法
    不要修改 mock

  危险信号：
    - “我会 mock 代码实际调用的内容”
    - 从实现中复制方法名
    - 未阅读接口就编写 mock
    - “测试失败，所以我把这个方法加入 mock”
```

**检测：**

看到运行时错误“X 不是函数”而测试却通过时：

1. 检查 X 是否被 mock

2. 比较 mock 方法与接口方法

3. 查找方法名不一致

```

**为什么有效：**
直接处理反馈中的故障模式。

### 8. subagent-driven-development：允许实现者修复自己发现的问题

**修改步骤 2：**

**当前：**

```

```

**建议：**

```
子智能体先自我反思，然后：

如果自我反思发现可修复问题：
  1. 修复问题
  2. 重新运行验证
  3. 报告：“初次实现 + 自我反思修复”

否则：
  报告：“实现完成”

报告中包括：
- 自我反思发现
- 是否应用修复
- 最终验证结果
```

**为什么有效：**
实现者已经知道修复方法时，可以减少往返延迟。有记录的案例显示，原本可为入口点缺陷节省一次往返。

**取舍：**
提示词稍复杂，但端到端更快。

## 风险与缓解措施

### 风险：提示词膨胀

**问题：** 添加全部要求会让提示词难以承受
**缓解：**

- 分阶段实现（不要一次添加全部）

- 让部分补充具有条件（端到端卫生只用于端到端测试）

- 考虑为不同任务类型提供模板

### 风险：分析瘫痪

**问题：** 过多反思／验证拖慢执行
**缓解：**

- 让门控函数保持快速（数秒，而非数分钟）

- 初期将精简上下文设为可选

- 监控任务完成时间

### 风险：虚假安全感

**问题：** 遵循检查清单不能保证正确
**缓解：**

- 强调门控函数是最低要求，而非上限

- 在技能中保留“运用判断”的表述

- 记录技能捕获常见失败，而非全部失败

### 风险：技能分歧

**问题：** 不同技能给出冲突建议
**缓解：**

- 跨全部技能审查改动的一致性

- 记录技能如何互动（集成章节）

- 部署前用真实场景测试

## 建议

**立即推进阶段 1：**

- verification-before-completion：配置变更验证

- testing-anti-patterns：mock 与接口漂移

- requesting-code-review：明确读取文件

**最终确定前与 Jesse 测试阶段 2：**

- 征求关于自我反思影响的反馈

- 验证流程卫生方案

- 确认技能阅读要求值得额外开销

**阶段 3 在验证前暂缓：**

- 精简上下文需要真实世界测试

- 实现者修复工作流变更需要仔细评估

这些改动处理用户记录的真正问题，同时尽量减少使技能变差的风险。
