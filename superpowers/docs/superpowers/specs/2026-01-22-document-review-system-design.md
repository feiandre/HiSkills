# 文档审查系统设计

## 概述

向 superpowers 工作流增加两个审查阶段：

1. **规格文档审查**——头脑风暴之后、writing-plans 之前

2. **计划文档审查**——writing-plans 之后、实施之前

二者都遵循实施审查使用的迭代循环模式。

## 规格文档审查者

**目的：** 验证规格完整、一致，可用于实施规划。

**位置：** `skills/brainstorming/spec-document-reviewer-prompt.md`

**检查内容：**

| 类别 | 查找内容 |
|----------|------------------|
| 完整性 | TODO、占位符、“TBD”、不完整章节 |
| 覆盖 | 缺失错误处理、边界情况、集成点 |
| 一致性 | 内部矛盾、冲突需求 |
| 清晰度 | 含糊需求 |
| YAGNI | 未被要求的功能、过度设计 |

**输出格式：**

```
## 规格审查

**状态：** 已批准 | 发现问题

**问题（如有）：**
- [章节 X]：[问题]——[为什么重要]

**建议（仅供参考）：**
- [不阻塞批准的建议]
```

**审查循环：** 发现问题 → 头脑风暴代理修复 → 重审 → 重复直到批准。

**分派机制：** 用 Task 工具，`subagent_type: general-purpose`。审查者提示词模板提供完整内容。头脑风暴技能的控制器分派审查者。

## 计划文档审查者

**目的：** 验证计划完整、符合规格且任务分解合理。

**位置：** `skills/writing-plans/plan-document-reviewer-prompt.md`

**检查内容：**

| 类别 | 查找内容 |
|----------|------------------|
| 完整性 | TODO、占位符、不完整任务 |
| 规格一致 | 计划覆盖规格需求，无范围蔓延 |
| 任务分解 | 任务原子化、边界清楚 |
| 任务语法 | 任务及步骤有复选框语法 |
| 块大小 | 每块少于 1000 行 |

**块定义：** 块是计划文档内任务的逻辑分组，由 `## Chunk N: <name>` 标题分隔。writing-plans 技能按逻辑阶段（如“基础”“核心功能”“集成”）创建边界。每块应自足到可独立审查。

**规格一致验证：** 审查者收到两项：

1. 计划文档（或当前块）

2. 供参考的规格文档路径

审查者阅读两者并比较需求覆盖。

**输出格式：** 与规格审查者相同，但仅限当前块。

**审查流程（逐块）：**

1. writing-plans 创建块 N

2. 控制器将块 N 内容与规格路径分派给 plan-document-reviewer

3. 审查者读取块与规格并返回裁决

4. 有问题：writing-plans 代理修复块 N，返回第 2 步

5. 已批准：进入块 N+1

6. 重复直到所有块批准

**分派机制：** 与规格审查者相同，Task 工具配 `subagent_type: general-purpose`。

## 更新后的工作流

```
brainstorming -> spec -> SPEC REVIEW LOOP -> writing-plans -> plan -> PLAN REVIEW LOOP -> implementation
```

**规格审查循环：**

1. 规格完成

2. 分派审查者

3. 有问题：修复 → 返回第 2 步

4. 已批准：继续

**计划审查循环：**

1. 块 N 完成

2. 为块 N 分派审查者

3. 有问题：修复 → 返回第 2 步

4. 已批准：下一块或实施

## Markdown 任务语法

任务和步骤使用复选框语法：

```markdown
- [ ] ### Task 1: Name

- [ ] **Step 1:** Description
  - File: path
  - Command: cmd
```

## 错误处理

**审查循环终止：**

- 没有硬性迭代上限，循环持续到审查者批准

- 超过 5 轮时，控制器应提请人类指导

- 人类可选择继续迭代、带已知问题批准或中止

**分歧处理：**

- 审查者提供建议：指出问题但不阻塞

- 代理认为反馈错误时，应在修复中解释原因

- 同一问题迭代 3 轮后仍分歧，提请人类

**审查者输出格式错误：**

- 控制器应验证输出含必需字段（状态、适用时的问题）

- 格式错误时，附带预期格式说明重新分派

- 两次格式错误后，提请人类
