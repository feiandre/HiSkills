# SDD 修复循环重设计——设计规范

**状态：**已批准设计（2026-07-15 与 Jesse 头脑风暴）；随后编写实现计划。
**目标：**使 subagent-driven-development 技能的审查修复循环收敛且自主运行，并让文档易读，同时不重写经评估调优的语言。
**硬性不变量：**现有经评估调优的句子只移动，不改写。新机制随演练证据交付。

## 问题

四个问题，均在真实会话中观察到：

1. **病态审查循环。**循环字面上是“重复直到批准”——没有轮次上限。每次重审都是对整个差异的全新完整审查，因此不确定的前沿审查者每轮都会提出新发现，而不是验证修复。结果：实现、审查、修复、审查、审查、修复、审查、修复——没有断路器。严格成本规范（2026-06-10）独立测得审查循环次数是运行间成本波动的最大来源。

2. **互相矛盾的修复策略。**流程图和“构造审查者提示词”派发专用修复子代理；Red Flags 说“实现者（同一子代理）修复它们”；implementer-prompt.md 的“Review 后发现”部分假定会重新接续实现者。同一个技能对“谁修复？”给出三个答案。

3. **结构不断累积。**十三个顶层部分；一项活动的指导散落在其中四个部分。“构造审查者提示词”成了大杂烩，包含审查者指导、修复策略、最终审查策略及计划冲突裁定。

4. **Red Flags 格式。**七个相邻技能使用 `| Excuse | Reality |` 合理化表；SDD 则有一个 17 条“Never”清单及三个“If X”迷你块。

## 设计决策

| # | 决策 | 理由 |
|---|----------|-----------|
| 1 | 原实现者修复自己的审查发现——就地恢复它。 | 它已掌握任务上下文；所有权胜过路过式修补者。全新“修复子代理”会为每项发现重建上下文，并且缺少任务框架。 |
| 2 | 重审范围限定在发现项。 | 每轮全新完整审查是反复变动的引擎。限定范围的重审使循环在结构上收敛；最终整分支审查仍是广泛的最后安全网。 |
| 3 | 五轮修复时触发断路器：三次恢复，然后用更强模型全新派发两次。 | Jesse 的决定。经历三次恢复仍存活的循环通常意味着实现者看不到自己的问题——在更强能力的全新派发中一步解除锚定并提升能力。 |
| 4 | 断路器跳闸时，控制器裁定并路由。不新增人类检查点——结构性失败进入现有 BLOCKED 停止。 | SDD 的重点就是自主执行。控制器掌握审查者缺少的计划与跨任务上下文；现有文本已授权它这样做（“在审查循环中裁定”），只是从未说明机制。 |
| 5 | 按生命周期重组 SKILL.md，保留调优句子。 | 从根源解决“难以遵循”。内容移至使用点，符合项目方向（近期提交把回顾部分折叠到使用点）。 |
| 6 | 将 Red Flags 转为 `| Excuse | Reality |` 合理化表；把硬规则移到各自使用点。 | 与其他七个技能一致。借口需要反驳；规则在读者行动处执行。 |

## 修复循环

触发条件：任务审查返回规范 ❌ 或任何 Critical/Important 发现。

**第 1–3 轮——恢复原实现者。**原样发送发现（Critical/Important 及规范缺口）。实现者修复、重跑覆盖测试、将修复报告追加到现有报告文件，并返回简短契约。在没有代理恢复功能的宿主上，“恢复”是携带简报、报告文件和发现的全新派发——无论哪种方式，报告文件都是持久记忆。

**第 4–5 轮——全新实现者，更强能力模型。**完整任务上下文：简报、报告文件、未解决发现，以及以下定位：“先前实现者已尝试 N 次；现在由你负责该任务。”

**每轮重审都限定范围。**重审者收到简报、更新后的报告、原始发现清单及限定修复范围的差异包（`review-package FIX_BASE HEAD`，其中 FIX_BASE 是审查者上次审查的头部；脚本已支持任意范围）。它裁决每项发现已解决/未解决，并仅标记修复差异中的新破坏。对修复未触及代码的新发现按非阻塞报告；控制器记入账本供最终审查。

**修复报告完整性门槛（保留现有规则）：**派发重审前，确认修复报告指出覆盖测试、运行命令和输出。

**不提前退出。**控制器在上限前绝不裁定——提前退出会重新打开现有内容有意封堵的漏洞：“预先评判发现，以免自己再跑审查循环”。一个例外与今天不变：与计划文本要求相冲突的发现立即交给人类（计划权威，而非循环反复）。

**Minor 发现**从不进入循环：到达时记入账本（保留现有规则）。

### 跳闸时裁定

第五轮失败后，控制器停止派发，并对照简报、计划和跨任务上下文裁定每项未解决发现：

- **有争议或错误** → 记入账本并写一行裁定（“控制器：审查者错误，因为 X”），继续。最终审查会看到双方。

- **真实但不承重** → 以 known-open（已知未解决）记入账本，继续。之后触及该区域的派发会携带该条目的指针。

- **真实且承重**（后续任务依赖它，或它揭示计划缺陷） → 进入现有 BLOCKED 停止。搁置并继续会把结构性失败推迟到成本最高点，让依赖项在它之上构建，因此结构性失败应停止运行——通过现有停止条件，不新增检查点。

每项裁定都是账本条目。仍禁止静默丢弃。

## 文档重组

新的骨架，按执行顺序：

1. 引言——为何使用子代理、核心原则、叙述、连续执行

2. 何时使用——不变，包括决策图

3. 流程——为新循环更新图表

4. 设置——工作树、账本检查/恢复、飞行前计划审查、待办事项

5. 模型选择——保持一个横切部分；每次派发都查阅，因此折叠到使用点会重复五次

6. 任务循环——五个编号步骤：

1. 派发实现者（task-brief 脚本、五部分派发组合、必须提供模型行）

2. 处理报告（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）

3. 审查任务（review-package 脚本、审查者派发组合、约束视角、不预判、⚠️ 处理）

4. 修复循环（上述机制）

5. 完成任务（追加账本、更新待办）

7. 最终审查——审查包、固定模型、一次修复波、一次限定范围重审、裁定

8. 完成——finishing-a-development-branch

9. 常见合理化——表格

10. 示例工作流——更新以展示基于恢复的修复轮，以及断路器未触发

“构造审查者提示词”“文件交接”和“持久进度”融入各规则适用步骤。每个经评估调优的句子只落到一个新位置；实现计划中的移动图跟踪来源 → 目标，使审查能验证没有内容被删除或改写。

## 合理化表

以借口形式表达的 Never 项转为行；新行覆盖循环病态。草拟行（最终措辞在实现时确定）：

| 借口 | 现实 |
|--------|---------|
| “规范符合度差不多就行” | 审查者发现缺口 = 未完成。 |
| “我自己修吧，派发是开销” | 控制器修复会污染你的上下文并跳过审查。恢复实现者。 |
| “再来一轮就会收敛” | 超过上限后，轮次不会收敛。应裁定。 |
| “审查者反正还会找新东西” | 限定范围重审检查修复，不检查品味。未触及代码的新发现进入账本，不进入循环。 |
| “这个发现显然错了，我丢掉它” | 只能在上限时裁定，且每项裁定都是账本条目。禁止静默丢弃。 |
| “修复很小，跳过重审” | 未经审查的修复正是回归进入的方式。 |

并非借口的硬规则（绝不并行实现者、绝不在没有差异文件时派发审查者、必须提供模型行、绝不重新派发账本已完成任务）移到使用点。

## 提示词模板

- **implementer-prompt.md**——“Review 后发现”按恢复语义重写：你会带着发现被恢复；修复、重跑覆盖测试、追加到报告文件、返回简短契约。

- **task-reviewer-prompt.md**——仅用于初次审查；尾部重审句子移出。

- **re-review-prompt.md（新）**——限定范围的重审契约：输入为简报、更新报告、原始发现、限定修复范围的差异包；输出为逐发现裁决（已解决/未解决）、修复差异中的新破坏，以及其外的非阻塞观察。作为独立模板，因为它是不同契约——把完整审查模板过度复用于多种用途造成了当前歧义。

- **接管派发（第 4–5 轮）**——由 implementer-prompt.md 加 SKILL.md 指导组成（简报、报告路径、未解决发现、接管定位）；不新增模板文件。

## 最终审查循环

不变：合并基线包、最强模型、一个拥有完整发现清单的修复者。新增：对修复波只做一次限定范围重审，然后由控制器裁定。剩余承重发现会在 finishing-a-development-branch 向已参与的人类呈现。分支末端也获得有界循环。

## 评估

`evals/` 中三个新演练场景：

1. **恢复而非重新派发：**任务审查返回发现；控制器必须恢复同一实现者，而非派发修复子代理。

2. **断路器跳闸：**预置一个永不满足的审查者；第五轮失败后控制器必须停止派发、裁定、记账并继续——不得循环。

3. **结构性发现停止：**一个承重发现（后续任务依赖）；控制器必须通过 BLOCKED 停止，而非搁置。

另对现有 SDD 场景做前后运行，以捕获重组引起的回归。
