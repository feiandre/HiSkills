# SDD 按任务限定范围的审查派发

通过将每项任务的审查提示限定在该任务内并停止重复工作，让子智能体驱动开发的逐任务审查更省钱、更快，同时不降低审查力度；最终分支审查仍保持广泛范围。

## 问题

SDD 的逐任务代码质量审查员经常针对单个任务的差异做出分支级审查规模的工作。证据来自两个真实的本地 SDD 会话：`a1a6719a-6109-453a-9933-34ae396f5bae`（sen-core-v2）和 `0cc1a12d-9984-4c35-8615-9d42dadb2c47`（serf），均位于 `~/.claude/projects/`：

- 在 sen-core-v2 会话中，8 名质量审查员中的 7 名进行了全仓库 grep 搜索；最昂贵的一名在约 200 秒内运行了 50 多条 Bash 命令。在这两个会话中，同样任务的质量审查成本是规格审查成本的 4 至 8 倍。

- 规格审查员的提示包含“仅读取此差异中的文件。不要遍历更广泛的代码库”，因此范围始终紧凑：6 至 16 次工具调用，耗时 14 至 65 秒。

- 没有审查员自主运行重量级测试。所有观察到的整包或重复测试运行，都是控制器编写的提示明确要求的（“检查所有使用处”“如果有帮助就运行测试，尤其是针对竞态的测试”“还有其他地方读取 `Meta()` 吗？”）。

根本原因，按影响大小排序：

1. **逐任务质量提示继承了合并就绪审查。** `code-quality-reviewer-prompt.md` 委托给 `requesting-code-review/code-reviewer.md`，后者询问架构、可扩展性、安全性、生产就绪程度，并以“可以合并了吗？”结束。这种框架允许对单任务差异开展分支级广度的审查。规格提示对差异范围的限制从未移植过来。

2. **控制器没有获得编写审查提示的指导**，因此自行发明开放式指令（“检查所有使用处”），而审查员会逐字照办。

3. **整个流水线重复劳动。** 质量模板中的“计划一致性”维度再次检查规格审查员刚刚验证的内容。审查员对相同代码重新运行实现者已经运行并报告过、且附有 TDD 证据的测试套件。

4. **逐任务审查和最终审查共用一个模板**，因此任何地方都没有体现“逐任务窄范围、最终审查宽范围”。

一份现场报告（`~/2026-06-09-code-quality-reviewer-scope-budget-issue.md`）首先指出了这个问题。它引用的会话和主要数字无法核实，但其定性诊断已通过两个真实本地会话得到确认。其中一点需要更正：横切审计（锁顺序、变更的契约）有时是*正确*的审查方法；修复方案必须要求先说明具体风险才能扩大范围，而不是禁止扩大范围。

## 目标

- 逐任务审查限定在任务范围：先读差异、有理由才扩大范围、不重复运行测试。

- 最终整分支审查保持当前广度。

- 不减少审查能发现的问题。

## 非目标／明确保留的行为

- **保留完整复审。** 修复后复审时，审查员仍以完整阅读范围审查整个任务。（但不重新运行实现者刚刚在修订代码上运行的测试。）这有意拒绝现场报告提出的“复审预算”补救办法：其最糟示例中运行 `-race` 和 `-count=100` 循环的复审成本，由下述测试预算约束，而不是通过缩小复审员的阅读范围来约束。

- ~~**两个审查阶段保持独立。** 规格符合性和代码质量仍由独立子智能体负责，串行设关，不合并。~~ **已被下述成本迭代取代**：实际评估的经济数据表明每次派发的开销主导成本，维护者允许重新考虑一切。目前逐任务阶段由一名任务审查员给出两项结论；独立且范围广泛的最终审查仍然保留。

- **协调器保留模型判断权。** 不强制审查使用更高或更低的模型档次。

- **不改动 `requesting-code-review/`。** 它继续作为最终分支审查和临时审查的宽范围模板。

- 结论顺序（先报告规格符合性，再报告质量）、修复与复审循环，以及必须修复严重／重要问题的要求均不改变。

## 成本迭代（上线后的评估经济数据）

质量强化文字（证据规则、约束传递、干净输出）加入后，实际的前后对照运行暴露了成本回退：go-fractals 从 42.8 分钟／14.5M token（首个任务范围版本）增加至 69.9 分钟／32.2M（强化版本），质量则达到与基线持平（盲评 8.5 对 8.5）。对子智能体轮次的分析将成本依次归因于：便宜模型执行多步骤工作需要 2 至 3 倍轮次（1197 个子智能体轮次中 678 个来自 haiku）；每次派发的开销（每个任务启动 3 个子智能体，每个都重新推导差异；控制器协调占费用的一半）；以及证据规则导致的叙述。

- **迭代 1：** 模型选择指导强调轮次数比 token 单价更重要（多步骤工作至少使用中档模型），可选的内联差异，证据只引用不叙述，重要问题定义为修复前无法信任，仅对严重／重要问题派发修复。结果：68.2 分钟／22.9M，token 降低 29%，实际耗时基本不变；措辞为可选时，控制器仅在 22 次审查派发中的 2 次粘贴了差异。

- **迭代 2：** 将逐任务规格和质量审查合并为一个 `task-reviewer-prompt.md`（一名审查员、一次差异阅读、两项结论；一次修复派发处理两类问题）；实现者迭代时运行针对性测试，提交前运行一次完整套件。结果（go-fractals）：47.5 分钟／15.7M／13.55 美元，各维度均优于基线，盲评为 9/10，基线为 7/10。

- **迭代 3：** 校准规则将妨碍合并的可维护性损害（原样重复、吞掉错误、无断言的测试）列为重要问题，且轻微问题必须粘贴进最终审查供分诊；审查员的怀疑范围扩展至实现者的设计理由（“按 YAGNI 保留”只是说法，不是结论）；将差异作为文件交给审查员（`git diff > /tmp/sdd-task-N.diff`，通过重定向避免进入控制器上下文；审查员只需一次 Read 调用）。此前要求粘贴进提示的指导，因为局部看来合理的上下文经济考虑而未被采用（11 至 17 次派发中仅 0 至 6 次采用）。

- **最终冻结配置（e355795），全部五个场景通过：** go-fractals 为 44.4 分钟／13.4M／11.67 美元（相较基线，时间减少 32%、token 减少 37%、费用减少 27%）；svelte-todo 为 62.8／19.7M／15.76 美元（-21%／-28%／-25%）；rejects-extra-features 为 1.31 美元（对照 1.88 美元）；spec-reviewer-flaws 持平；植入缺陷场景（v3：判断性决策适用公开标记的透明度标准，名称承诺验证却从未执行验证的测试适用必须修复标准）通过，缺陷被发现并修复。

### 迭代 4 至 5（2026-06-10）：如实呈现方差、结构性修复、正向操作配方

相同配置的重跑暴露了运行间方差（提示相同，耗时却从 44.4 增至 57.1 分钟；审查员使用逃生口的倾向从每次审查 1.0 次工具调用变成 6.3 次），因此此后所有结论都使用范围。go-fractals 上五种并行实验变体，加上对真实本地会话记录的挖掘，产生了最终配置（包含负面结果的完整日志：`evals/docs/experiments/2026-06-10-sdd-cost-experiments.md`）：

- **采用：** 最终审查包（按控制器模型价格计费的最终审查员从 33 轮降至 6 轮）；两个模板中强制的 `model:` 行（文字指导曾在会话中途失效，17 次派发继承 opus，多花 5 美元）；任务简报和报告文件（`scripts/task-brief`；忠实性锚点，小幅节省上下文）；`<git-dir>/sdd/progress.md` 中的进度账本（真实会话压缩后重新派发整段已完成任务，约 22 个任务产生 269 次派发）；汇总式最终修复者（一个真实会话的逐问题修复波次比其所有任务总和还贵）；限定范围的修复测试；使用唯一 SHA 范围命名附带材料（兼容工作树和子模块）；派发组合配方和审查员具名风险预算（微型测试中正向配方转录 3.0 个值，禁止式 4.4，对照 3.6，禁止可能适得其反；见 `2026-06-10-positive-instruction-redesign-design.md`）。

- **已测试但未采用：** 控制器轮次批处理和并行调用流水线（控制器每条消息恰好发出一次工具调用，每次运行均为 0 条多工具消息；46% 的轮次用于思考／叙述，形成提示无法降低的下限）；后台派发流水线（28 次中 7 次采用该机制，但收益低于这些场景约 ±6 分钟的噪声下限）。

- **最终验证配置（b81f35b 系列），所有关卡通过：** go-fractals 为 54.1 至 54.7 分钟／14.4 至 16.6M／12.81 至 14.31 美元（基线 64.9／21.2M／16.07 美元）；svelte-todo 为 55.0 分钟／19.3M／14.99 美元（基线 79.7／27.3M／20.98 美元）；植入缺陷通过／2.77 美元。全部 8 次相同设计的 fractals 运行范围为 44.4 至 57.1 分钟／13.4 至 20.0M／11.67 至 14.84 美元，即使最差抽样也在所有维度优于基线；中间区间通常节省约 20% 至 25%。

## 设计

### 共同原则：不要对未改变的代码重跑测试

实现者的报告包含与受审代码完全对应的测试结果和 TDD 红／绿证据。审查员通过阅读验证。只有阅读产生了现有运行结果无法回答的具体疑问时才运行测试，且只运行针对性测试而非整个套件。在审查子智能体只读的运行环境中（例如 Antigravity 将审查模板映射到无命令访问权的 `research` 类型），审查员改为在报告中指出本来会运行的测试。

修复后，实现者重跑覆盖修订代码的测试；复审员不重复运行。目前没有任何机制强制这一前提：`implementer-prompt.md` 只描述初始的实现、测试、提交流程，没有修复迭代指令。因此本规格也向 `implementer-prompt.md` 加入：修复审查发现后，重跑覆盖修订代码的测试，并在修复报告中包含结果。

这一原则出现在两个审查提示、实现者提示和控制器指导中。

### 1. 新文件：`skills/subagent-driven-development/code-quality-reviewer-prompt.md` 改为自包含

停止委托给 `requesting-code-review/code-reviewer.md`。逐任务质量审查员获得独立且限定范围的提示模板：

- **定位：**“你正在审查一个任务的实现的代码质量。”这是限定任务范围的关卡，不是合并审查。

- **规格符合性已经确定：** 规格审查已经通过，不重新争论需求或计划一致性。

- **保留的审查维度：** 代码质量（清晰度、重复、错误处理）、测试质量（真实行为而非模拟）、可维护性，以及现有 SDD 专属检查（单一职责、独立可测试性、计划中的文件结构、此次变更造成的文件增长）。移除：计划一致性、安全性／可扩展性／生产就绪维度以及合并结论。

- **范围预算：** 从 `git diff BASE..HEAD` 开始，优先阅读变更文件；只有为了评估能明确说出的具体风险才查看相邻代码。锁顺序、函数／API 契约变更、共享可变状态等横切变更都是合理的具名风险，可以据此检查调用处。默认不遍历代码库。

- **测试预算：** 除上述共同原则外，除非先指出具体怀疑的不稳定测试或竞态，否则不运行整包套件、竞态检测器或重复／高次数运行。其他情况下在报告中建议重量级验证，而不是自行运行。实现者报告的测试输出中的警告或噪声也属于发现的问题；输出应当干净（实现者自审也检查这一点）。

- **证据规则：** 审查员针对每个“检查事项”给出文件:行号证据，不能只回答是／否。（实际评估发现审查员放过了提示已明确指出的缺陷之后加入：无障碍名称检查和临时目录清理检查都获得了没有依据的“是”，尽管缺陷就在受审差异中。）

- **只读规则** 以精简形式保留：不修改工作树、索引、HEAD 或分支状态。当前模板中说明如何 `git worktree add` 的句子不移入此文件，限定差异范围的审查无需检出其他版本（理由与下述规格提示清理相同）。

- **结论：** 优点／问题（严重／重要／轻微）／“任务质量：批准 | 需要修复。”

### 2. 清理 `skills/subagent-driven-development/spec-reviewer-prompt.md`

- 移除介绍 `git worktree add` 用法的句子。保留只读规则；限定差异范围的规格审查无需检出其他版本。

- 解决“仅限差异”的限制与“独立验证一切”之间的矛盾：通过对照需求阅读差异判断规格符合性。实现者的 TDD 证据证明“能够运行”，适用共同测试原则。

- 新增第三种结论通道：无法从差异验证的需求（位于未改动代码中、横跨多个任务）明确报告为“⚠️ 无法从差异验证，控制器应检查 X”，不再遍历代码库或静默放行。流程图的通过／失败二元菱形无法分流这种情况，所以控制器指导（§3）定义了处理方式：⚠️ 项目不阻止派发质量审查员，但控制器必须在标记任务完成前自行解决每一项（它掌握计划与跨任务上下文）；控制器确认的真实缺口按规格审查失败处理，退回实现者。

- 把虚构前提“实现者完成得快得可疑”替换为有依据的怀疑：将实现者报告视为关于代码的未验证主张。保持同样不轻信，不发明事实。

### 3. `skills/subagent-driven-development/SKILL.md` 控制器变更

- **模型选择：** 将“架构、设计和评审任务：使用最有能力的可用模型”替换为判断指导——像选择实现者模型那样选择评审者模型，并随差异大小、复杂性和风险调整。“任务复杂性信号”列表重新界定，明确其条目描述实现任务；评审者模型选择遵循同样判断，因此狭窄差异评审不会自动映射为“广泛代码库理解 → 最有能力的模型”。

- **评审者提示词构建**（危险信号附近的新指导）：派发评审者时，没有具体任务理由就不要写开放式指令（“检查所有用法”“必要时运行竞争测试”）；不要让评审者重跑实现者已在同一代码上运行的测试；不要把发现预先判给评审者（绝不指示评审者忽略或不要标记某问题——在评审循环中裁决疑似误报）；每任务评审是限定到任务的闸门——广泛评审只在最终整个分支评审时进行一次。（预判规则是在一次实际评测发现控制器虚构“计划禁止共享辅助函数”并指示质量评审者不要标记植入的 DRY 违规后加入的。）控制器还必须粘贴约束该任务的全局规格约束——版本下限、命名和文案规则、平台要求。一次实际运行在“Go 1.21+”设计上交付了 `go 1.26.1` 模块下限，因为评审者从未看到约束。控制器还必须在每次派发时明确指定模型；省略模型会继承会话模型（通常最昂贵），静默破坏模型选择。

- **处理规格评审者的 ⚠️ 项**（处理实现者状态旁边的新指导）：控制器在标记任务完成前，自行解决每个“无法从差异验证”的项目；确认的缺口作为规格评审失败退回实现者。

- **Final review stays broad, explicitly:** the final whole-branch reviewer dispatch node gains an explicit pointer to `../requesting-code-review/code-reviewer.md`. （目前该模板只能通过每任务质量提示词的委派触达；移除委派后，无引用的最终评审模板会成为孤儿。） 集成章节中 `superpowers:requesting-code-review` 提供“评审子智能体代码评审模板”的说明修正为只适用于最终评审。

- **示例工作流：** 示例中的质量评审者行更新为新结论词汇（“任务质量：已批准”）；最终评审者的“可合并”行保留。

- 流程图拓扑不变；⚠️ 通道由控制器指导处理，不新增图分支。

## 本变更未修复的内容（已知、延后）

规格评审者依据控制器粘贴的任务文本判断；它无法发现控制器从计划提取时遗漏的要求。这是“控制器提供全文”的架构属性，不是提示词问题，不在本变更范围。

## 验证

- 插件基础设施测试（`tests/`）仍通过。

- 改动前后运行 SDD 技能行为评测（`git submodule update --init evals`，然后按 `evals/README.md`）。具体包括：`sdd-go-fractals`、`sdd-svelte-todo`、`sdd-rejects-extra-features`（端到端 SDD，含规格评审者的 YAGNI 闸门）和 `spec-reviewer-catches-planted-flaws`。

- 本变更暴露的已知评测缺口：还没有场景在单个 SDD 任务内植入代码质量缺陷并断言每任务质量评审者捕获它，也没有场景衡量每评审者探索成本（工具调用／grep 次数）。增加一个场景覆盖首个缺口（植入单任务质量缺陷 → 每任务评审者必须在最终评审前标记）。探索成本方面，人工比较改动前后评测记录中的评审子智能体工具调用次数。
