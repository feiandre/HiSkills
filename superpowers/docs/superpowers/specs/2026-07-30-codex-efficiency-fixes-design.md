## 五项处理

### T1. 禁止 SDD 工作者派发审查

**证据：**4 个语料中的 9/9 个二级派生都由实现者发起审查；9 个都是控制者本已派发审查的同任务重复。派发契约从未说审查不是工作者的职责，实现者提示中的“自审”在子代理可再派生的宿主（Codex）中被具体化成一个审查子代理。

**修改：**

- `skills/subagent-driven-development/implementer-prompt.md`：增加“不得派发子代理”。自审就是阅读自己的 diff；所有审查派发由控制者负责；工作者创建的审查者会重复流程已有审查。

- `skills/subagent-driven-development/SKILL.md`：任务循环增加一行派发契约，并增加 Red Flags 行：“独立审查能增强报告” → 审查是控制者的下一步；你的审查者会是重复席位。

- 使用宿主中立措辞（子代理无法派生的宿主中无操作）。

**评分：**`score_e6.py`（按派生者角色统计二级派生、重复审查族）；同范围变体由 `score_e5.py` 评分。**基线：**9/9 由工作者发起，0 个反例。**标准：**二级派生中 0 个由工作者发起，且审查覆盖保留（每个任务仍恰好获得一次控制者派发的任务审查）。

### T2. 事件驱动等待

**证据：**每个语料中 60–78% 的 `wait_agent` 调用超时（dev 67.1%，spinout 60.2%）。源码调研：V2 等待是事件订阅而非轮询；一次长等待与每 10 秒轮询的唤醒延迟相同，调用量约为其 1/90；已完成子代理的 FINAL_ANSWER 会推入父代理邮箱，在下一次模型请求时被取出，无需等待。

**修改**（`skills/using-superpowers/references/codex-tools.md`）：

- 绝不用短超时轮询。

- 仍有本地工作时不要等待——子结果会在下一轮通过邮箱到达。

- 确实空闲时，只调用一次 `wait_agent`，使用较长 `timeout_ms`（900000 以上；宿主上限 3600000）。

- 说明 V2 限制：完成邮件带 `trigger_turn=false`，不会唤醒空闲控制者——这是 `wait_agent` 唯一职责。

**评分：**`score_e7.py`（超时率、轮询间隔、缓存重复计费估计——该数字始终标为估算）。**基线：**dev 超时率 67.1%。**标准：**超时率低于 25%，且任务完成率不下降。

### T3. 修正 codex-tools.md

**证据：**现行指引有五项说法被 Codex 源码否定（能力文档均有文件行号引用）：

1. 多代理 V2 不存在 `close_agent`（仅 V1 有）。V2 自动 LRU 淘汰已完成子代理；不关闭无成本；`followup_task` 会透明重载被淘汰子代理。

2. 修复轮始终可通过 `followup_task` 恢复实现者——dev 中“宿主无法再给派生代理发消息时，每轮修复派新实现者”的分支在 V2 已失效。

3. 角色文件（`~/.codex/agents/**.toml`）在 0.145+ 的隔离分叉中确实通过 `agent_type` 附加到派生代理。

4. 全历史分叉接受 `model`/`reasoning_effort` 覆盖；只拒绝 `agent_type`。（出于上下文卫生，SDD 仍建议隔离分叉，但准确说明行为。）

5. 派发指引绝不能列出非 V2 模型预设——V2 派生允许列表仅含 v2 预设，其他会直接报错。

**修改：**重写 `skills/using-superpowers/references/codex-tools.md` 的多代理段落，使版本描述合乎事实（V1 与 V2 行为不同处明确标注）。

**评分：**源码引用（已验证）；共享测试没有评分器回归。`score_e8.py` 保留为 V1/V2 schema 检测器，而非卫生评分器——不发布 `close_agent` 清单。

### T4. 头脑风暴三路径路由器（variant C：始终保留批准）

**证据：**微型测试中，现行 HARD-GATE 文案把有界任务推入完整流程 5/5 次；无指引控制组和三路径路由器都能区分 5/5：绝对措辞压制了模型本来具有的区分能力。完整测试中，流程量随规模适度变化（16.7 对 24.0 次工具调用，有界对架构），但两份文档仪式（规格→计划）在每次重复中无条件执行。测得浪费来自无条件产物仪式，而非批准关卡。

**设计（variant C）：**三条路径调整**产物规模**，每条路径在实施前都保留人工批准：

- **探针**（可行性问题，明确一次性）：用 2–3 句话说明问题和探测方式，获得点头后执行。无文档。结果作为建议返回；构建产物始终标记为一次性。

- **有界**（对已理解流程的明确小改动）：在聊天中给出简短设计，获批准后实施。不写规格文件，不调用 writing-plans。

- **架构**（重构组件、新子系统、修改公共接口）：沿用当前完整流程——规格文档、审查、writing-plans。

**护栏（均随路由器发布）：**

- 明确说出分类（“这看起来有界，所以我在这里给出短设计，而不写规格”），让人类可以推翻。

- 两条路径之间拿不准时，选更重的一条。

- 单向棘轮：中途发现隐藏复杂度时升级路径；任务中途绝不降级。

- 新增 Red Flags 行，针对把分类当逃生通道（“我把它叫作有界，就能跳过文档”）。

**修改**（`skills/brainstorming/SKILL.md`）：HARD-GATE 保留“批准前不实施”，删除把“不论看起来多简单”作为流程驱动；重写反模式部分（罪过是跳过批准，非跳过文档）；清单步骤 6–9 成为架构路径；流程图加入路由器；增加危险信号。内容经过精心调校，遵循 writing-skills 方法，并随以下完整评估证据发布。

**评分（三层）：**

1. **微型测试**（改编 `ceremony-path-micro.py`）：variant C 原文，加上活动尚未测试的对抗性模糊简报（模式像有界、实际隐藏公共接口变更）。标准：探针/有界/架构可区分（每格至少 4/5）；模糊简报升级为完整流程（至少 4/5）；架构从不下调（5/5）。

2. **Codex 仪式测试：**修复臂运行 `cx-ceremony-{spike,bounded,arch}`，各 3 次，用 `score_e4.py` 普查。标准：有界重复有批准轮，但零已提交规格文件、零 writing-plans 仪式；架构保留完整双文档流程；探针保持最小。

3. **全局回归测试：**在 Claude Code 和 Gemini 上运行同样三个仪式场景（实验装置工作：这些场景目前受 codex gate），各 3 次；并在三个宿主上检查触发验收（“做一个 React 待办列表”应自动触发头脑风暴并进入完整/架构路径）。

### T5. 子代理派生时明确指定模型

**证据：**CLI 0.146 根派生 100% 明确模型（dev 14/14）；实际缺口在二级——2/2 子代理派生遗漏 `model`。源码调研：只设 `model` 而不设 `reasoning_effort` 会把 effort 重置为模型默认，而非父代理值。

**修改**（`skills/using-superpowers/references/codex-tools.md`）：

- 每次派生（包括作为子代理）都同时设 `model` 和 `reasoning_effort`；明确点名 effort 重置陷阱。

- 建议在 `~/.codex/config.toml` 设置 `[agents].default_subagent_model` 和 `[agents].default_subagent_reasoning_effort`，作为可能遗漏的机器级兜底。

**评分：**共享测试中用 `score_e1.py` 按深度统计每次派生的明确模型率。**基线：**二级 0/2 明确。**标准：**每个深度的每次派生都明确模型和 effort。预先登记的限制：若 T1 完全消除二级派生，T5 改按根派生回归（保持 100%）和文档正确性评分，二级结果记为“零结果不确定”；配置兜底成为实际机制。
