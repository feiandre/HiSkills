# 编写技能

## 概述

**编写技能就是把测试驱动开发应用到流程文档中。**

**个人技能存放在运行环境的技能目录中**（Claude Code 中为 `~/.claude/skills/`）——其他运行环境中的路径见 [codex-tools.md](../using-superpowers/references/codex-tools.md) 或 [gemini-tools.md](../using-superpowers/references/gemini-tools.md)。Codex、Copilot CLI 和 Gemini CLI 也都识别 `~/.agents/skills/` 作为跨运行环境别名。

你编写测试用例（使用子智能体的压力场景），观察它们失败（基线行为），编写技能（文档），观察测试通过（智能体遵从），然后重构（堵住漏洞）。

**核心原则：** 如果没有看过智能体在没有技能时失败，你就不知道技能是否教了正确内容。

**必需背景：** 使用本技能前必须理解 superpowers:test-driven-development。该技能定义 RED-GREEN-REFACTOR 基本循环。本技能将 TDD 适配到文档。

**官方指导：** Anthropic 官方的技能编写最佳实践见 references/anthropic-best-practices.md。该文档提供额外模式和指南，补充本技能以 TDD 为核心的方法。

## 什么是技能？

**技能**是经过验证的技术、模式或工具的参考指南。技能帮助未来的智能体找到并应用有效方法。

**技能是：** 可复用技术、模式、工具、参考指南

**技能不是：** 关于你曾经如何解决一次问题的叙事

## 技能的 TDD 映射

| TDD 概念 | 技能创建 |
|-------------|----------------|
| **测试用例** | 使用子智能体的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | 智能体在没有技能时违反规则（基线） |
| **测试通过（GREEN）** | 智能体在技能存在时遵从 |
| **重构** | 在保持遵从的同时堵住漏洞 |
| **先写测试** | 编写技能之前运行基线场景 |
| **观察失败** | 记录智能体使用的准确合理化理由 |
| **最少代码** | 编写针对这些具体违规行为的技能 |
| **观察通过** | 验证智能体现在遵从 |
| **重构循环** | 发现新的合理化理由 → 堵住漏洞 → 再次验证 |

整个技能创建过程都遵循 RED-GREEN-REFACTOR。

## 何时创建技能

**在以下情况创建：**

- 该技术对你而言并不直观明显

- 你会在不同项目中再次参考它

- 模式适用范围广（不限于具体项目）

- 其他人能从中受益

**不要为以下情况创建：**

- 一次性方案

- 已在别处有充分文档记录的标准做法

- 项目专属约定（放入你的指令文件）

- 机械性约束（如果可用正则／验证强制执行，就自动化；文档留给需要判断的情况）

## 技能类型

### 技术

带步骤的具体方法（condition-based-waiting、root-cause-tracing）

### 模式

思考问题的方式（flatten-with-flags、test-invariants）

### 参考

API 文档、语法指南、工具文档（office docs）

## 目录结构

```
skills/
  skill-name/
    SKILL.md              # 主要参考（必需）
    supporting-file.*     # 仅在需要时
```

**扁平命名空间**——所有技能位于同一个可搜索命名空间

**以下内容使用独立文件：**

1. **大型参考**（100 行以上）——API 文档、完整语法

2. **可复用工具**——脚本、实用程序、模板

**保持内联：**

- 原则和概念

- 代码模式（少于 50 行）

- 其他所有内容

## 编写 SKILL.md

技能的 `description` 只说明何时使用：触发条件和症状，并以“Use when...”开头。绝不概括技能工作流，因为读到工作流摘要的智能体会遵循摘要，而不读取技能本身。

编写或修改技能前置元数据、名称或描述，或需要缩减其大小时，阅读 [references/discovery.md](references/discovery.md)：SKILL.md 模板、描述和关键词指南、命名、token 预算以及交叉引用其他技能。

## 流程图

在技能中新增或修改流程图时，先阅读 [references/flowcharts.md](references/flowcharts.md)：流程图何时值得存在、Graphviz 约定以及如何渲染。

## 代码示例

**一个优秀示例胜过许多平庸示例**

选择最相关的语言：

- 测试技术 → TypeScript/JavaScript

- 系统调试 → Shell/Python

- 数据处理 → Python

**优秀示例：**

- 完整且可运行

- 注释充分，说明原因

- 来自真实场景

- 清楚展示模式

- 可直接调整（不是通用模板）

**不要：**

- 用 5 种以上语言实现

- 创建填空模板

- 编写刻意造作的示例

你很擅长移植——一个优秀示例就足够。

## 文件组织

### 自包含技能

```
defense-in-depth/
  SKILL.md    # 所有内容内联
```

适用情况：所有内容都能容纳，不需要大型参考

### 带可复用工具的技能

```
condition-based-waiting/
  SKILL.md    # 概述和模式
  example.ts  # 可调整的可用辅助程序
```

适用情况：工具是可复用代码，而不只是叙述

### 带大型参考的技能

```
pptx/
  SKILL.md       # 概述和工作流
  pptxgenjs.md   # 600 行 API 参考
  ooxml.md       # 500 行 XML 结构
  scripts/       # 可执行工具
```

适用情况：参考材料太大，不适合内联

在正文中通过解释器调用随附脚本（`bash scripts/tool.sh`、`node scripts/tool.js`），绝不要直接使用裸路径：某些运行环境的插件打包器会移除可执行位，裸 `scripts/tool.sh` 在那里会以 `Permission denied` 失败。

## 铁律（与 TDD 相同）

```
没有先失败的测试，就没有技能
```

这适用于新技能以及对现有技能的编辑。

先写技能再测试？删除它，从头开始。
未经测试就编辑技能？同样违规。

**没有例外：**

- 不适用于“简单新增”

- 不适用于“只是添加一个章节”

- 不适用于“文档更新”

- 不要把未测试的修改作为“参考资料”保留

- 不要在运行测试时“顺手调整”

- 删除就是删除

**必需背景：** superpowers:test-driven-development 技能解释了为何重要。同样原则适用于文档。

## 测试所有技能类型

不同技能类型需要不同测试方法：

### 强制执行纪律的技能（规则／要求）

**示例：** TDD、verification-before-completion、designing-before-coding

**测试方法：**

- 学术问题：他们理解规则吗？

- 压力场景：他们会在压力下遵从吗？

- 组合多种压力：时间＋沉没成本＋疲惫

- 找出合理化理由并加入明确反制

**成功标准：** 智能体在最大压力下仍遵循规则

### 技术技能（操作指南）

**示例：** condition-based-waiting、root-cause-tracing、defensive-programming

**测试方法：**

- 应用场景：他们能正确应用该技术吗？

- 变体场景：他们能处理边界情况吗？

- 缺失信息测试：指令有缺口吗？

**成功标准：** 智能体成功将技术应用到新场景

### 模式技能（心智模型）

**示例：** reducing-complexity、information-hiding 概念

**测试方法：**

- 识别场景：他们知道何时适用该模式吗？

- 应用场景：他们能使用心智模型吗？

- 反例：他们知道何时**不应**应用吗？

**成功标准：** 智能体正确识别何时及如何应用模式

### 参考技能（文档／API）

**示例：** API 文档、命令参考、库指南

**测试方法：**

- 检索场景：他们能找到正确信息吗？

- 应用场景：他们能正确使用找到的信息吗？

- 缺口测试：常见用例都覆盖了吗？

**成功标准：** 智能体找到并正确应用参考信息

## 跳过测试的常见合理化理由

| 借口 | 事实 |
|--------|---------|
| “技能显然很清楚” | 对你清楚 ≠ 对其他智能体清楚。要测试。 |
| “这只是一份参考” | 参考也会有缺口和不清楚的章节。测试检索。 |
| “测试太小题大做” | 未测试的技能一定会有问题。测试 15 分钟能节省数小时。 |
| “出现问题再测试” | 问题就是智能体无法使用技能。部署前测试。 |
| “测试太繁琐” | 测试比在生产中调试糟糕技能更省事。 |
| “我很确信它很好” | 过度自信必然带来问题。仍然测试。 |
| “学术审阅足够” | 阅读 ≠ 使用。测试应用场景。 |
| “没时间测试” | 部署未测试技能，会在之后修复它时浪费更多时间。 |

**这些都意味着：部署前测试。没有例外。**

## 让形式匹配失败类型

编写指导前先归类基线失败。能防住一种失败的形式，可能明显加剧另一种失败。

| 基线失败 | 正确形式 | 错误形式 |
|---|---|---|
| 在压力下跳过／违反规则（知道更好却仍这样做） | 禁止＋合理化理由表＋警示信号（见 references/bulletproofing.md） | 温和指导（“优先……”“考虑……”） |
| 遵从了，但输出形态错误（提示膨胀、结论被埋没、重述规格） | 正向配方或契约：说明输出**是**什么——由哪些部分组成及顺序 | 禁止清单（“不要重述”“绝不叙述”） |
| 在已经产出的内容中遗漏必需元素 | 结构性：在他们填写的模板中加入 REQUIRED 字段或槽位 | 模板附近的散文提醒 |
| 行为应取决于某个条件 | 以可观察谓词为条件的处理（“若简报存在，就引用它”） | 无条件规则＋豁免条款 |

**为何禁止式指导在塑造输出时适得其反：** 面对竞争性激励（“让提示自包含”），智能体会围绕“不要 X”讨价还价。在派发提示指导的直接措辞对比测试中，禁止组产生的不想要内容明显多于配方组（分布完全分离），甚至比无指导对照组更差——要对自己的案例做微型测试，不要假设，但绝不默认使用禁止。配方没有可讨价还价的余地：输出要么符合声明形态，要么不符合。

**无论选择哪种形式，都遵守这些规则：**

- **不要加细微例外条款。**“除非重要，否则不要 X”会重新打开谈判；在同一措辞测试中，给获胜配方追加一个细微例外，就把它从稳定退化到噪声。把真实例外表达为基于可观察谓词的独立条件。

- **豁免条款不能限定范围。**“此限制不适用于代码块”仍会压制代码块。如果输出某部分必须豁免，就重构，使规则触及不到它。

## 防范合理化理由

基线失败属于纪律失败时，编写指导前阅读 [references/bulletproofing.md](references/bulletproofing.md)：堵住漏洞、精神与字面的界线、合理化理由表和警示信号列表。

## 技能的 RED-GREEN-REFACTOR

遵循 TDD 循环：

### RED：先写失败测试（基线）

在**没有**技能时用子智能体运行压力场景。记录准确行为：

- 他们做出了哪些选择？

- 他们使用了哪些合理化理由（原样记录）？

- 哪些压力触发了违规？

这就是“观察测试失败”——编写技能前，必须看到智能体自然会做什么。

### GREEN：编写最小技能

编写针对这些具体合理化理由的技能。不要为假设情况添加额外内容。

在**有**技能时运行相同场景。智能体现在应遵从。

### REFACTOR：堵住漏洞

智能体找到了新的合理化理由？加入明确反制。重新测试直到无懈可击。

### 完整场景前先微型测试措辞

完整压力场景是最终关卡，但每轮迭代都慢且昂贵。先用微型测试验证措辞本身：

1. **每次调用一个全新上下文样本**——直接 API 调用，或没有 API 访问权时用单次子智能体。系统提示＝指导将实际所在的真实上下文（完整技能或提示模板，而非孤立的指导）；用户消息＝一个会诱发失败的容易诱惑任务。

2. **始终包含无指导对照组。** 如果对照组没有出现失败，就没有需要修复的问题——停止，不要编写指导。

3. **每个变体至少 5 次重复。** 单个样本会说谎。

4. **人工阅读每个被标记的匹配项。** 可以程序评分，但模板回显和引用的反例会被误判为命中；仅凭自动计数会同时夸大失败和成功。

5. **方差也是一项指标。** 指导生效时，重复结果会收敛到同一形态。五次重复出现五种不同解释，说明措辞没有约束力——先收紧形式，再增加文字。

微型测试验证措辞；不能代替纪律技能的压力场景。

**测试方法：** 完整测试方法见 [references/testing-skills-with-subagents.md](references/testing-skills-with-subagents.md)：

- 如何编写压力场景。

- 压力类型：时间、沉没成本、权威、疲惫。

- 系统地堵住漏洞。

- 元测试技术。

## 反模式

### ❌ 叙事式示例

“在 2025-10-03 的会话中，我们发现空的 projectDir 导致……”

### ❌ 多语言稀释

example-js.js、example-py.py、example-go.go
**为什么不好：** 质量平庸，维护负担重。

### ❌ 在流程图中放代码

```dot
step1 [label="import fs"];
step2 [label="read file"];
```

**为什么不好：** 无法复制粘贴，阅读困难。

### ❌ 泛化标签

helper1、helper2、step3、pattern4
**为什么不好：** 标签应具有语义。

## 停下：转向下一个技能之前

**编写任何技能后，你都必须停下并完成部署流程。**

**不要：**

- 批量创建多个技能而不逐一测试。

- 当前技能尚未验证，就转向下一个技能。

- 以“批量处理效率更高”为由跳过测试。

**下面的部署检查清单对每个技能都是强制要求。**

部署未测试的技能等同于部署未测试的代码，违反质量标准。

## 技能创建检查清单（TDD 改编版）

**重要：为下面每个检查项创建一条待办。**

**RED 阶段：编写失败测试：**

- [ ] 创建压力场景；纪律类技能应组合 3 种以上压力。

- [ ] 不提供技能运行场景，逐字记录基线行为。

- [ ] 识别自我辩解和失败中的模式。

**GREEN 阶段：编写最小技能：**

- [ ] 名称仅使用字母、数字、连字符，不含括号或特殊字符。

- [ ] YAML frontmatter 含必需的 `name` 与 `description` 字段，最多 1024 个字符；参阅[规范](https://agentskills.io/specification)。

- [ ] 描述以“Use when...”开头，包含具体触发条件和症状。

- [ ] 描述使用第三人称。

- [ ] 全文包含便于搜索的关键词，如错误、症状、工具。

- [ ] 概述清晰，包含核心原则。

- [ ] 针对 RED 阶段识别的具体基线失败。

- [ ] 指导形式与失败类型匹配，参阅“让形式匹配失败类型”。

- [ ] 对行为塑形指导，其措辞已与无指导对照组进行微测试，重复 5 次以上，并手动阅读每个被标记的匹配结果；纯参考技能不适用。

- [ ] 代码放在正文中，或者链接到独立文件。

- [ ] 一个优秀示例，而不是多个语言版本。

- [ ] 提供技能运行场景，验证代理现在能够遵从。

**REFACTOR 阶段：堵住漏洞：**

- [ ] 从测试中识别新的自我辩解。

- [ ] 添加明确反驳，适用于纪律类技能。

- [ ] 根据全部测试迭代建立自我辩解对照表。

- [ ] 创建危险信号清单。

- [ ] 重新测试，直到没有可钻的漏洞。

**质量检查：**

- [ ] 仅在决策不明显时使用小型流程图。

- [ ] 快速参考表。

- [ ] 常见错误章节。

- [ ] 不写叙事故事。

- [ ] 辅助文件仅用于工具或大型参考资料。

**部署：**

- [ ] 将技能提交到 git，并在已配置时推送到自己的 fork。

- [ ] 如果具有广泛用途，考虑通过 PR 回馈上游。

## 发现工作流

未来的代理如何找到你的技能：

1. **遇到问题**，例如“测试不稳定”。

2. **搜索技能**，例如用 grep 搜索描述、浏览分类。

3. **找到 SKILL**，因为描述匹配。

4. **浏览概述**，判断是否相关。

5. **阅读模式**，查看快速参考表。

6. **加载示例**，仅在实现时进行。

**针对这一流程优化：** 尽早并经常放入可搜索词语。
