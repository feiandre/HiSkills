# 让技能抵御合理化借口

属于 superpowers:writing-skills。基线失败属于纪律失败时使用：智能体知道规则，却在压力下跳过。

## 让技能抵御合理化借口

强制纪律的技能（如 TDD）必须抵抗合理化。智能体很聪明，在压力下会找漏洞。

**范围：** 此工具集用于纪律失败——智能体知道规则却在压力下跳过。输出形式错误或遗漏元素时，基于禁止的加固会反噬；改用“让形式匹配失败”。

**心理学说明：** 理解说服技巧为何有效，有助于系统应用。参见本目录的 persuasion-principles.md，了解权威、承诺、稀缺、社会认同和团结原则的研究基础（Cialdini, 2021; Meincke 等，2025）。

### 明确堵住每个漏洞

不要只陈述规则——禁止具体变通：

```markdown
测试前写了代码？删除它。
```

```markdown
测试前写了代码？删除并重新开始。

**没有例外：**
- 不要留作“参考”
- 写测试时不要“改编”
- 不要看它
- 删除就是删除
```

### 处理“精神与字面”争论

尽早加入基础原则：

```markdown
**违反规则字面要求，就是违反规则精神。**
```

这能切断整类“我在遵循精神”的合理化。

### 建立合理化借口表

从基线测试记录借口（见下方测试章节）。智能体每个借口都进入表：

```markdown
| 借口 | 现实 |
|--------|---------|
| “太简单，不用测” | 简单代码也会坏。测试只需 30 秒。 |
| “我之后测” | 测试立即通过证明不了什么。 |
| “事后测试达到相同目标” | 事后测试 =“它做什么？”；先测试 =“它应该做什么？” |
```

### 创建危险信号列表

让智能体在合理化时容易自查：

```markdown
## 危险信号——停止并重新开始

- 测试前写代码
- “我已经手动测过了”
- “事后测试达到相同目的”
- “重在精神，不在仪式”
- “这次不同，因为……”

**这些都意味着：删除代码，用 TDD 重新开始。**
```

### 为违规征兆更新 SDO

在 description 中加入即将违反规则的征兆：

```yaml
description: 实现任何功能或修复缺陷时，在编写实现代码之前使用
```
