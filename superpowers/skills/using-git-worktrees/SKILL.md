# 使用 Git 工作树

## 概述

确保工作在隔离工作区中进行。优先使用平台的原生工作树工具。只有没有可用的原生工具时，才退回手动创建 git 工作树。

**核心原则：** 先检测现有隔离。然后使用原生工具。最后才退回 git。绝不要与运行环境对着干。

**开始时声明：** “我正在使用 using-git-worktrees 技能设置隔离工作区。”

## 步骤 0：检测现有隔离

**创建任何东西之前，先检查是否已经位于隔离工作区中。**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**子模块防护：** 在 git 子模块内部，`GIT_DIR != GIT_COMMON` 也成立。在得出“已经位于工作树中”的结论前，确认自己不在子模块中：

```bash
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**若 `GIT_DIR != GIT_COMMON`（且不是子模块）：** 你已经位于链接工作树中，应跳到第 2 步“项目设置”，不要再创建另一个工作树。

报告时附上分支状态：

- 位于分支：“已经在 `<path>` 的隔离工作区中，分支为 `<name>`。”

- 游离 HEAD：“已经在 `<path>` 的隔离工作区中（游离 HEAD，由外部管理）。需要在收尾时创建分支。”

**如果 `GIT_DIR == GIT_COMMON`（或位于子模块中）：** 你位于普通的仓库检出目录中。

用户是否已在指令中表达过工作树偏好？如果没有，创建工作树之前先征求同意：

> “需要我设置一个隔离工作树吗？它能保护你当前的分支，使其不受改动影响。”

已有明确偏好时直接遵循，不要再问。如果用户拒绝，在原处工作，并跳到步骤 2。

## 步骤 1：创建隔离工作区

**有两种机制。按以下顺序尝试。**

### 1a. 原生工作树工具（首选）

用户已经要求隔离工作区（步骤 0 中同意）。你是否已经有创建工作树的方法？可能是名为 `EnterWorktree`、`WorktreeCreate` 的工具，`/worktree` 命令，或 `--worktree` 标志。如果有，就使用它，并跳到步骤 2。

原生工具会自动处理目录位置、分支创建和清理。有原生工具却使用 `git worktree add`，会创建运行环境无法看见或管理的幽灵状态。

只有没有可用的原生工作树工具时，才进入步骤 1b。

### 1b. Git 工作树后备方案

**只有步骤 1a 不适用时才使用**——即没有可用的原生工作树工具。手动使用 git 创建工作树。

#### 目录选择

遵循以下优先顺序。用户明确表达的偏好，始终优先于观察到的文件系统状态。

1. **检查指令中是否已声明工作树目录偏好。** 用户已经指定时，直接使用，不要再问。

2. **检查是否有现成的项目本地工作树目录：**

注释含义：`.worktrees` 是首选（隐藏目录），`worktrees` 是替代选项。如果找到就使用。两者都存在时，优先 `.worktrees`。

3. **如果没有其他可用指导，** 默认使用项目根目录下的 `.worktrees/`。

#### 安全验证（仅针对项目本地目录）

**创建工作树前，必须验证目录已被忽略：**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**如果未被忽略：** 将它添加到 .gitignore，提交改动，然后继续。

**为什么关键：** 防止意外把工作树内容提交进仓库。

#### 创建工作树

```bash
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**沙箱回退：** 如果 `git worktree add` 因权限错误失败（沙箱拒绝），应告诉用户沙箱阻止了工作树创建，而你改为在当前目录工作；随后原地运行设置和基线测试。

## 步骤 2：项目准备

自动检测并执行适当的准备：

```bash
if [ -f package.json ]; then npm install; fi
if [ -f Cargo.toml ]; then cargo build; fi
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi
if [ -f go.mod ]; then go mod download; fi
```

## 步骤 3：验证干净基线

运行测试，确保工作区从干净状态开始：

```bash
npm test / cargo test / pytest / go test ./...
```

注释含义：使用适合项目的命令。

**如果测试通过：** 报告已准备就绪。

### 报告

```
工作树已就绪，位于 <full-path>
测试通过（<N> 个测试，0 个失败）
已准备好实施 <feature-name>
```

## 快速参考

| 情况 | 行动 |
|-----------|--------|
| 已在关联工作树中 | 跳过创建（步骤 0）。 |
| 位于子模块中 | 按普通仓库处理（步骤 0 的防护）。 |
| 有可用的原生工作树工具 | 使用它（步骤 1a）。 |
| 没有原生工具 | 使用 Git 工作树后备方案（步骤 1b）。 |
| `.worktrees/` 已存在 | 使用它（验证已被忽略）。 |
| `worktrees/` 已存在 | 使用它（验证已被忽略）。 |
| 两者都存在 | 使用 `.worktrees/`。 |
| 两者都不存在 | 检查指令文件，然后默认使用 `.worktrees/`。 |
| 目录未被忽略 | 添加到 .gitignore 并提交。 |
| 创建时出现权限错误 | 执行沙箱后备处理，在原处工作。 |
| 基线测试失败 | 报告失败并询问。 |
| 没有 package.json/Cargo.toml | 跳过依赖安装。 |

## 常见的自我辩解

| 借口 | 实际情况 |
|--------|---------|
| “我显然不在工作树中——没必要检查” | 执行步骤 0。运行环境创建的隔离和子模块都会误导目测判断；检测命令才能确定。 |
| “`git worktree add` 比找原生工具更快” | 原生工具（例如 `EnterWorktree`）负责位置、分支和清理。绕过它是首要错误——会创建运行环境无法看见或管理的幽灵状态。 |
| “工作树目录肯定已经被忽略了” | 运行 `git check-ignore`。未被忽略的工作树目录会让整棵目录树被提交进仓库。 |
| “什么目录名都行” | 明确指令优先于现有项目本地目录，而现有项目本地目录优先于 `.worktrees/` 默认值。 |
| “工作区是全新的——基线测试可以等等” | 不干净的基线会让后续每次失败都难以归因。现在运行测试；测试失败后是否继续，由人类协作者决定。 |
