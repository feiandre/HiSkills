# 编写计划

## 概述

为没有看过这个代码库、也没有看过这份规格的工程师编写实施计划。假设他们知道精确接口和精确测试后，就能用项目语言编写符合惯例的代码；计划留有选择空间时，他们也会作出合理选择。他们无法知道的是你已经作出的决定：哪些文件、哪些名称和签名、规格中的哪些数值、哪些测试能证明每项任务。这些都要记录。把整个计划拆成小块任务交给他们。DRY。YAGNI。TDD。频繁提交。

**开始时声明：** “我正在使用 writing-plans 技能创建实施计划。”

**上下文：** 如果在隔离工作树中工作，该工作树应当已在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`

- 用户对计划位置的偏好优先于此默认值。

## 范围检查

如果规格覆盖多个独立子系统，头脑风暴时就应已将其拆为子项目规格。如果没有，建议拆成单独计划——每个子系统一份。每份计划都应能独立产出可工作、可测试的软件。

## 文件结构

定义任务前，先列出将创建或修改哪些文件，以及各文件的职责。分解方式的决定在这里确定。

- 设计边界清楚、接口定义明确的单元。每个文件应有一项清楚的职责。

- 对能够一次装进上下文的代码，你最容易推理；文件职责集中时，编辑也更可靠。优先采用更小、专注的文件，避免一个大文件承担太多工作。

- 经常一起变更的文件应放在一起。按职责拆分，而不是按技术层拆分。

- 在已有代码库中，遵循既定模式。如果代码库使用大文件，不要擅自重构结构；但如果正在修改的文件已经膨胀到难以管理，将拆分纳入计划是合理的。

此结构将指导任务分解。每项任务都应产出完整自洽、独立看也合理的改动。

## 合理确定任务大小

任务是自带测试周期、值得让一位全新审查者把关的最小单元。划定任务边界时：将准备、配置、脚手架、文档步骤合并到其交付物需要这些内容的任务中；只有当审查者能够有意义地拒绝某项任务、同时批准相邻任务时，才拆分。每项任务结束时，都应有一个可以独立测试的交付物。

## 步骤粒度

**每个步骤都是一个具有可检查结果的动作：**

- “编写失败测试”——一个步骤。

- “运行它，确保失败”——一个步骤。

- “实现让测试通过的最少代码”——一个步骤。

- “运行测试，确保通过”——一个步骤。

- “提交”——一个步骤。

## 计划文档头部

**每份计划都必须以下面的头部开始：**

```markdown
# [功能名称] 实施计划

> **供代理工作者使用：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans，逐项任务实施此计划。步骤使用复选框（`- [ ]`）语法跟踪。

**目标：** [用一句话说明要构建什么]

**架构：** [用 2—3 句话说明方案]

**技术栈：** [关键技术/库]

**规格：** [本计划所实施的规格/设计文档路径——计划依据规格展开论证，
因此规格随计划一起交付；执行者两者都要阅读]

## 全局约束

[规格中适用于整个项目的需求——最低版本、依赖限制、
命名与文案规则、平台要求——每项一行，从规格中逐字复制精确值。
每项任务的需求都隐含包含本节。]

## 审查重点

[规格隐含、但尚未被任何任务测试覆盖，且最可能给软件使用者带来问题的五类输入
或故障模式——每项一行，说明输入或条件，以及合理的人会期待的行为，
按最可能发生的顺序排列。规格是一份愿景文档：它说明软件必须做什么，
不会穷尽软件将遇到的一切；没有提及某种输入，并不代表允许该输入导致程序崩溃。
将规格放在面前，在此一次性写出列表。然后针对每一行，
按照负责相关代码的任务自身的步骤风格，将锁定该行为的测试添加到该任务。]

---
```

## 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 使用：[本任务使用的前序任务产物——精确签名]
- 产出：[后续任务依赖的内容——精确函数名、参数与返回类型。
  任务实现者只能看到自己的任务；此块让其获知相邻任务使用的名称与类型。]

- [ ] **步骤 1：编写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试，验证其失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，并显示 "function not defined"（函数未定义）

- [ ] **步骤 3：在 `exact/path/to/file.py` 中实现 `function(input: InputType) -> ResultType`**

如果签名和测试仍留下选择空间，用一行说明方案
（调用哪个库函数、采用哪种数据结构）；只有它们无法确定的算法才提供代码块。

- [ ] **步骤 4：运行测试，验证其通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 一个步骤包含什么

当实现者能据此写出恰好一种合理实现时，这个步骤就写好了。全部要求就是：无歧义，而非事无巨细。每类步骤只包含使其无歧义所必需的信息，不再多写：

- **测试步骤：** 以代码给出测试名与断言，其中包含规格规定的精确值。

- **代码步骤：** 精确签名（名称、参数、返回类型）、所在文件，以及规格固定的具体值。函数体由实现者编写。只有对于签名和测试无法确定的算法，或规格固定的精确文案，才给出函数体。

- **验证步骤：** 要运行的命令，以及表示通过的输出。

- **引用另一任务：** 另一任务的 Interfaces 块会说明使用什么；计划不重复该任务的代码。

计划是实现者无法独自作出的决定的集合。计划比所描述的代码还长，就已经把代码写完了，而不是在写计划。没有作出任何决定的文字（“TBD”“处理边界情况”“添加适当验证”“为上述内容编写测试”，或没有任何任务定义的类型、函数）是另一种相反的失败；自审应发现这两类问题。

## 自审

写完整份计划后，用全新视角查看规格，并对照检查计划。这是你自己执行的检查清单，不是要派遣子代理。

**1. 规格覆盖：** 浏览规格中的每节、每项需求。是否能指出实现它的任务？列出所有缺口。

**2. 步骤扫描：** 每个步骤必须让实现者写出恰好一种合理内容，而且任何步骤都不得承载更多：没有决定任何事情的一行是缺口；签名和测试已经能确定的函数体是逐字转录。两类问题都要修正。

**3. 类型一致性：** 后续任务使用的类型、方法签名和属性名，是否与前序任务定义的一致？任务 3 中叫 `clearLayers()`，任务 7 中却叫 `clearFullLayers()`，就是缺陷。

**4. 审查重点：** 对规格隐含的每类输入或故障模式，是否有某项任务的测试覆盖？将其中尚未覆盖、最可能给使用者造成问题的五项放进 Review Focus 部分，并为每一行在负责的任务中添加对应测试。该部分为空，应表示你检查过且没有发现，而不是跳过检查。

**5. 比例：** 比较计划与规格的长度。计划比所实施的规格长数倍，就是程序的转录稿，不是计划。如果文档大部分是代码块，用签名、测试名和断言替代函数体，并检查每个步骤仍然没有歧义。

发现问题就直接修改。无需重新审查——修好并继续。如果发现某条规格需求没有对应任务，就添加任务。

## 执行交接

保存并自审计划后，向人类协作者提供链接供其阅读。如果他们已明确提供执行方式，请他们审阅计划并确认它体现了他们的需求；实施之前等待这次审阅，然后使用已确定的方式。否则，请他们在实施前审阅计划并选择执行方式。

**尚未提供执行方式时：**

**“计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。请审阅计划。你更倾向于哪种执行方式？**

- **子代理驱动**——每项任务由一个全新子代理实施，在下一项开始之前，由一位全新审查者检查；最后再做整个分支审查。最全面；每项任务和每次审查都需要全新上下文。

- **原生方式**——我在当前会话中，按照这个运行环境的工作方式亲自实施全部任务，然后由一位使用最强模型的全新审查者检查整个分支。费用最低、速度最快；直到最后才进行独立审查。由于计划已经承载设计，使用中档会话模型也能很好运行。

**对于这份计划，我推荐 <one of the two>（两者之一），因为 <one sentence from the plan: how much the tasks depend on each other's interfaces, how many there are, what a shipped mistake would cost>（结合计划用一句话说明：任务间对接口的依赖程度、任务数量、发布后发生错误的代价）。计划是否准确体现了你的需求，我们应采用哪种方式？”**

**已经提供执行方式时：**

**“计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。请审阅计划。它是否准确体现了你的需求？”**

**如果选择子代理驱动：**

- **必需子技能：** 使用 `superpowers:subagent-driven-development`。

**如果选择原生方式：**

- **必需子技能：** 使用 `superpowers:executing-plans`。
