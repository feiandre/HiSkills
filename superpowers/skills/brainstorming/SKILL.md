# 头脑风暴

你很擅长构建。你会构建自己认为用户想要的东西，而这种判断的依据，通常比感觉中薄弱得多。此技能用于在开始构建之前，弄清楚他们真正想要什么，以及为什么想要。

人们往往还没有完全想清楚自己要什么。好的问题能帮助他们想透。理解原因后，你才能按他们本来会作出的选择，处理那一百个他们从未提及的决定。

## 首先：你究竟知道什么？

回复之前，先问自己：关于他们想要什么、为什么想要，我知道些什么？

- **请求已包含所有重要信息**（“把图标改成矢车菊蓝”）。这是一个快速、清楚的任务。直接完成，并说明做了什么。

- **缺少某些不容忽视的信息。** 开始对话。

开始实施之前，必须依次：

1. 用一条单独的消息列出方案，并让人类协作者选择一个（参见“列出方案”）。

2. 编写设计文档，可以是简短版或完整版（参见“确定工作规模”）。

3. 获得他们对该文档的批准。

4. 调用 `superpowers:writing-plans` 技能。

有两种事情不属于实施：他们已经同意的探索原型（参见“用探索原型摸清情况”），以及他们选择跳过提问后，执行他们所要求的工作。

## 提问前先查看

在已有项目中，或他们提供了上下文时（规格、计划、交接说明、指定文件、之前的对话），在发出第一条消息之前先深入了解。阅读他们提及的内容，以及与之关联的代码或材料；持续阅读，直到能解释相关部分目前如何运作，以及这次改动会触及什么。项目或他们提供的上下文已经回答的问题，绝不要再问。

## 你的第一条消息

用以下一种方式推进工作：

- **他们已经说明想要什么**（一份规格、一份计划、一个详细请求）：整条消息以大约 200 个词为目标。用自己的话复述他们的请求，让他们判断你是否理解了整体：他们想要什么、为谁而做、为什么做，以他们已经说明的内容为限。补充你发现的相关情况：相关部分目前如何工作，改动会涉及什么。如果发现了他们可能未曾考虑、会改变请求内容或实现方式的情况，例如约束、冲突或成本更低的路径，直白说明。如何构建要等到理解他们的目标后再讨论（参见“列出方案”）。结尾先用一行邀请纠正，再提出一个关于他们需求的问题：在请求尚未明确的部分中，答案最能改变最终构建内容的那件事。规格往往不完整，所以先确认，再以它为基础继续。

- **他们尚未说明：** 使用他们自己的说法，围绕请求中最大的未决事项，提出一个开放式问题。解释为什么提问：答案会改变你构建的哪些内容。例如，对于“给我的面包店做一个网站”：“如果主要面向正在决定要不要到店的人，我会把营业时间和今天橱窗里有哪些商品放在最前面；接单则是另一种网站。你希望访客打开网站后做什么？”

如何结束这条消息，取决于他们是否要求进行头脑风暴：

- **他们要求了**（直接点名、调用此技能，或要求讨论设计）：以问题结尾。他们想进行这场对话。

- **他们没有要求：** 他们可能完全不想展开对话。提问之后，追加一句轻松的提议，表示也可以直接开始，例如“如果你更希望我直接动手，也可以说一声。”如果他们接受，技能到此结束：用一句清楚的话说明任何重要的实现选择（平台、语言、媒介），然后按正常流程完成他们要求的工作。

整条消息就这些内容。

## 对话

每条消息以一个问题结尾：一个句子，不要在后面附带示例答案列表。使用简单语言，难度只略高于人类协作者当前的理解水平。沿用他们的词汇，绝不要使用流程术语。你永远不需要向人类协作者引用本技能。

清楚、简洁。先说重要的内容。避免术语。报告发现时，提供最重要的发现，并表示其他内容也可提供。

**让他们描述。** 优先提出开放式问题。他们自己的表达包含你的选项无法承载的意图。只有他们卡住时，才提供简短选项。当他们说“你猜吧”或“你怎么看？”，提出具体建议。

**如何实现。** 每个项目都建立在关于媒介、工具、材料和资源的选择之上：应用的平台、编程语言和库；艺术作品的媒介。尽早弄清楚这些选择中哪些是他们想亲自决定的，哪些交给你，以及他们已经拥有哪些可用资源。有强烈见解或相关技能的人会希望详细讨论；依赖你的人需要合理的默认选择，并用简单的话说明。有现成工作时，沿用其已有技术。你作出的任何选择都应在设计中记为你的判断，绝不能写成他们已经同意的事。

**需要覆盖的范围。** 这是一片需要探索的领域，不是固定脚本。绝不要把下面内容照着念成问题：

- 这是什么类型的事物，特别之处是什么。

- 为什么现在做，他们认为什么样才算成功。

- 目标、非目标，以及反目标（即使技术上可用，什么情况仍会让它算失败）。

- 已有参考：他们在别处见过什么，喜欢或讨厌什么。

- 当前状态：现在有什么，试过什么。

- 他们在意的细节。

**让每个问题具体对应**他们的项目和已经告诉你的信息。像敏锐的同事一样采用苏格拉底式提问：每个问题都建立在他们上次的回答或你的发现之上，帮助他们思考可能遗漏的后果或情形（“投票在会议之前截止，这个月又有两名成员加入。在一轮投票进行中加入的人有投票权吗？”）。如果提问原因尚不明显，说明你希望了解什么，或答案会改变什么。给出一个可由他们纠正的提议，再解释理由，往往比提问更有效。

**提议调查。** 在具备一定基础后，如果进一步查看有帮助，提议去调查：深入他们的代码库或项目、他们自己的文件与数据，或网络。说明准备查找什么。是否进行，由他们决定。

**列出方案。** 在理解他们想要什么之后、正式撰写内容之前，用一条单独消息说明构建方式。提出几种真正可行的替代方案，剔除薄弱方案，包括违背他们初衷的方案和被现有工作排除的方案。展示剩下的两到三种，每种都要立足项目实际情况，并说明取舍。推荐其中一种并说明原因，然后询问他们选择哪种。如果确实只有一种合理方式，就直接说明，并解释其他方式为何不适合。这一步讨论如何构建；对于他们想要什么，应先让他们描述。

**展示，而不只是讲述。** 只要看图比阅读更有帮助，就提议使用下文的可视化辅助：

- 他们将会看到的东西：屏幕、页面、打印件、标牌。

- 布局或安排：屏幕、房间、日程。

- 流程或步骤序列。

- 外观会彼此不同的选项。

- 看图比读文字更易理解的结构：示意图、时间线、地图。

他们接受之后，用它提供可供反馈的模型、并排比较的方案，以及可以点击的临时原型。

**用探索原型摸清情况。** 代理式工作是瀑布式的，但速度非常非常快。快速做一个用完即弃的构建，往往是了解他们想要什么、或验证某种东西是否可行的最低成本方式。有帮助时就提议。如果他们只想做探索原型，就不要碍事。探索原型不写测试或只写极少测试，不追求万无一失，跳过计划、实施和审查流程。把探索得到的认识带回对话。

## 复述确认

边进行边复述。只要你已经充分理解某一部分，足以描述它（例如它的用途和服务对象，或某个部分的行为），就用大约 200—300 个词复述该部分，然后回到对下一部分的提问。整场对话交替进行复述与提问；最后一段覆盖所有剩余内容。

只有他们说过的内容才能记为他们的意见。你补充的任何内容，都应作为你的提议，并解释原因。每一段结尾都询问哪里不对或缺了什么。

发送一段复述之前，检查：它是否描述他们将要看到的东西，例如页面、屏幕、日程或打印件？如果是，且他们还没有收到可视化辅助的提议，就先单独发送下文的提议，把这段复述留到下一条消息。接受之后，将模型与描述放在一起。

## 确定工作规模

理解他们想要什么，且他们已经选定方案后，用简单的话说明工作规模。他们可以推翻这一判断。

| 规模 | 设计文档 |
|------|----------------|
| 小改动 | 简短版：把你们已经一起讨论过的内容写下来。 |
| 一个项目 | 完整的书面设计，见下文。 |

无论简短还是完整，设计文档都包含一个 **Approaches（方案）** 部分：考虑过的两到三种构建方式，各自的取舍，他们选了哪种，以及原因。他们应在对话中、你写文档之前作出选择。

如果工作在进行中扩大，停下来说明，并将规模提高一级。

如果这实际上是多个独立项目，就说明情况，商定顺序，然后逐个进行头脑风暴。

## 书面设计

编写一份清楚的文档，使该领域有能力的构建者无需回头询问人类协作者，就能据此制定计划。覆盖：

- 意图及其原因。

- 目标、非目标、反目标。

- 约束。

- 方案（见上文）。

- 实现方式中由他们决定的部分，按他们的决定记录。

- 留给构建者决定的内容。

对于小改动，简短设计也覆盖相同要点，每点一两行，直接交给人类协作者，不经过构建者检查。

**保存位置：** 在软件仓库中，保存为 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，并提交。其他情况先询问。人类协作者的偏好优先于这两项规定。

**构建者检查**（用于项目）：使用此目录中的 `builder-check-prompt.md` 派遣一个全新子代理。告诉人类协作者你要整理成文时，说明会先由一位审查者阅读，并且你可能再回来集中问一次问题。检查结果返回之前，不要交付文档。将构建者提出的问题分成三类：

- **已经回答：** 对话或项目已有答案，把答案写进文档。

- **小问题：** 合理的构建者可以自行决定，而且不会改变构建内容。你自行解决，并在文档中标注为你的决定。

- **属于他们的问题：** 只有人类协作者能回答，而且答案会改变构建内容。

将“属于他们的问题”集中在一条消息中提出，最重要的放前面。根据回答更新文档，然后交付，并简短列出你自行作出的决定，让他们阅读时能检查这些决定。这是检查产生的唯一一轮提问。没有子代理工具时，自己以该构建者的视角阅读文档。

<HARD-GATE>
在人类协作者批准设计文档之前，不得构建任何东西：小改动批准简短版，项目批准完整版。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实施技能。读取与探索可以进行。

有两个例外。如果他们选择跳过提问，本技能结束，关卡也随之解除。他们同意的探索原型可以构建；它始终标记为用完即弃，而保留其产物属于新的请求，必须重新经过本关卡。

设计文档批准后，下一步是计划：调用 `superpowers:writing-plans`，不要调用任何其他技能。
</HARD-GATE>

## 危险信号

| 想法 | 实际情况 |
|---------|---------|
| “我提供一组选项，让他们选择可能想要什么” | 选项会引导他们。先让他们自己描述。 |
| “我来填入合理的默认值” | 可以。明确说出来。他们没听过的默认选择，也是他们无从拒绝的选择。 |
| “我回答过他们的问题了，接下来写文档” | 先用一条单独消息列出方案。 |
| “我应该先解释流程” | 直接提问。流程会自然体现出来。 |
| “他们说这个想法‘听起来不错’” | 批准只涵盖你展示过的内容。尚未写出的设计文档没有获得批准。 |
| “探索原型能用了，我继续在它上面构建” | 保留它属于新请求。重新经过关卡。 |

## 可视化辅助

用于展示模型、示意图和原型的浏览器标签页。它是工具，不是一种模式：接受它，不代表每个问题都要转到浏览器。

**在需要时才提议。** 上文列出的情形第一次出现时才提议，绝不要一开始就提。提议必须单独成一条消息，里面不放其他内容：

> “展示给你看可能更容易。要我打开一个带模型预览的浏览器标签页吗？”

如果他们拒绝，继续使用文字；除非他们主动提起，不要再提供。

**对每个问题都问：看见它是否更易理解？**模型、布局、示意图和并排设计放在浏览器中。需求、范围、取舍和概念选择留在文字中。涉及 UI 的问题并不自动等于可视化问题。

如果他们接受，在启动服务器前读取本目录中的 `visual-companion.md`。
