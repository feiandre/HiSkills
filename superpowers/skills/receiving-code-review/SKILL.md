# 接收代码评审

## 概述

代码评审需要技术评估，不需要情绪表演。

**核心原则：** 先验证再实现。先询问再假设。技术正确性优先于社交舒适。

## 回应模式

```
收到代码评审反馈时：

1. READ（阅读）：完整阅读反馈，先不作反应
2. UNDERSTAND（理解）：用自己的话重述要求，或提问
3. VERIFY（验证）：对照代码库现实检查
4. EVALUATE（评估）：对这个代码库来说技术合理吗？
5. RESPOND（回应）：技术确认，或有理由的异议
6. IMPLEMENT（实现）：一次一项，逐项测试
```

## 禁止的回应

**绝不要：**

- “你完全正确！”（明确违反指令文件）

- “好观点！”／“反馈太棒了！”（表演式）

- “我现在来实现”（尚未验证）

**应改为：**

- 重述技术要求

- 提出澄清问题

- 建议错误时用技术推理提出异议

- 直接开始工作（行动胜于言语）

## 处理不清楚的反馈

```
如果有任何条目不清楚：
  停止——暂时不要实现任何内容
  对不清楚条目请求澄清

原因：条目可能相关。部分理解 = 错误实现。
```

**示例：**

```
你的人类伙伴：“修复 1-6”
你理解 1、2、3、6，不清楚 4、5。

❌ 错误：现在实现 1、2、3、6，稍后问 4、5
✅ 正确：“我理解第 1、2、3、6 项。继续前需要澄清第 4 和第 5 项。”
```

## 按来源处理

### 来自你的人类伙伴

- **可信**——理解后实现

- 范围不清楚时仍要**提问**

- **不要表演式赞同**

- **直接行动**或作技术确认

### 来自外部评审者

```
实现之前：
  1. 检查：对这个代码库技术正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现为何存在？
  4. 检查：适用于所有平台／版本吗？
  5. 检查：评审者理解完整上下文吗？

如果建议似乎错误：
  用技术推理提出异议

如果不易验证：
  明确说明：“没有 [X]，我无法验证。我应该 [调查／询问／继续] 吗？”

如果与你的人类伙伴先前决定冲突：
  先停下并与其讨论
```

**你的人类伙伴的规则：**“外部反馈——保持怀疑，但仔细核查。”

## 对“专业”功能进行 YAGNI 检查

```
如果评审者建议“正确实现”：
  在代码库中 grep 实际使用情况

  如果未使用：“这个端点没有被调用。移除它（YAGNI）？”
  如果已使用：再正确实现
```

**你的人类伙伴的规则：**“你和评审者都向我汇报。如果不需要这个功能，就不要添加。”

## 实现顺序

```
对于多项反馈：
  1. 先澄清所有不清楚内容
  2. 然后按以下顺序实现：
     - 阻塞问题（破坏、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项测试每个修复
  4. 验证没有回归
```

## 何时提出异议

以下情况提出异议：

- 建议会破坏现有功能

- 评审者缺少完整上下文

- 违反 YAGNI（未使用功能）

- 对该技术栈技术上不正确

- 存在遗留／兼容性原因

- 与你的人类伙伴架构决定冲突

**如何提出异议：**

- 使用技术推理，不作防御

- 提出具体问题

- 引用可工作的测试／代码

- 涉及架构时让你的人类伙伴参与

**如果不愿直接提出异议：** 说明这种顾虑，再把你看到的问题告诉伙伴。他们会欣赏你的诚实。

## 确认正确反馈

反馈确实正确时：

```
✅ “已修复。[简短说明改了什么]”
✅ “发现得好——[具体问题]。已在 [位置] 修复。”
✅ [直接修复并在代码中展示]

❌ “你完全正确！”
❌ “好观点！”
❌ “谢谢你发现！”
❌ “谢谢你 [任何事]”
❌ 任何感谢表达
```

**为什么不说感谢：** 行动说话。直接修复，代码本身会表明你听到了反馈。

**发现快写“谢谢”：** 删除它，改为说明修复。

## 得体纠正自己的异议

提出异议后发现错误时：

```
✅ “你是对的——我检查了 [X]，它确实 [Y]。现在开始实现。”
✅ “已验证，你是对的。我最初理解错了，因为 [原因]。正在修复。”

❌ 冗长道歉
❌ 为提出异议辩护
❌ 过度解释
```

客观说明纠正，然后继续。

## 常见错误

| 错误 | 修复 |
|---------|-----|
| 表演式赞同 | 重述要求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 批量处理而不测试 | 一次一项，逐项测试 |
| 假定评审者正确 | 检查是否破坏东西 |
| 回避提出异议 | 技术正确性优先于舒适 |
| 部分实现 | 先澄清所有条目 |
| 无法验证仍继续 | 说明限制，请求方向 |

## 真实示例

**表演式赞同（错误）：**

```
评审者：“移除遗留代码”
❌ “你完全正确！让我移除……”
```

**技术验证（正确）：**

```
评审者：“移除遗留代码”
✅ “正在检查……构建目标是 10.15+，此 API 需要 13+。为向后兼容仍需遗留代码。当前实现 bundle ID 错误——修复它，还是放弃 13 前支持？”
```

**YAGNI（正确）：**

```
评审者：“实现完整的指标跟踪，包括数据库、日期过滤、CSV 导出”
✅ “已 grep 代码库——没有地方调用此端点。移除它（YAGNI）？还是遗漏了使用位置？”
```

**不清楚条目（正确）：**

```
你的人类伙伴：“修复第 1-6 项”
你理解 1、2、3、6，不清楚 4、5。
✅ “理解 1、2、3、6。实现前需要澄清 4 和 5。”
```

## GitHub 讨论串回复

回复 GitHub 行内评审评论时，在评论串中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要作为 PR 顶层评论。
