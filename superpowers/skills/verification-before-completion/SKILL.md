# 完成前验证

## 概述

**核心原则：** 始终先有证据，再作断言。

**违反本规则的字面要求，就是违反本规则的精神。**

## 铁律

```
没有最新验证证据，不得声称完成
```

如果没有在当前消息中运行验证命令，就不能声称它通过。

## 关卡函数

```
在声称任何状态或表达满足之前：

1. 确定：什么命令能证明这个声明？
2. 运行：执行完整命令（最新、完整）
3. 阅读：完整输出，检查退出码，统计失败数
4. 验证：输出是否确认该声明？
   - 否：带证据说明实际状态
   - 是：带证据陈述声明
5. 只有此时：作出声明

跳过任一步骤＝撒谎，而非验证
```

## 常见失败

| 声明 | 所需证据 | 不足以证明 |
|---|---|---|
| 测试通过 | 测试命令输出：0 个失败 | 之前运行、“应该会通过” |
| Linter 干净 | Linter 输出：0 个错误 | 局部检查、外推 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 修改代码、假定已修复 |
| 回归测试有效 | 已验证红绿循环 | 测试通过一次 |
| 智能体已完成 | VCS 差异显示变更 | 智能体报告“成功” |
| 满足要求 | 逐行检查清单 | 测试通过 |

## 警示信号——停止

- 使用“应该”“大概”“似乎”

- 验证前表达满足（“太好了！”“完美！”“完成！”等）

- 未验证就要提交／推送／创建 PR

- 相信智能体的成功报告

- 依赖局部验证

- 认为“就这一次”

- 疲惫且想让工作结束

- **任何在未运行验证的情况下暗示成功的措辞**

## 防止合理化

| 借口 | 事实 |
|---|---|
| “现在应该能工作” | 运行验证 |
| “我很有信心” | 信心 ≠ 证据 |
| “就这一次” | 没有例外 |
| “Linter 通过了” | Linter ≠ 编译器 |
| “智能体说成功了” | 独立验证 |
| “我累了” | 疲惫 ≠ 借口 |
| “局部检查足够了” | 局部不能证明任何事 |
| “换个词就不适用规则” | 遵循精神高于字面 |

## 关键模式

**测试：**

```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “现在应该通过”／“看起来正确”
```

**回归测试（TDD 红绿）：**

```
✅ 编写 → 运行（通过）→ 回退修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ “我已经写了回归测试”（未验证红绿循环）
```

**构建：**

```
✅ [运行构建] [看到：退出码 0] “构建通过”
❌ “Linter 通过了”（linter 不检查编译）
```

**需求：**

```
✅ 重读计划 → 创建清单 → 逐项验证 → 报告缺口或完成
❌ “测试通过，阶段完成”
```

**智能体委派：**

```
✅ 智能体报告成功 → 检查 VCS 差异 → 验证变更 → 报告实际状态
❌ 相信智能体报告
```

## 何时应用

**始终在以下行为之前：**

- 任何成功／完成声明的变体

- 任何满足表达

- 任何对工作状态的正面陈述

- 提交、创建 PR、完成任务

- 进入下一任务

- 委派给智能体

**规则适用于：**

- 准确短语

- 改述和同义词

- 暗示成功的内容

- 任何暗示完成／正确的沟通
