# 修复循环

属于 superpowers:subagent-driven-development。任务审查报告规范 ❌、Critical/Important 发现，或你确认为真实缺口的 ⚠️ 项。

循环开始前，有两条路径立即离开：

- 推进过程中把 Minor 发现记入进度账本（`Task <N>: minor (deferred): <one-liner>`），并让最终整分支审查指向该列表，以分诊哪些必须在合并前修复。无人阅读的汇总等于静默丢弃。Minor 发现绝不进入循环。

- 标记为计划要求的发现——或任何与计划文本要求冲突的发现——由你裁决：对照计划文本权衡，依据规范作为约束权威决定，并在行动前记录裁决。不要因计划要求而驳回发现，也不要未经记录裁决就派发与计划冲突的修复。其余内容进入循环。一个修复轮包含一次修复派发和一次限定范围重审。每任务最多五轮：

**第 1-3 轮——恢复原实现者。**原样发送未解决发现。其上下文完整：知道任务、代码及自己的选择。若宿主无法向活跃子代理再发消息，派发携带简报路径、报告文件路径和发现的全新实现者——无论哪种方式，报告文件都是持久记忆。

**第 4-5 轮——在更强能力模型上派发全新实现者**（按 SKILL.md 的 Model Selection），携带简报路径、报告文件路径、未解决发现及以下定位：“先前实现者已尝试该任务 [N] 次；现在由你负责。阅读报告文件了解尝试过什么。”经历三次恢复仍存活的循环通常意味着实现者看不到自己的问题——全新视角与能力提升一步完成。

**每轮，无论哪种方式：**实现者修复、重跑覆盖修改代码的测试、将修复报告追加到同一报告文件，并返回简短契约。再次派发审查者前，确认修复报告包含覆盖测试、运行命令和输出；三者齐全后派发重审。在修复消息中点名覆盖测试文件——一行修复不需要整套测试。

**重审限定范围。**运行 `bash scripts/review-package PLAN_FILE FIX_BASE HEAD`，其中 FIX_BASE 是上一审查看到的头部，并用发现清单、简报、报告文件及打印的差异路径派发 [re-review-prompt.md](../re-review-prompt.md)。重审者对每项发现裁决 ADDRESSED 或 NOT ADDRESSED，并只标记修复差异中的新破坏。修复差异中的新 Critical/Important 破坏加入未解决清单。范围外观察作为延后 Minor 记入账本——绝不延长循环。

**每轮后，**向账本追加：`Task <N>: fix round <R>/5 (<X> addressed, <Y> open — <finding one-liners>; commits <a7>..<b7>)`（任务 N 第 R/5 轮修复：X 项已处理、Y 项开放；提交 a7..b7）

绝不要在控制器会话中亲自修复发现——你的上下文保持干净以协调，控制器修复会跳过审查。

**断路器。**第 5 轮重审仍有未解决发现时停止派发。亲自裁定每项发现——你掌握审查者缺少的计划和跨任务上下文：

- **审查者错误或观点可争议：**搁置——`Task <N>: parked — <finding> — Ruling: <why the code stands>`（任务 N：搁置——发现——裁决：代码为何成立）。最终审查看到双方。

- **真实，但无下游依赖：**同样搁置，裁决说明真实但延后。

- **真实且承重**——后续任务依赖，或揭示计划缺陷：裁定解除依赖工作阻塞的最小改动，记录为 `Task <N>: Ruling: <finding> — <what you decided and why>`，并带入下一任务派发。静默搁置结构性失败会让每个依赖任务在它之上构建；只有缺陷使前进每条路径都靠猜测时才停止。

只在达到上限时裁定。更早裁定来结束循环，只是换了名字的预判。每项裁定都是账本条目——禁止静默丢弃。
