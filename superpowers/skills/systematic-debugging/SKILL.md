# 系统化调试

## 概述

**核心原则：** 在尝试修复之前，始终先找到根本原因。只修复症状就是失败。

**违背此流程的字面要求，也就是违背调试的精神。**

## 铁律

```
未先调查根本原因，不得修复
```

如果尚未完成阶段 1，就不能提出修复方案。

## 何时使用

适用于任何技术问题：

- 测试失败。

- 生产环境缺陷。

- 意外行为。

- 性能问题。

- 构建失败。

- 集成问题。

**尤其在以下情况使用：**

- 面临时间压力（紧急情况会诱使人猜测）。

- “只需快速修一下”看起来显而易见。

- 已经尝试多次修复。

- 上一次修复无效。

- 还没有完全理解问题。

**以下情况也不要跳过：**

- 问题看起来简单（简单缺陷也有根本原因）。

- 赶时间（仓促行事必然导致返工）。

- 经理要求立刻修好（系统化处理比盲目折腾更快）。

## 四个阶段

必须完成每个阶段，才能进入下一阶段。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**

- 不要跳过错误或警告。

- 它们往往包含精确的解决方法。

- 完整阅读堆栈跟踪。

- 记下行号、文件路径和错误码。

2. **稳定复现**

- 能否可靠触发？

- 精确步骤是什么？

- 每次都会发生吗？

- 如果无法复现 → 收集更多数据，不要猜。

3. **检查最近的变更**

- 有什么变化可能导致此问题？

- Git 差异、最近的提交。

- 新依赖、配置变更。

- 环境差异。

4. **在多组件系统中收集证据**

**当系统具有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

**提出修复前，添加诊断观测手段：**

```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次，收集证据以显示故障发生在哪里
   然后分析证据，确定出故障的组件
   然后调查该特定组件
   ```

**示例（多层系统）：**

```bash
   echo "=== 工作流中可用的密钥： ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo 已设置 || echo 未设置)"

   echo "=== 构建脚本中的环境变量： ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "环境中存在 IDENTITY" || echo "环境中不存在 IDENTITY"

   echo "=== 钥匙串状态： ==="
   security list-keychains
   security find-identity -v

   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

**由此揭示：** 哪一层出了故障（密钥 → 工作流 ✓，工作流 → 构建 ✗）。

5. **追踪数据流**

**当错误发生在调用栈深处时：**

完整的反向追踪技巧见此目录中的 `root-cause-tracing.md`。

**简要步骤：**

- 错误的值来自哪里？

- 是什么携带错误值调用了这里？

- 持续向上追踪，直到找到源头。

- 在源头修复，而不是只修症状。

### 阶段 2：模式分析

**修复前先找到模式：**

1. **寻找正常工作的示例**

- 在同一代码库中查找类似且正常工作的代码。

- 哪些正常工作的内容，与出问题的内容相似？

2. **与参考实现比较**

- 如果是在实现某种模式，完整阅读参考实现。

- 不要略读——逐行阅读。

- 充分理解模式后再应用。

3. **找出差异**

- 正常和故障版本之间有什么不同？

- 列出每项差异，无论多么微小。

- 不要认定“这不可能有影响”。

4. **理解依赖**

- 它还需要哪些组件？

- 需要哪些设置、配置、环境？

- 它作出了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **提出单一假设**

- 清楚表述：“我认为 X 是根本原因，因为 Y。”

- 写下来。

- 要具体，不要含糊。

2. **最小化测试**

- 通过尽可能小的改动来检验假设。

- 一次只改变一个变量。

- 不要同时修多件事。

3. **验证后再继续**

- 是否有效？是 → 阶段 4。

- 无效？提出新的假设。

- 不要在其上继续叠加修复。

4. **当你不知道时**

- 说“我不理解 X”。

- 不要假装知道。

- 请求帮助。

- 做更多研究。

### 阶段 4：实施

**修复根本原因，而不是症状：**

1. **创建失败测试用例**

- 尽可能简单地复现。

- 能自动化就使用自动化测试。

- 没有框架时，编写一次性测试脚本。

- 必须在修复之前具备。

- 使用 `superpowers:test-driven-development` 技能编写正确的失败测试。

2. **实施单一修复**

- 解决已识别的根本原因。

- 一次只作一项改动。

- 不要附带“既然改到这里了”的改进。

- 不要捆绑重构。

3. **验证修复**

- 测试现在通过了吗？

- 是否没有破坏其他测试？

- 问题是否真正解决？

- 在声称成功之前，使用 `superpowers:verification-before-completion` 技能。

4. **如果修复无效**

- 停止。

- 统计：已经尝试了多少次修复？

- 如果 < 3：回到阶段 1，结合新信息重新分析。

- **如果 ≥ 3：停止并质疑架构（见下方步骤 5）。**

- 没有讨论架构之前，不要尝试第 4 次修复。

5. **如果 3 次及以上修复都失败：质疑架构**

**表明架构存在问题的模式：**

- 每次修复都在不同位置暴露新的共享状态、耦合或问题。

- 修复需要“大规模重构”才能实现。

- 每次修复都会在其他地方产生新症状。

**停下来，质疑根本基础：**

- 这种模式在根本上是否合理？

- 我们是否“只是出于惯性而坚持它”？

- 应该重构架构，还是继续修补症状？

**尝试更多修复前，与人类协作者讨论。**

这不是假设失败——这是架构错误。

## 危险信号——停止并遵循流程

如果发现自己在想：

- “先快速修一下，稍后调查。”

- “试着改一下 X，看看是否有效。”

- “添加多项改动，再运行测试。”

- “跳过测试，我手动验证。”

- “大概是 X，我来修。”

- “我还没完全理解，但这也许可行。”

- “模式说要 X，但我会换一种方式调整它。”

- “主要问题如下：[未调查就列出修复方案]。”

- 在追踪数据流之前提出解决方案。

- **“再试一次修复”（已经尝试 2 次以上时）。**

- **每次修复都在不同位置暴露新问题。**

**这些情况全都意味着：停止。回到阶段 1。**

**如果 3 次及以上修复都失败：** 质疑架构（参见阶段 4 的步骤 5）。

## 人类协作者发出的“你做错了”信号

**留意这些纠正：**

- “那不是正在发生吗？”——你未经验证就作了假设。

- “它会让我们看到……吗？”——你本应添加证据收集。

- “别猜了。”——你还没理解就开始提出修复。

- “再深入想一想。”——质疑根本基础，而不只是症状。

- “我们卡住了？”（感到挫败）——你的方法没有奏效。

**看到这些信号时：** 停止。回到阶段 1。

## 常见的自我辩解

| 借口 | 实际情况 |
|--------|---------|
| “问题简单，不需要流程” | 简单问题也有根本原因。对简单缺陷，这个流程也很快。 |
| “紧急情况，没时间走流程” | 系统化调试比猜测加试错的折腾更快。 |
| “先试这个，再调查” | 第一次修复会奠定做事模式。从一开始就做对。 |
| “确认修复有效后再写测试” | 未经测试的修复不牢靠。测试先行才能证明。 |
| “同时修多处省时间” | 无法隔离出哪项改动有效，还会引入新缺陷。 |
| “参考太长，我调整一下模式就行” | 不完整的理解必然带来缺陷。完整阅读。 |
| “我看到问题了，让我修” | 看到症状 ≠ 理解根本原因。 |
| “再试一次修复”（已经失败 2 次以上） | 失败 3 次以上 = 架构问题。质疑模式，不要再修一次。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误、复现、检查改动、收集证据 | 理解发生了什么，以及为什么。 |
| **2. 模式** | 寻找正常示例、比较 | 找出差异。 |
| **3. 假设** | 建立理论、进行最小化测试 | 确认假设，或形成新假设。 |
| **4. 实施** | 创建测试、修复、验证 | 缺陷解决，测试通过。 |

## 当流程显示“没有根本原因”

如果系统化调查表明，问题确实来自环境、依赖时序，或由外部因素造成：

1. 你已经完成此流程。

2. 记录调查过的内容。

3. 实施适当的处理（重试、超时、错误消息）。

4. 添加监控或日志，供未来调查使用。

**但是：** 95% 的“没有根本原因”情况，其实是调查不完整。

这些技巧是系统化调试的一部分，位于此目录中：

- **`root-cause-tracing.md`**——沿调用栈反向追踪缺陷，找到最初的触发源。

- **`condition-based-waiting.md`**——用条件轮询替代任意设置的超时时间。
